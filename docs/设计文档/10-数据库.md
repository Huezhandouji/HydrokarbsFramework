**设计说明**

| 决策 | 理由 |
|---|---|
| UUID 存 `BINARY(16)` 而非 `CHAR(36)` | 主键索引体积 1/3,`match_participant` 这类明细表行数最多,收益最大 |
| 偏好放 `settings JSON` 而非逐列 | 偏好会持续增加;JSON 列免迁移。**但不要**把统计数字塞进 JSON——无法索引聚合 |
| `best_score` 用 max 语义而非累加 | 同一张表里混了"累加列"和"取极值列",`StatsDelta` 必须区分列语义(§10.3.4 的 `MergeMode`) |
| 无外键指向"角色"或"地图" | 角色 id 来自外部插件、地图 id 来自配置文件,都不是本库的实体。用字符串 + 应用层校验 |
| `match_participant` 有外键 | 同一库内的强关系,级联删除让清理历史变得安全 |
| ★ 会话不建表 | Session 是进程内运行时,重启即无;只有它的**产物**(对局历史)值得落库。`session_id` 只作审计外键字串 |

### 10.2 数据的存放位置划分(MySQL / 内存 / 配置文件)

> **★v1.3 迁宿主线**(21-D1):「MySQL」各行与「DB 连接信息」行随持久化归宿主;「内存/配置文件」各行的口径仍为框架基线(会话与实例状态不落库的原则不变——框架本来也没有库)。

| 数据 | 存放 | 理由 | 权威方 |
|---|---|---|---|
| **地图定义**(区域/出生点/交互点/元数据) | 配置文件 `maps/*.yml` | 静态、需人工编辑、需进版本控制、随地图包分发 | 配置 |
| **世界模板**(`maps/templates/<id>/`) | 文件系统 | 世界副本的母本,随地图包分发 | 文件 |
| **模式参数**(回合数、分数上限、Boss 阈值、大厅倒计时…) | 配置文件 `modes/*.yml` | 调平衡/运营不该重新编译;**大厅参数也是模式参数** | 配置 |
| **角色策略** | 配置文件(默认)+ 模式代码(兜底) | 让服主能禁某个角色而不改代码(**SHDF 扩展线示例**,见 Shdf具体玩法设计案/08;通用口径:领域策略配置优先,模式代码兜底) | 配置优先 |
| **引擎/会话参数**(tick 节拍、拓扑、最短驻留、断线宽限) | `config.yml` | 全局单例 | 配置 |
| **DB 连接信息** | `config.yml`(密码走环境变量/独立文件) | 见 §14.11 | 配置 |
| **会话运行时**(名册、连接态、当前模式、切换状态) | **内存**(`Session`) | 每 tick 读写;进程内概念,**不落库** | Session |
| **对局实时状态**(阶段、计时、比分、存活、目标物状态) | **内存**(`MatchModeInstance`) | 每 tick 都读写,绝不落库 | MatchModeInstance |
| **交接载荷**(Handoff) | **内存**(一次切换的栈上数据) | 用完即弃;要留的(战报)经 Display 展示后也弃,想长期看的进 match_history | — |
| 玩家当前角色 | **内存**(宿主角色系统持有;SHDF 扩展线,随宿主角色桥接引入,见 Shdf具体玩法设计案/08) | 角色系统的既定语义(框架基线不持有该状态) | 宿主角色系统 |
| 玩家运行时状态(team/state/attributes) | **内存**(`Participant`) | 每 tick 读写,实例关闭即弃 | MatchModeInstance |
| 玩家档案(首见时间、偏好、语言) | **MySQL** | 需跨重启跨服 | MySQL |
| 累计/分模式/角色统计 | **MySQL** | 需长期聚合与排行 | MySQL |
| 对局历史与参与者明细 | **MySQL** | 需审计、复盘查询 | MySQL |
| 战绩的"本局累加值" | 内存 `StatLedger` → 结束时转 `StatsDelta` | 避免每杀一人就写库 | 内存 → MySQL |
| 排行榜 | MySQL 查询(虚拟线程)+ 内存 LRU 缓存(TTL 60s) | 排行是读多写少 | MySQL |

> **一句话原则**(保留 v1):**能被 tick 循环碰的东西一律内存;需要活过进程重启或需要聚合排序的东西才进 MySQL。**

#### 10.3.2 虚拟线程执行器

```java
package com.hydrokarbs.data;

/**
 * 数据库 IO 的执行器。
 * ★ 虚拟线程解决的是「阻塞等待 IO 时不占用平台线程」,不是「无限并发」。
 *   真正的并发上限由 HikariCP 的 maximumPoolSize 决定——见 §10.4。
 */
public final class AsyncExecutor implements AutoCloseable {

    private final ExecutorService vt = Executors.newVirtualThreadPerTaskExecutor();
    private final Semaphore inflight;   // 背压:防止一次性提交一万个查询

    public AsyncExecutor(int maxInflight) {
        this.inflight = new Semaphore(maxInflight);
    }

    public <T> CompletableFuture<T> submit(String opName, Supplier<T> blockingWork) {
        CompletableFuture<T> out = new CompletableFuture<>();
        vt.execute(() -> {
            boolean acquired = false;
            try {
                inflight.acquire();
                acquired = true;
                out.complete(blockingWork.get());
            } catch (Throwable t) {
                out.completeExceptionally(t);
                LOG.log(Level.WARNING, "异步操作失败: " + opName, t);
            } finally {
                if (acquired) inflight.release();
            }
        });
        return out.orTimeout(DB_TIMEOUT_SECONDS, TimeUnit.SECONDS);
    }
}
```

#### 10.3.4 `StatsDelta`:区分"累加"与"取极值"列

```java
package com.hydrokarbs.data.model;

/**
 * 一次落库的增量。用 MergeMode 显式区分列的合并语义——
 * 这是最容易写错的地方:把 best_score 写成加法会越刷越高。
 */
public record StatsDelta(
        UUID uuid,
        String modeId,
        Map<StatColumn, Long> accumulate,   // SUM 语义:击杀、死亡、时长、伤害
        Map<StatColumn, Long> extremum,     // MAX 语义:best_score
        long matchesPlayedDelta,
        long matchesWonDelta
) {}

public enum StatColumn { KILLS, DEATHS, DAMAGE_DEALT, DAMAGE_TAKEN,
                         OBJECTIVES_DONE, BOSS_KILLS, PLAY_SECONDS, BEST_SCORE }
```

#### 10.3.5 `StatsFlusher`:write-behind(避免每杀一人写一次库)

```java
package com.hydrokarbs.data;

public final class StatsFlusher {

    private final ConcurrentMap<StatKey, StatsDelta> pending = new ConcurrentHashMap<>();
    private final StatsRepository repo;
    private final AsyncExecutor executor;
    private final ScheduledExecutorService scheduler = Executors.newSingleThreadScheduledExecutor(
            Thread.ofPlatform().name("hydrocarbs-flush").daemon(true).factory());

    /** 主线程调用:纯内存合并,零阻塞。 */
    public void accumulate(StatsDelta delta) {
        var key = new StatKey(delta.uuid(), delta.modeId());
        pending.merge(key, delta, StatsDelta::merge);
    }

    public void start(Duration interval) {
        scheduler.scheduleAtFixedRate(this::flushSafely,
                interval.toMillis(), interval.toMillis(), TimeUnit.MILLISECONDS);
    }

    /** 实例结束时主动冲刷(不阻塞主线程,返回 future 供观察)。 */
    public CompletableFuture<Void> flushNow() {
        var batch = drain();
        if (batch.isEmpty()) return CompletableFuture.completedFuture(null);
        return repo.applyDeltas(batch);
    }

    /** onDisable 调用:有界等待,绝不挂死 watchdog。 */
    public void drainAndShutdown(Duration budget) {
        scheduler.shutdown();
        try {
            flushNow().get(budget.toMillis(), TimeUnit.MILLISECONDS);
        } catch (TimeoutException | InterruptedException | ExecutionException e) {
            LOG.warning("统计落库未在 " + budget.toSeconds() + "s 内完成,放弃剩余 "
                    + pending.size() + " 条(内存数据已尽力而为)");
        }
    }
    private synchronized List<StatsDelta> drain() { ... }
    private void flushSafely() { try { flushNow().join(); } catch (Throwable t) { /* 不因一次失败中断定时器 */ } }
}
```

**写放大核算**(保留 v1):"每次击杀写一次库" = 20 人 20 分钟对局约 400 次写;write-behind = 30s 一次 + 结束一次 ≈ 41 次,降一个数量级,崩溃损失窗口 30s。

### 10.4 连接池选型与配置要点(HikariCP)

> **★v1.3 迁宿主线**(21-D1):HikariCP/`mysql-connector-j` 依赖与 shade 义务随 L5 出框架(框架 jar 零 DB 依赖);选型结论对宿主线仍有效。

**选型理由**(保留 v1):HikariCP 是 Paper 生态事实标准,零依赖、`getConnection()` 延迟最低;替代方案(DBCP2 落后、C3P0 停维护、自研池是负资产)不考虑。

```java
package com.hydrokarbs.data;

public final class Database implements AutoCloseable {

    public static Database create(DbConfig cfg) {
        var hc = new HikariConfig();
        hc.setJdbcUrl("jdbc:mysql://" + cfg.host() + ":" + cfg.port() + "/" + cfg.database()
                + "?useSSL=false"                        // 内网/本地:避免握手开销与证书问题
                + "&allowPublicKeyRetrieval=true"        // MySQL 8 caching_sha2_password 必需
                + "&characterEncoding=utf8"
                + "&connectionCollation=utf8mb4_unicode_ci"
                + "&serverTimezone=Asia/Shanghai"
                + "&useServerPrepStmts=true"
                + "&cachePrepStmts=true"
                + "&prepStmtCacheSize=250"
                + "&prepStmtCacheSqlLimit=2048"
                + "&rewriteBatchedStatements=true"       // ★ 批量 UPSERT 提速的关键
                + "&tcpKeepAlive=true");
        hc.setUsername(cfg.username());
        hc.setPassword(cfg.password());

        // ★ 虚拟线程不需要「一人一连接」。池只该有 8~12 条。
        hc.setMaximumPoolSize(cfg.maxPoolSize());        // 默认 10
        hc.setMinimumIdle(cfg.minIdle());                // 默认 2

        hc.setConnectionTimeout(5_000);                  // ★ 必须 < 服务端 watchdog 容忍度
        hc.setValidationTimeout(2_000);
        hc.setIdleTimeout(60_000);
        hc.setMaxLifetime(1_500_000);                    // ★ 25min,短于 MySQL wait_timeout 且留余量
        hc.setKeepaliveTime(120_000);                    // 防中间件静默断连

        hc.setPoolName("HydroKarbsPool");
        hc.setLeakDetectionThreshold(10_000);            // 借出 >10s 未还 → 打日志
        hc.setRegisterMbeans(false);
        hc.setConnectionInitSql("SET NAMES utf8mb4");

        // ★ 关键:不要让建池失败拖死 onEnable。负数 = 不重试也不抛,首个 getConnection 才真正建连。
        hc.setInitializationFailTimeout(-1);

        return new Database(new HikariDataSource(hc));
    }

    public boolean isReady() { return ds != null && !ds.isClosed(); }
    public DataSource dataSource() { return ds; }

    @Override public void close() { if (ds != null) ds.close(); }
}
```

**要点清单**

| 要点 | 数值/做法 | 为什么 |
|---|---|---|
| 池大小 | 10(8~12 区间) | 虚拟线程 ≠ 连接;连接是有限的,池是背压阀 |
| `maxLifetime` | 25 min | 短于 MySQL `wait_timeout`,避免用到已被服务端关闭的连接 |
| `connectionTimeout` | 5 s | 快速失败让上层降级为内存模式 |
| `leakDetectionThreshold` | 10 s | 抓"忘记 close"的经典泄漏 |
| `InitializationFailTimeout` | **-1** | 让 `onEnable` 不因库不可用而卡死/失败 |
| `rewriteBatchedStatements` | true | 批量 UPSERT 提速 3~10× |
| 不用 `DriverManager` | 一律 `dataSource.getConnection()` | `DriverManager` 每次做驱动发现 + 不池化 |
| 事务粒度 | 明细表批量写一事务 | 一局 20 人不应产生 20 次提交 |
| JDBC 虚拟线程钉扎 | Java 21 下 `synchronized` 会钉住载体线程;调试期可加 `-Djdk.tracePinnedThreads=short` | 排查"虚拟线程不虚拟" |

### 10.5 主线程 / 数据库线程的交互边界(必答)

> **★v1.3 保留为框架基线**(21-D1 分割注):本节是 `util/Threads` 与「主线程单点回程」纪律(★8、15 §15.3)的设计权威——**不随持久化出框架**;表中「玩家统计读取/排行榜/StatsFlusher」等 DB 行为历史口径(迁宿主线后由宿主遵守同一铁律),「读配置/世界模板复制/发送消息/Bukkit 状态」各行与 `Threads` 回程口为框架现行基线。

> 宿主扩展线 API(如角色系统桥接的 `RoleFacade#*`)不在本表展开——它们同受「触碰玩家实体状态 ⇒ 主线程」铁律约束,逐方法线程口径见 Shdf具体玩法设计案/08-角色桥接.md(框架基线无此 API)。

| 操作 | 必须在哪个线程 | 为什么 |
|---|---|---|
| 读 `Session` / `SessionRoster` / `MatchModeInstance` 状态 / `AttributeBag` | **主线程** | 这些结构**不是线程安全的**,且每 tick 在变 |
| 改会话/实例状态(比分、阶段、目标进度、切换) | **主线程** | 同上,且可能连锁触发事件派发 |
| 发 `MatchModeInstanceEvent` / `SessionEvent` | **主线程** | 派发是同步的,订阅者会改状态 |
| 世界操作(实体生成、传送、改方块、加载/卸载世界) | **主线程** | Bukkit API 铁律 |
| 发送消息 / BossBar / Sidebar / 音效 / 粒子 | **主线程** | Adventure & 实体 API |
| 注册/注销 Bukkit 监听器 | **主线程** | `registerEvents` 内部会碰服务端状态 |
| 读 `config.yml` / 解析 `maps/*.yml` + `modes/*.yml` | **虚拟线程**(文件 IO + 反序列化)→ 回主线程注册 | 解析是可并行的纯计算 + IO |
| **世界模板复制**(切换阶段 A6) | **虚拟线程**(文件 IO)→ 加载世界回主线程 | 复制是纯 IO;`WorldCreator` 必须主线程 |
| 迁移 DDL、`schema_version` 查询 | **虚拟线程** | 纯 IO |
| 玩家统计读取、排行榜查询、对局历史写入 | **虚拟线程** | 纯 IO |
| `StatsFlusher#accumulate` | **主线程**(但只做内存合并) | 输入来自主线程状态,且必须零阻塞 |
| `StatsFlusher#flushNow` 的 SQL 执行 | **虚拟线程** | 纯 IO |
| `onDisable` 的 `drainAndShutdown` | 主线程发起,**有界等待**(≤ 3 s) | 主线程被服务端等待;久等会触发 watchdog |

**边界铁律与胶水代码**(保留 v1):

```java
package com.hydrokarbs.util;

/** 异步 → 主线程的唯一回程口。所有跨线程回调必须经它。 */
public final class Threads {

    private static Plugin plugin;

    public static void init(Plugin p) { plugin = p; }

    /** 在虚拟线程里跑阻塞逻辑;结果在主线程消费。 */
    public static <T> void supplyThenOnMain(
            Supplier<T> blockingWork, Consumer<T> onMain, Consumer<Throwable> onError) {
        CompletableFuture.supplyAsync(blockingWork, ASYNC_EXECUTOR.asExecutor())
                .whenComplete((value, err) ->
                        Bukkit.getScheduler().runTask(plugin, () -> {
                            if (err != null) onError.accept(err);
                            else            onMain.accept(value);
                        }));
    }

    /** 已在主线程时不要重复调度(会被判定为"下一 tick")。 */
    public static void runOnMain(Runnable r) {
        if (Bukkit.isPrimaryThread()) r.run();
        else Bukkit.getScheduler().runTask(plugin, r);
    }
}
```

> ★ **两条容易踩的规则**(保留 v1):
> 1. `CompletableFuture#thenAccept` 的回调运行在**完成它的那个线程**。**必须**显式 `runTask` 回主线程。
> 2. `Bukkit.getScheduler().runTask(...)` 在主线程调用时会**延后到下一 tick**。统一用 `runOnMain` 判断。
> 3. **反向绝对禁止**:主线程不得 `future.get()` 阻塞等待 DB(唯一例外:`onDisable` 的有界冲刷)。`switchMode` 的 `CompletableFuture` 同理——发起后由 ticker 在后续 tick 检查完成状态,绝不阻塞等待。

## 1. 决策 D1~D5

### D1:持久化整体出框架(R1)

**决策**:框架基线不含任何持久化。移除清单(框架包树与构建的 diff):

| 移除项 | 说明 |
|---|---|
| `data/**`(L5 全包:Database/AsyncExecutor/MigrationRunner/StatsFlusher/DbConfig/repo//model/) | 持久化实现整体出框架;§10.1~§10.4 设计资产加存档注保全(供宿主线参照) |
| build 依赖 `com.zaxxer:HikariCP` / `com.mysql:mysql-connector-j` 与 shadow shade 义务 | 框架 jar 不再携带 DB 栈;`sql/001_init.sql` 资源目录同删 |
| `engine/port/PersistencePort` 接口 | **连接口一起删**:该端口今日**零消费者**(引擎内核不调它,组件经 Spec 构造数据避开它,唯一规划中的调用方是 5.4 的 `PersistencePortImpl` 自证)——为不存在的消费者保留公共契约,正是 A13/A9 判据反对的 hypothetical seam(假想接缝) |
| `bridge/persistence/PersistencePortImpl` | L1 防腐层的 DB 出口随之消失;`bridge/` 只余 `config/`、`world/`(框架基线)与宿主扩展示例 `role/` |
| config `database:` 块(九键) | 连接信息/密码方案随宿主线自理(secrets 方案归宿主插件数据目录) |
| config `engine.shutdown-flush-budget-seconds` | 见 D4-② |

**理由**:①**纯框架哲学**——框架的机制词汇是「会话/切换/组件/端口」,而 `player_stats`/`match_history`/排行榜是**战绩域词汇**:哪张表、哪列指标、要不要 role 维度,全部由宿主玩法决定(§10.1 的 `boss_kills` 列本就是玩法线示例列);框架持有它们 = 框架与某一个小游戏的实现相关,违背用户哲学。②**假想接缝判据(与 A13/A9 同源)**——A13(00 §0.2-13):「存在真实消费者诉求才做,不做 hypothetical seam」;A9(00 §0.2-9):「不提供运行期装饰入口,杜绝加载顺序地狱」。`PersistencePort` 自 v1 定义至今零消费者,却占据 `engine/port/` 公共契约位、`ApiSurfaceTest` 白名单反面词表与 01/11/12 多处分层口径——接口留守会让「框架该不该带 DB」在每次扩面时重新开庭;删掉后真有跨玩法通用持久化诉求时,再按 A13 以真实消费者立项(届时走「只增不改」新版本裁决,不欠历史债)。③**发行中立(R3 同源)**——框架 jar 携带 HikariCP/驱动 shade 与 `database:` 配置面,对不需要 DB 的宿主是死重;「可选降级」(A4)的复杂度整个随包消失。

**归宿(主线)**:宿主自建持久化——经**自己的组件**(如 `StatsComponent` 的 `StatsDelta` 出口消费方)或**自己的进程级服务**(宿主 `service/` 内自建仓储/Flusher,装配纪律照 v4.1 ServiceRegistry 先例)直连**自己的 DB 栈**(依赖、连接池、迁移、secrets 全部宿主自理)。框架侧保留的接口面:`component/stats/StatsComponent`(采集 + `LAST_SUMMARY` 交接)与 `StatsDelta` 值对象——**采集是组件行为,落库是宿主消费**;两者之间的接线(谁订阅、何时 flush)归宿主线设计。

**分割注(存档不销毁)**:10-数据库整篇不删除——头部加「v1.3 分割注」:§10.1~§10.4(DDL/存放划分/访问层/连接池)迁宿主线参照;**§10.5(Threads 与线程边界)例外保留为框架基线**——它是 `util/Threads` 与「主线程单点回程」纪律的设计权威(★8 的依据),不随持久化出框架。施工侧 5.3/5.4 头部加「v1.3 迁宿主线」撤销注(文件保留);★10~★12 归属改标(§4)。

### D2:表现层出框架(R2)

**决策**:框架基线移除 `component/display/**`(DisplayComponent/DisplayModel/DisplayLine/LineStyle/Countdown/Progress)、`render/**`(BossBarRenderer/SidebarRenderer/TitleRenderer/CountdownRenderer)与 config `display:` 块;施工子阶段 4.3 撤销;06 §6.2 全部设计资产迁 `Shdf具体玩法设计案/10-表现层组件.md`(标注「自框架 06 §6.2 v1.3 迁入」),**保全不销毁**;Shdf 侧 README 索引加一行,其余正文不动。

**理由**:①BossBar/侧边栏/Title 的**行内容是玩法语义**(比分行、战报行、目标进度——§6.2 自己的示例就要读 `StatsComponent.LAST_SUMMARY`);「渲染什么」由玩法决定,框架持有渲染器族与刷新节拍配置,与「框架不认识内容」相悖——`DisplayPort` 早在 v3.1 就以同一理由删除(00 §0.5.3),本条是把同一裁决推到组件与配置面。②display 组件在框架内的唯一结构性收益是「组件登记显示、stop 统一回收」(§2.5 登记资源)——该机制属组件基类(登记口通用),不要求框架自带一个渲染组件;宿主自建 display 组件同样能经既有登记口回收。③与 R1 同构:框架配置面(`display:` 块的开关与时长)是玩法偏好,不是框架节律。

**计数处置**:06 §6.1 表 #12 行加迁出注(行保留指向 Shdf 侧 10);P3 组件计数 **L3 实数 21→20**(16 §16.1 P3 行加注:`component/**` 表 24 行中 #12 亦迁出,#20~#22 原已迁玩法线;框架交付行数 20)。阶段4 出口闸门「21 行组件单测全覆盖」同步 21→20(施工计划/完成清单 同步注明计数变化)。

**保留(R4 前半,见 D4)**:`performance.component-budget-ms` 不随 display 出框架——它观测的是**任意组件(含跨 jar 第三方贡献)的单 tick 预算**,是 v1.1 D9③ 信任边界观测键,属框架机制而非玩法参数。

### D3:发行配置中立化(R3,含空值语义)

**决策**:框架发行配置(`config.yml`)不携带任何玩法缺省值。`config-version` 2→3。逐项:

1. **`session.initial-mode` 默认改空**(`""`),注释引导「填你自己的模式 id」;L0 装配读键的缺省兜底同步改空串(不再有 `"lobby"` 字样)。**空值语义**:`initial-mode` 为空或未注册 → 启动装配记 **WARN(不再 ERROR)**,会话**保留待后补切换**(名册为空待机;模式后补注册或管理员 `/sm switch` 后进入运行;运行期加入在有实例之前无实例可摆——「有成员必有实例」底线不破)。
2. **`session.fallback-mode` 默认改空**;**为空或未注册 → 切换回退链跳过一级(fallback 切换)、直接执行二级 dissolve**(全员传送主城、SEVERE、`SessionDissolved`)——回退链仍是「fallback → dissolve」两级的**机制**,只是空配置下第一级不可用。
3. **`arenas` 示例行注释化**:`initial-mode`/`map-pool` 里的 `lobby`/`crossfire` 等示例值全部注释化,改为占位说明。
4. **A3 表述改为**:「回退去向 = 配置指向的**任意已注册模式**,框架不设出厂模式」(00 §0.2-A3 加注;引擎源码零模式字面量的既有断言不变)。

**理由**:「默认 lobby」让框架发行包隐含一个它并不提供的模式(lobby 属 SHDF 玩法线,框架基线无任何模式)——v1.0 剥离玩法后这是残留的出厂偏好;空缺省 + WARN 保留语义让「零玩法配置起框架」成为**合法状态**(纯框架自检/测试部署),配置正确性责任显式交还服主。与 ★4(引擎/组件无 mode id 字面量)同源:配置缺省值是同一纪律在发行面的缺口。

**空值语义的边界**:本条只改「装配/回退」两条路径的空值行为;切换两阶段算法、min-dwell、三级回退的机制代码零改动(空 fallback 走的仍是既有「无可用回退目标 → dissolve」分支,该分支 v1.1 D8 已有:玩法插件 disable 摘模式后无回退即 dissolve)。

### D4:信任边界键保留与 flush 键废止

①**`performance.component-budget-ms` 保留**——v1.1 D9③ 的信任边界观测键:观测对象 = 任意组件(实例级/会话级/跨 jar 第三方贡献)的单 tick `update` 耗时,与「观测谁渲染」无关;删它会在跨 jar 场景(★48/★53)留下观测盲区。它是框架机制键(同 `tick-period`),不是玩法参数。②**`engine.shutdown-flush-budget-seconds` 废止**——它唯一服务于 `StatsFlusher#drainAndShutdown` 的停服有界冲刷(≤3s,§10.3.5/§16.4 铁律③的例外条款),随 L5 持久化整体迁宿主线;框架 `onDisable` 不再有任何 DB 冲刷语义(停服路径回归 `EngineTicker.close()` 既有三步:取消任务 → dissolve 全部会话 → services.shutdown)。

### D5:启动建会话特性删除,会话创建权移交宿主

**决策**:删除「启动即自动创建会话」特性。`HydroKarbsAssembly` 的**整段拓扑装配**(topology 读取 / rotation·arena 分支 / 建会话循环 / 启动期首切换)移出框架基线——框架 `onEnable` **零会话**,「零会话起服」为合法状态(`EngineTicker` 空转与 `onDisable` 对空会话集的解散循环本就幂等,无需改);**会话创建权移交宿主**。随装配分支删除的配置键:

| 删除键 | 说明 |
|---|---|
| `session.topology` | 部署形态(rotation/arena)不再是框架配置——拓扑 = 宿主调几次 `SessionService.create(SessionSpec)`(§3.6 引擎零感知口径更纯粹) |
| `session.arenas` | 竞技场清单随拓扑分支删除;要几个会话、各绑什么地图池,由宿主构造各自的 `SessionSpec` |
| `session.initial-mode` | 开局进什么模式由宿主填 `SessionSpec.initialModeId`(字段保留,每会话首切换目标);D3-① 的「启动装配读 initial-mode、空值 WARN 待机」路径随装配消失 |
| `session.dissolve-after-empty-seconds` | 唯一框架侧消费者就是被删的 arena 装配分支——空场组件时长此后由宿主组装 `SessionSpec.sessionComponents` 时自供(直接给 `EmptyArenaComponent.Spec` 的 `after`) |

**保留**:`session.fallback-mode`/`session.min-dwell-ticks`/`session.disconnect-grace-seconds` 三键——`SessionServiceImpl` 全局消费的内核节律(切换回退去向/防切换风暴/断线宽限),与谁建会话无关。

**理由**:①与 R3 同源且更进一步——`topology`/`arenas`/`initial-mode` 是框架替宿主预设的**部署形态与开局动作**(建几个会话、开局进哪个模式),属玩法编排而非框架机制:rotation 还是多竞技场并行、开局进大厅还是直接进对局,全是宿主玩法线的编排决定;框架持有这些键 = 框架对「会话怎么开」做了玩法缺省,违背用户哲学。②`SessionService.create(SessionSpec)` 本就是会话唯一创建路径(§3.2 冻结签名),且 v1.1-D14 的 `MiniGameApi.createSession(...)`/`SessionRecipe.initialModeId` 已确立「调用方填初始模式」的第三方建会话形态——D5 把宿主拉平到同一口径,框架不再有一条只属于自己的特权装配路径。③启动期首切换是日志噪音与状态分叉源:`onEnable` 期间玩法模式可能尚未注册(形态 B 还要 v1.1 的「拓扑装配延迟至首 tick/`ServerLoadEvent`」补丁,12 §12.1 要点①)——创建权移交后,宿主在自己的编排点(全部插件 enable 完成后)调 `create`,**启动期不再发生任何切换**,该噪音源整体消失,装配延迟补丁随之作废。

**语义后果**:①会话唯一创建路径仍是 `SessionService.create(SessionSpec)`(§3.2 冻结签名不动);宿主填 `initialModeId` → `create` 内既有机制「发 `SessionCreated` → 走首次 switchMode(初始模式)」不变(§3.8 装配流程零改动)——目标未注册时走 §3.2-A1 `MODE_NOT_FOUND` 拒绝、会话保留零实例零名册待机(与 D3-① 待机语义同构,触发点自框架装配移至宿主参数)。②拓扑 = 宿主调几次 `create`(§3.6);③启动期不再发生任何切换;④`EmptyArenaComponent` 机制零改动(★31 原样):挂不挂、`after` 给多少,全是宿主组装 `SessionSpec.sessionComponents` 时的声明——「rotation 不挂 = 永不解散」的口径不变,只是挂载决定权自 L0 移宿主;⑤`SessionPolicy` 的 `topology`/`dissolveAfterEmptySeconds` 字段随键删除失去框架消费者(节律收敛为 min-dwell 与断线宽限,`fallback-mode` 仍构造注入)——字段瘦身为宿主线回填项(§5-7),本修正案不动 `engine/session` 内部结构。

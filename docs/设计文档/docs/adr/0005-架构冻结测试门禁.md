# ADR-0005:架构冻结测试门禁——测试即架构

- 状态:已接受(2026-10-18,阶段 1.4「架构冻结测试」落盘)
- 关联:施工计划总览 `设计案/施工计划/README.md` §3-4(测试即架构)、`设计案/16-路线图与验收.md` §16.2(★1/★2/★3/★4/★13/★22/★23/★24/★25/★26)、`设计案/02-核心概念.md` §2.6/§2.7/§2.8-决断二、`设计案/14-陷阱清单.md` §14.12/§14.21/§14.23/§14.24/§14.25/§14.26、施工计划 `1.4-架构冻结测试.md`;ADR-0001(大厅即模式)、ADR-0002(聚合根零行为与引擎纯度)、ADR-0004(会话级组件)
- 落地位置:`ShdfMatchPlugin/src/test/java/com/shdf/match/architecture/`(LayeringTest、AggregatePurityTest、EnginePurityTest、EngineHasNoModeStringsTest、InstanceServicesMembersTest)、`ShdfMatchPlugin/src/test/java/com/shdf/match/engine/`(AttributeNamespaceTest、ComponentResolutionTest)

## 背景(Context)

设计案把九条架构命题写成"可机械检验"的验收(§16.2),但它们此前只是文档里的句子:聚合根"零行为"、引擎"零状态机零内容词汇"、svc"三成员封闭"、组件"无 mode id 字面量"、组件"只写自己命名空间"。工程里没有任何东西阻止实现者在赶工的那一天顺手加一个方法、写一个 `if (mode.id().equals("lobby"))`、往 `InstanceServices` 里塞第四个成员——§14.12/§14.21/§14.23/§14.24/§14.25/§14.26 记的就是这六种反弹,它们共同的特征是:**第一次妥协都无害,第三次妥协时架构已经塌方**。

1.4 把这九条命题变成七个可执行的测试类(纯 JUnit + ArchUnit,离线可跑,无需活服)。

## 决策(Decision)

### 1. 测试即架构,建立即永久生效

七类测试与它们的冻结面:

| 测试类 | 验收 | 冻结什么 |
|---|---|---|
| `LayeringTest` | ★1/★2/★3(先建)/★23 | L2 不认识 L3/L4;模式互不依赖;仅 `bridge.role` 碰角色插件;仅 `component.role` 碰桥接;api 只依赖 engine/JDK/Paper |
| `AggregatePurityTest` | ★22 | `MatchMode` 公开方法集**恰为** 9 个;类 final、无 public 构造器 |
| `EnginePurityTest` | ★24 | `engine/**` 源码零禁词(Phase/Rule/WinCondition/EndCondition/Role/Team/Score/Objective) |
| `EngineHasNoModeStringsTest` | ★4/★13 | `engine/**`+`component/**` 零 mode id 字面量(**含 `lobby`**) |
| `InstanceServicesMembersTest` | ★25 | record 组件集恰为 `(self, components, modeInfo)` |
| `AttributeNamespaceTest` | ★26 | 跨命名空间写被拦;`Key` 常量的引用者与它同包(ArchUnit 复核腿先建) |
| `ComponentResolutionTest` | §2.6 六行 + §2.3 前置闸 | 依赖校验算法逐行;`createInstance` 校验不可绕过 |

**此后任何阶段不得为通过功能而放宽断言**。测试红了的唯一正确动作是"把行为还给组件 / 把词汇赶出引擎"(§14.23/§14.24/§14.25/§14.26 的规避),而不是改断言、加豁免、删测试。

### 2. 修改测试须在 PR 中单独说明理由

发现测试本身写错(或设计演进确需改判定)时,修测试**必须在同一个 PR 里单独说明理由**:说明它为什么不是"为通过功能放宽断言",并给出设计案出处。评测者以本 ADR + `施工计划/README.md` §4 的「验收 → 阶段映射表」核对。**测试断言是架构的执行体,不是实现的可调参数。**

### 3. `LayeringTest` 的包锚定修正(与 §16.2 字面写法的唯一差异;命题不变)

§16.2 代码块用 `"..mode.." / "..component.."` 这种口语化写法。ArchUnit 的 `..` 匹配**零个或多个**包段,照抄会把引擎自己的 `com.shdf.match.engine.mode` / `com.shdf.match.engine.component` 子包卷进禁止集——引擎每一处"引用自家子包"都会变成红灯。

- **修正**:锚定到 L3/L4 顶层包——`com.shdf.match.mode..` / `com.shdf.match.component..`。
- **命题不变**:"L2 内核不认识 L3 组件与 L4 模式"逐字保持(引擎不位于锚定包下,判定对象集仍是 §16.2 原意的那两个包)。
- **实测反证(1.4 破坏性自检副产品)**:临时把该规则改回字面写法跑 `./gradlew.bat test --console=plain`,`engineMustNotKnowModes` 报 **209 次 violation**,全部是引擎类依赖自家 `engine.component` 子包(如 `AttributeBag` → `MatchModeComponent`、`MatchMode` → 自身嵌套 `ComponentEntry`);恢复锚定写法后同一命题零 violation、全绿。
- **判定**:**检验方式的技术修正,不是放宽断言**。已记录于 `施工计划/阶段1/README.md` §4 风险表、`1.4-架构冻结测试.md` 步骤 1 与类注释。

### 4. 目标包尚未落盘的规则,以 `allowEmptyShould(true)` 放行"空集"这一合法状态

三条规则在本阶段作用于**还不存在**的包:`modesMustNotKnowEachOther`(★2,`mode/**` 建于阶段 5/6)、`apiDependsOnlyOnEngine`(`api/**` 建于阶段 7)、`AttributeNamespaceTest` 的 ArchUnit 复核腿(★26,`component/**` 的实体组件建于阶段 4)。ArchUnit 1.3 默认把"没检查到任何类"判为**失败**(防止规则静默失效),实测这三条因此报"failed to check any classes"。处置:对这三条显式 `allowEmptyShould(true)`——放行的是"目标包尚不存在"这一合法状态,**断言本身零改动**,规则在所涉包落盘后自然开始有牙齿(§16.2 映射表的"规则先建"口径)。其余规则(`engineMustNotKnowModes`/`onlyBridgeImportsRolePlugin`/`onlyRoleComponentTouchesBridge`)选择集非空,**保持默认严格**:对象集变空即失败。

### 5. v4 增补条款:只预留判定、不实现

`component/session/**` 归 L3(锚定禁入集天然覆盖)、`InstanceServices` 三成员不变(会话服务集是独立 record `SessionServices`)、`InstancePort#session()` 允许——三条为**判定补充**、不新增禁止项、不放宽既有断言,实现落在施工计划 2.6(§16.2 ★v4 修订注、`设计案/17-v4变更指示书.md` §7)。

## 破坏性自检(1.4 步骤 8 的实测记录;均已还原并复验全绿)

| 注入 | 期望红灯 | 实测 |
|---|---|---|
| `MatchMode` 临时加一个公开方法 `isRoundBased()` | `AggregatePurityTest` | 红:31 tests, 1 failed;`expected: <[…9 个…]> but was: <[…, isRoundBased, …]>` |
| `engine/AttributeBag.java` 临时写一词 `"lobby"` | `EngineHasNoModeStringsTest` | 红:报 `src\main\java\com\shdf\match\engine\AttributeBag.java:27 → lobby` |
| `InstanceServices` 临时加第四个成员 `ConfigPort config` | `InstanceServicesMembersTest` | 红:`expected: <[self, components, modeInfo]> but was: <[self, components, modeInfo, config]>` |
| `LayeringTest` 临时改回 §16.2 字面包写法 | `engineMustNotKnowModes` | 红:209 次 violation(锚定修正的理由实证,见决策 3) |
| `engine/EngineTicker.java` 注释里临时写一词 `PhaseChanged` | `EnginePurityTest` | 红:报 `EngineTicker.java:14 → PhaseChanged`(★24 扫描含注释的实证) |

每次注入都只触发**目标测试**变红(其余用例保持绿),证明测试确实在守门,而不是"全绿因为什么都没测"。

## 后果(Consequences)

- **正面**:§16.2 的九条从"文档承诺"变成"构建期事实";六种反弹(§14.12/§14.21/§14.23/§14.24/§14.25/§14.26)各自有一个机械执法点;越界的第一步(加方法 / 写禁词 / 写 mode id / 碰桥接 / 加 svc 成员 / 跨命名空间写)就在 CI 级别的红灯里,不依赖记忆与自律。
- **负面/成本**:每个阶段的收尾都要跑一次架构测试;"测试红了怎么办"有且只有一个答案(改代码,不改断言);断言本身写错时的修复要走 PR 说明流程(决策 2)。
- **不可逆点**:本 ADR 一旦生效,§16.2 的冻结面变成**只能收紧、不能放宽**的契约——它同时是后续阶段"顺手一下"的预先否决。

## 未决(提请上游裁决)

- **源码扫描类测试的输入未纳入 Gradle 输入快照(★24/★4 的门禁静默风险)**:`EnginePurityTest`/`EngineHasNoModeStringsTest` 在运行期读 `src/main/java/**` 的<b>源码文本</b>,但 `test` 任务的输入快照只有"测试类 + 测试类路径(编译产物)",不含主源集文本。实测:把 `EngineTicker.java` 某条 javadoc <b>原地改写</b>加入禁词 `PhaseChanged`(行数不变 ⇒ 字节码不变)后,`./gradlew.bat test --console=plain` 与 `--cleanTest test` 都报 `BUILD SUCCESSFUL`,`test` 走的是 `FROM-CACHE`/`UP-TO-DATE` —— <b>违规没被当场发现</b>;只有 `--rerun-tasks`(或删除构建缓存/在干净工作区 CI)才变红并准确报 `EngineTicker.java:14 → PhaseChanged`。反之,<b>新增行</b>(行号表变化 ⇒ 字节码变化)会被正常重跑并抓到(前述 `"lobby"` 注入即如此)。处置备选:①`tasks.test { inputs.files(fileTree("src/main/java")) }`(或对 scanner 测试单列输入),让主源集文本进入 `test` 的输入快照;②接受现状,以 CI 干净构建为准,并把 `--rerun-tasks` 写进阶段收尾脚本。属 1.4 授权范围外(改 build.gradle.kts),登记待裁决。
- **ArchUnit 的分析对象是否排除 test 类**:`@AnalyzeClasses(packages = "com.shdf.match")` 实测把 test 类一并导入(反证记录里出现 `com.shdf.match.engine.AttributeNamespaceTest$ProbeComponent`)。而 `设计案/12` §12.1 的测试树把未来的测试放在 `com.shdf.match.{engine,session,mode,component,bridge,api}/` 下——与生产同包名。若后续某阶段出现"测试类合法地同时引用 L2 与 L3/L4"(切换/端到端测试最可能),`engineMustNotKnowModes` 会在 test 代码上报假阳性。备选:①`@AnalyzeClasses(..., importOptions = ImportOption.DoNotIncludeTests.class)`(规则只判生产码);②保持现状,由各阶段把跨层测试移出 `engine..` 包。1.4 授权范围只含"包锚定修正",故本版未单方决定,登记为待裁决。

# ADR-0001:大厅作为普通模式,模式切换作为框架一等能力

- 状态:已接受(2026-10-15,架构设计 v2.0)
- 关联:`MC小游戏系统架构设计.md` §2.5 / §3 / §4;`CONTEXT.md`
- 修订注:**部分被 ADR-0004 取代(2026-10-17)**:决策 4(组件只挂实例、不引入会话级组件)由两级挂载取代;决策 3 的名册/世界机制部分保留(空场等策略下放为会话级组件);决策 1/2(大厅是普通模式、switchMode 一等公民)继续有效。详见 `docs/adr/0004-session-level-components.md`。

## 背景(Colontext)

v1 架构把"一局对局(Match)"作为一等公民,大厅只是 config.yml 里的一个回传坐标,换图/换玩法由使用者自己"关旧 Match、建新 Match"。这留下三个空白:

1. 切换的时序、清场、传送、世界处置没有统一保证,每个调用方各写各的;
2. 大厅行为(等人、投票、闲玩)没有落点,最终必然长成引擎里的特判;
3. 同一张图被两个对局并发使用时世界会互相污染(v1 未回答)。

项目目标已经明确:**用同一个角色系统 API 承载差别可能非常大的多种玩法**——这要求框架把"玩法之间的过渡"本身产品化。

## 决策(Decision)

1. **大厅是一个普通 Mode**(实现 `Mode` SPI,有地图/阶段链/组件/EndCondition),出厂自带、默认启用、可替换;引擎源码不出现 `"lobby"` 字面量,回退模式是配置项 `session.fallback-mode`。
2. **模式切换是框架一等方法** `SessionService#switchMode`,两阶段实现:准备阶段(可异步,校验能力/地图/人数/组件依赖,失败则旧实例毫发无损)→ 执行阶段(主线程单 tick 原子:旧实例 onHandoff + close → 名册原地位移 → 新实例 attach),失败三级回退(fallback 模式 → dissolve → 兜底清理)。
3. **引入 Session 常驻容器**:成员名册/连接追踪/世界句柄挂在会话上跨模式存活;`ModeInstance` 的全部状态随 close 销毁,带出数据的唯一通道是类型化 `Handoff`。
4. **组件只挂实例**。会话级行为(名册、连接、空场策略)是 SessionService 内建职责,不引入会话级组件(避免组件模型翻倍)。
5. **`WinCondition` 泛化为 `EndCondition`**,结果加 `NEXT` 种类(非竞技自然走完),下一站由三层决定:EndResult 显式意图 > 外部指令 > 模式缺省 TransitionPolicy。
6. **角色系统从硬依赖改为软依赖 + Capability 声明**(`strict.require-role` 可恢复旧行为)——大厅不需要角色系统,框架必须允许无角色模式存在。

## 备选方案(Considered)

- **方案 A:保留 v1 的 Match 一等 + 大厅特判**。否决:每个"回大厅"的调用方都要手写清场与传送,v1 已证明这会复制粘贴;且无法回答"大厅自身要不要玩法化"(投票/闲玩)。
- **方案 B:会话级 + 实例级两层组件**。否决:会话级行为总共四件事(名册/连接/空场/世界句柄),两层组件模型带来的复杂度远超收益(§2.5)。
- **方案 C:大厅用独立于模式之外的专用子系统实现**。否决:等于在引擎里承认"有一个特殊的模式",通用性从第一行代码开始腐烂;换大厅、第三方大厅都无法实现。

## 后果(Consequences)

- **正面**:任何模式可作回退目标;换大厅零引擎改动(§12.3 验收动作);跨局残留结构性不可能(实例状态全灭 + Handoff 唯一出口);第三方可注册自己的模式并控制切换。
- **负面/成本**:v1 的 Match 族术语全部更名(迁移表见设计文档 §0.5),框架尚未动工,此刻改名零成本;切换机制引入新的失败面(风暴/重入/世界泄漏),以 §13.16–13.22 陷阱清单 + §15.2 验收测试 #13–#21 对冲;世界模板复制带来一次性的磁盘与 IO 成本(REUSE_DIRTY 可摊销)。
- **不可逆点**:术语与包结构一旦实现落地,`Session/ModeInstance/Handoff` 将成为公共词汇(含 MiniGameApi 冻结面),再改即破坏性变更——因此本 ADR 在动工前落定。

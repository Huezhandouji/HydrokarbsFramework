# ADR-0010:API 面收敛与地图注册单通道(v1.4)

- 状态:已接受(2026-10-27)
- 关联:[22-v1.4修正案-API面收敛与地图注册单通道.md](../../22-v1.4修正案-API面收敛与地图注册单通道.md)(变更指示全文);**Supersedes(部分)** [ADR-0008](0008-map-registration.md)——其「决策 3(双通道汇入单点)」与「决策 6 的 reload 口径」(文件式半边)随本裁决退场;0008 其余决策(显式注册 API、交成品不交工厂、模板落盘约定、卸载守卫、WorldPort 边界)继续有效并承载 v1.4 后的地图通道
- 验收:★56~★57(§16.2 追加;★19/★44 冻结快照随 v4 面合法重录——修正案 22 §5 为背书)

## 背景

至 v1.3,同一能力在两处出现了**双口径并存**:

1. **建会话**:`MiniGameApi` 同时暴露 `createSession(String, String)` 与 `createSession(SessionRecipe)`。两参形态自 v1.1 起以「保留,等价于空 recipe」(07 §7.1)悬挂——`SessionRecipe.of(modeId, mapId)` 对两参调用的每个可表示场景逐字段等价,双形态之间没有表达力差异,只有两份冻结清单行、两处 javadoc 口径、两行权限面表、每次讲解都要说两遍的持续成本。
2. **地图注册**:v1.2(ADR-0008)让显式注册与文件装载(`maps/*.yml` 启动扫描)双通道汇入 `MapRegistry` 同一命名空间。落地后,双通道产生了自身的复杂度:同一目录两条「先到者」规则(注册式撞名 vs 与文件式撞名)、`maps` 级 reload 只触碰文件半边的分叉语义(挂 13/15/14 三处口径注)、快照「文件式半边 + 注册式半边」双簿记。而注册通道本身已承载文件通道的全部场景:跨 jar 玩法图 = 解包 + 代码构造 + `registerMap`;动态活动图 = `unregisterMap` + `registerMap`;模板落盘约定(`maps/templates/<mapId>/`)与注册期校验(20-D2/D3)在任何通道下都成立。

两项并存的性质相同:**同一能力维护两份口径,其中一份不提供另一份所没有的能力**。One-Version Rule(07 §7.2 引用;本框架消费面纪律)反对的正是这种状态。

## 决策

1. **建会话单形态(D1/22)**:删除两参 `createSession(String, String)`;`createSession(SessionRecipe)` 为公共 API 建会话唯一形态。迁移口径:两参调用一律改 `SessionRecipe.of(modeId, mapId)`,便捷工厂即迁移目标。
2. **地图注册单通道(D3/D4/22)**:删除「配置文件声明地图」特性——配置装载不再产生任何地图条目(★57);`YamlCodec.readMap`、`MapDefinition.from`、`MapRegistry.replace` 与文件半边、无参构造退场;`MapRegistry` 只剩显式注册/摘除通道,目录顺序 = 注册序。迁移口径:原 `maps/*.yml` 声明改由宿主/玩法插件代码构造 `MapDefinition` 后 `registerMap`(模板仍先解包落盘,14.39 顺序不变;宿主如需"配置驱动地图清单",解析是宿主自己的家务)。
3. **破坏性变更升版本(D2/22)**:`API_VERSION` 3 → 4(破坏性变更必升版本,07 §7.2 版本协商纪律);冻结面 16 → 15 方法,★19/★44 冻结快照以修正案 22 §3 契约骨架为基线合法重录。

## 替代方案(已否)

- **建会话:保留两参,进入 `@Deprecated` 弃用过渡期**(一个次要版本后删,07 §7.2 许可"至多一个次要版本双轨"):否——该许可的双轨上限是为保护无法即时升级的存量消费者设的;当前消费面 = SHDF 宿主与 examples/测试插件,全部随本次施工窗口一并迁移(无外部冻结消费者),过渡期只会延长"等价于空 recipe"解释注的寿命、冻结测试多养一行,收益为零。One-Version Rule 明文"不允许长期双轨",与其短暂双轨不如一次付清。
- **建会话:保留两参重载作为薄便利方法**(`createSession(modeId, mapId)` 内部转 `SessionRecipe.of`):否——便利签名的语义"等价于"必须持续被冻结测试与 javadoc 双平台声明;一旦两形态行为或错误语义出现分歧(如 recipe 侧新增必填字段),"等价"从不变式退化为需要专门维护的承诺。多保留一个方法的成本不是零,收益只是省一次构造调用样板。(若单参便利确实可感,`SessionRecipe.of` 单字符串工厂已是最短形态,且它在冻结清单中只占一行。)
- **地图:保留文件通道为"服主加图"专供**:否——该受众诉求(服主零代码加图)在框架基线场景中没有出现;为其保留整条通道意味着继续维护双先到者语义与 reload 分叉。真实诉求出现时,由宿主插件自理解析自己的声明文件再逐张 `registerMap`(登记 22 §6-Q2),框架不需要任何改动。
- **地图:以 reload 命令统一两半边,而非删文件通道**:否——统一 reload 需要把"插件声明"引入命令可触碰域,与 20-D1「声明所有权在插件」相悖,且 reload 对注册式的正确语义(跳过正用图)早已由 unregister+register 覆盖;把交互修对比把交互删掉贵得多。

## 权衡

- **得**:冻结面 16→15,建会话口径单行;`MapRegistry` 单簿记、目录顺序 = 注册序(自动挑图取序首可预期性不减反增);撞名语义只剩一条(先注册者保留,响亮抛点名先到者与其提供方);07/12/13/14/15 五处双口径注与悬挂解释随文件通道与两参重载一起消失。
- **失**:对消费方是破坏性变更——旧两参调用与旧 `maps/*.yml` 装载行为消失。缓解:14.36 版本拒载纪律(消费方 onEnable 首行检查 + SEVERE + setEnabled(false),不崩服、给出明确日志);迁移口径各一句话(`SessionRecipe.of(modeId, mapId)`;宿主代码构造 + `registerMap`);注册通道的守卫语义(20-D2/D3/D4)一寸不动——模板目录约定、注册期校验、正用摘除被拒,使用方肌肉记忆不变。
- **判据同源**:与 A9/A13「假想接缝」判据同向——不为不存在的便利/受众维护口径;与 21-D1「零消费者的端口删除」同一推理形状,只是本次删的是已有一批消费者的口径,故必须走版本升级 + 迁移口径,而非静默删除。

## 后果

- 正:One-Version Rule 在框架自家的公共面上落成一个可机械检验的形态(冻结清单);地图目录序与撞名答复单语义化;`/sm reload maps` 的分叉注消解为「宿主 reload = unregisterMap + registerMap」。
- 负:API_VERSION 4 的窗口内,未迁移的消费方拒载(行为可预期、日志明确);服主侧原 `maps/*.yml` 手工声明的习惯失效,需宿主插件接手。
- 验收:★56(建会话单形态,冻结测试已更新)/★57(配置装载零地图条目,地图仅经 registerMap 进目录)——命题文本见 22 §5。
- 未决移交:22 §6(Q1 查战绩悬置维持 / Q2 通用声明插件不预置 / Q3 单参便捷工厂不设)。

### 13.3 ★ 换掉出厂示例模式(证明"任何模式无特权"的验收动作)

出厂示例模式(SHDF 的 lobby 大厅,见 Shdf具体玩法设计案/04-大厅模式.md)没有任何特权。比如想要一个"极简空转模式"(`minilobby`:无投票、无自动流转,管理员手动 `/sm switch` 开局)替换它:

| 1 | `mode/minilobby/MiniLobbyFactory.java` | `MatchModeProvider`:Builder 拼一张**最小表**——不挂 Vote/Idle/EndGate(`defaultTransition=STAY`,永远等外部指令),阶段表只有一个 Await 的 Gathering |
| 2 | `resources/modes/minilobby.yml` | 参数 |
| 3 | (经 §13.11 注册通道) | 一张小图:构造 `MapDefinition`(tags 随意/为空)+ 模板落盘 + `registerMap`(★v1.4:原「`resources/maps/lobby_mini.yml` 一份文件」步随文件式装载退场,22 号) | 见 §13.11 |
| 4 | SPI 注册 + 测试 | 同 13.1 |

然后把 `config.yml` 的 `session.initial-mode` 从 `lobby` 改成 `minilobby`(**★v1.3-D5:该键已随启动建会话特性删除——本验收动作同步改为「宿主把 `SessionService.create(SessionSpec)` 的 `initialModeId` 填 `minilobby` 后起服」;「引擎零改动」的验收命题不变**,21-D3/D5)。**引擎零改动**——如果这件事做不到,说明出厂模式被特判了,架构失败。v3 让这个验收更锋利:极简模式与出厂示例模式的差别**只是 Builder 里少了几行 `addComponent`**,连"不挂结束条件"都是一个自然后果(不挂 EndGate 组件,就没有结束判定),不需要任何"关闭结束判定"的开关参数。

### 13.4 ★ 跨插件注册模式(第三方扩展)

第三方插件(不改我们的 jar)。**★v1.1:步骤表含「API_VERSION 检查」首步(D7)——未查版本就调新面方法会崩在玩家路径上(14.36);★v1.6(24 号):注册时序反转——ServicesManager 提供方通道退场,第三方必须 `depend` 框架、`load(MiniGameApi)` 后显式登记(原「先启补收录」场景退役):**

| # | 步骤 | 内容 |
|---|---|---|
| 1 | **依赖声明 + API_VERSION 检查(首步)** | `plugin.yml` 写 `depend: [HydroKarbs]`(**★v1.6:由 softdepend 反转为 depend**——显式注册要求框架先启,原「先启后注册都安全」的事件收录口径退役);`onEnable` 首行:`api == null \|\| api.API_VERSION < REQUIRED_API_VERSION` → SEVERE + `setEnabled(false)`(拒载不崩服,D7/14.36) |
| 2 | **显式注册模式** | `api.registerMode(this, new TheirModeFactory())` → 成功返回 `MatchModeInfo` 并进 `modes()` 目录(注册工厂不是成品,聚合根由框架 `build()` 产出,内含 `verifyDependencies`;坏声明/重复 id **响亮抛**给调用方——onEnable 注册失败 = 拒载信号,可捕获;A9 三限制) |
| 3 | (可选)显式贡献会话组件 | `api.registerSessionComponents(this, specs)`(宿主级会话策略:自定义重连/宽限/准入记账等;干跑合并校验失败响亮抛;**模式无权贡献**,v4-D4) |
| 4 | 解包模板 + 注册地图(带图时) | 按 §13.11:`saveResource` 解包 → 构造 `MapDefinition` → `api.registerMap(this, def)`(先解包后注册,14.39) |
| 5 | 消费 API | 按 §7.5 权限面调用(查询/控制/成员/事件订阅/地图注册;★v1.7:原「能力标签」项随标签机制退场,25 号——外部能力 = 会话组件桥接,见 §13.7 注) |
| 6 | **卸载善后** | `onDisable` **显式反注册**:`unregisterMode(this, modeId)`(触发回退编排)/ `unregisterSessionComponents(this)` / `unregisterMap(this, mapId)` / 订阅句柄 `close()`;**框架 `PluginDisableEvent` 兜底**(★v1.6 四族:能力/模式/地图/会话组件贡献——**★v1.7:能力族随标签机制退场移除,兜底三族:模式/地图/会话组件贡献**,`ProviderUnloadListener`,14.38——兜底不是免死金牌,显式反注册仍是纪律) |

```java
// 第三方插件的 onEnable 里(★v1.6 顺序:load → 版本检查 → registerMode → registerSessionComponents → 解包模板 → registerMap → 订阅/命令)
public class TheirPlugin extends JavaPlugin {
    static final int REQUIRED_API_VERSION = 6;         // 消费方自带的最低版本常量(各消费方自理;★v1.7 现行面 = 6,25 号)
    private MiniGameApi api;

    @Override public void onEnable() {
        MiniGameApi api = getServer().getServicesManager().load(MiniGameApi.class);
        if (api == null || api.API_VERSION < REQUIRED_API_VERSION) {   // ★v1.1-D7:首行检查,拒载不崩服(14.36)
            getLogger().severe("HydroKarbs 缺席或 API_VERSION 过低,禁用 " + getName());
            setEnabled(false); return;
        }
        this.api = api;
        // 注册工厂,不是注册成品——聚合根由框架 build()(内含 verifyDependencies);坏声明/重复 id 响亮抛
        api.registerMode(this, new TheirModeFactory());
        // (可选)宿主级会话组件贡献——干跑校验失败响亮抛;模式无权贡献
        api.registerSessionComponents(this, List.of(new TheirGraceComponent.Spec(/*...*/)));
        // 带图时:先解包后注册(14.39)
        saveResource("maps/templates/their_arena/level.dat", false);   // 解包模板落盘
        api.registerMap(this, TheirMaps.declarations().get("their_arena"));
        // 之后:订阅会话事件 / 命令等消费面(§7.5)
    }
    @Override public void onDisable() {
        api.unregisterMode(this, "their_mode");            // 显式反注册(触发回退编排)
        api.unregisterSessionComponents(this);             // 后续会话不再合并
        api.unregisterMap(this, "their_arena");            // 正用摘除被拒是特性(20-D4)
        // ★v1.7:原「能力标签:无独立反注册法,随 disable 由框架兜底摘除(D8)」注为历史口径——
        // 能力标签机制退场(25 号),兜底收敛三族(模式/地图/会话组件贡献)
    }
}
```

**★v1.6(24 号)**:`MatchModeRegistry` 不再监听 ServicesManager 事件(原 `ProviderServiceListener` 整体删除)——显式 `registerMode` 经同一注册闸(`build` → `verifyDependencies` → id 查重)入表,**注册期双口径合一响亮**(原「启动期响亮 / 运行期 SEVERE + 忽略后来者」的事件口径随通道退场);摘除经 `unregisterMode` 的**回退编排**:`session.fallback-mode` 已配置且已注册 → force 切换回退(豁免 min-dwell,§3.5),否则 `FALLBACK_DISSOLVE` 解散;回退被拒(`SWITCH_IN_PROGRESS`)WARN 放弃不自旋(§14.17)。`MatchModeRegistry` 的 ServiceLoader 半边(本 jar `META-INF/services` 出厂模式)保留不动。约束(写进 api javadoc):第三方工厂只准依赖 `api/` + `engine` 契约 + L3 组件的公开 Spec(★v1.3:原「不准 import `data/**`」为历史口径——该包已出框架基线,禁令空转不减,21-D1);其组件抛异常只会隔离自己的实例(§3.1 quarantine),不会拖垮框架。

### 13.5 若新模式需要"引擎级"新能力(罕见的升级路径)

例如"模式需要两张世界并行"。那么(保留 v1 路径):

1. 先在 `engine/port/` 加**端口接口**(不实现);
2. 在 `bridge/` 加该端口的**实现**;
3. 让需要的组件消费新端口。

**永远不要**在 `engine/` 里 `import mode.xxx`,也**永远不要**为了一个模式把行为方法加回 `MatchMode` 聚合根(§2.8-决断二)。这两条用 ArchUnit + 源码扫描 + `AggregatePurityTest` 机械保证(§16.2)。

```java
}
```

> 软接入的边界(§3.8 跨级查询):**只读**;第一版实例组件**不得订阅会话事件**(未决 §11-Q7)。

**硬依赖——声明能力标签,由切换阶段 A2 挡住**

> **★v1.7 历史口径注(25 号,能力标签机制全链退场)**:本节「硬依赖 = meta 声明能力标签 + 切换 A2 校验」整段读作**历史口径**——A2 退役(§3.2),外部能力硬依赖改由**会话组件桥接**表达:提供方(或宿主自持防腐层)贡献类型化桥接会话组件(`registerSessionComponents`/`SessionRecipe`),消费方组件以 `requires(...)` 类型化声明依赖——**硬依赖缺失在装配期响亮失败**(干跑合并校验/`createSession` 拒绝,会话不创建、不留半装配态),运行期降级/quarantine 由桥接组件自身承接(D14 既有口径;provider 摘除只影响后续会话);软依赖 = `requiresOptional`(既有机制,非新增;★21/★60)。下方代码块与校验点三行保留为 v1.6 前历史写法,不再可用(`MatchModeMeta` 已无 `requiredCapabilities` 分量)。

```java
// 模式工厂的 Builder 链里(§13.1 第 1 步),把硬依赖写进 meta 的能力标签:
// (示例标签 "role" 属 SHDF 扩展线的宿主能力,见 Shdf具体玩法设计案/08-角色桥接.md;框架只认"能力标签"这一机制,不认识任何具体标签)

```

(标签的**提供方** = 会话组件在自己 Spec 上的 `.capabilities("xxx-capability")`,§13.6 第 2 步;词汇由提供方定义,引擎不认识任何具体标签。)

- 校验点:切换**阶段 A2**(§3.2)——`requiredCapabilities ⊆ CapabilityRegistry.available()`,可用集 = 进程级标签 ∪ **本会话**会话组件标签(会话组件标签随装配注册、随 `dissolve` 摘除)。

- 模式侧零代码变化:工厂仍只有 Builder 链(§13.1),硬依赖只是 meta 里多一个标签。

### 13.9 常驻模块选型(★v4.1:先问宿主,再问接缝)

"要加一个常驻能力"时,**先决定宿主,再决定接缝**(决断五,§2.8):宿主 = 组件级 / L1 / 进程级服务 / 伴随插件;接缝 = 是否需要 Port / 组件读口 / 事件 / API——**Port 不是宿主**。给 `MatchModeInstanceServices`/`SessionServices` 加成员永远是错误答案(★25)。

**四案判据(按侵入度从低到高,先问再落):**

| 案 | 形态 | 判据 | 参照 |
|---|---|---|---|
| ① 拉取式 | 进程级服务:只读快照 + 事件 | **零侵入**——不新增组件、不改模式;数据一律现取(`sessions()` 不可变 record),订阅生命周期事件维护"现存会话"视图 | `GlobalBoard`(§12.2) |
| ② 伴随插件 | 独立插件,框架零改动 | 只消费 `MiniGameApi` 公共面——★v1.1 起拥有**完整权限面**(查询+控制+成员+事件+会话定制;★v1.7:原「能力」项随标签机制退场,25 号;§7.5;`depend: [HydroKarbs]` + API_VERSION 检查 + 禁 shade,§13.4) | §7.5/§13.10 |
| ③ 防腐包装式 | L1 适配器 + Port + 包装组件 | 组件消费基础设施的既有先例(RoleComponent 之于 RoleFacade,§6.1;SHDF 扩展线例,见 Shdf具体玩法设计案/08-角色桥接.md、09-角色组件层.md);不改挂载级、不加 svc 成员 | 角色桥接(§9 → Shdf具体玩法设计案/08-角色桥接.md) |

### 13.10 跨 jar 消费三例(★v1.1:框架独立插件化后的典型消费方)

v1.1 起框架是独立插件、消费方是玩法/伴随插件(`depend: [HydroKarbs]`,compileOnly + API_VERSION 检查 + 禁 shade,§7.2/§13.4;完整权限面见 §7.5)。三个典型用例(共同骨架:`onEnable` 首行查版本、句柄只存实例字段、`onDisable` 显式回收,14.36/14.38):

**例一:入口牌子插件(成员操作 + 事件订阅)**

hub 世界的牌子/NPC 点击 → `leaveSession`(hub 出局,幂等)+ `joinSession`(arena 入局,含 `JoinAdmission` 裁决;`Rejected` 就地提示)——与 `/sm` 命令同权的编排权(D2,★42);同时 `subscribeSessionEvents` 听 `Dissolved`/`ModeSwitchCompleted` 刷新牌子状态(D3,★43)。代码骨架见 §7.5 示例一。

**例二:跨服/全局看板插件(事件订阅 + 只读快照)**

零侵入形态(§13.9 案①的同款接缝,宿主换成伴随插件):`subscribeSessionEvents` 维护"现存会话"视图,渲染数据一律现取自 `sessions()` 不可变快照——**不持活实例/活组件引用跨切换**(14.31 同款禁令);实例事件不暴露(19-§7-Q5),看板粒度止于会话级。

**例三:赛程器 / 第二宿主(会话定制,D14)**

- **单次定制**:`api.createSession(new SessionRecipe("their_arena", Optional.of(mapId), mapPool, List.of(new MyGraceComponent.Spec(...))))`——特殊竞技场按需带额外会话组件;无钉图/空池传 `Optional.empty()`/`List.of()`,或便捷工厂 `SessionRecipe.of(modeId, mapId)`(钉图 + 空池 + 零贡献);查重/缺依赖 → `createSession` 响亮失败(装配期失败代价低);随 dissolve 全灭(★52;**★v1.4:两参 `createSession(String, String)` 重载已删,`SessionRecipe` 是公共面建会话唯一形态**,22 号)。
- **宿主级默认策略**(**★v1.6/24 号:全局贡献改显式注册**):`api.registerSessionComponents(this, specs)`——干跑合并校验失败**响亮上抛**给调用方(可捕获;原 `SessionComponentProvider` SPI 经 ServicesManager 注册、坏 provider 拒收录会话照常的口径随通道退场为历史口径);通过后所有新会话合并其贡献(★51);插件 disable 后(显式反注册或框架兜底)新会话不再合并(已装配会话不受影响)。
- 边界:**模式仍无权贡献会话组件**(v4-D4 不变)、无运行期增删;贡献组件运行期异常只隔离自身、会话不解散(★53,★30 扩展)。

> 三例共同的回退口径:消费方插件 disable → 框架经 `PluginDisableEvent` 摘除其注册物(**兜底四族:能力标签/模式/地图/会话组件贡献**;★v1.6/24 号;**★v1.7:能力标签族随标签机制退场移除——兜底三族:模式/地图/会话组件贡献**,25 号),受影响会话走既有回退编排(模式摘除 = fallback force 切换或 FALLBACK_DISSOLVE,§3.2 二级;D8,★47)——消费方无需自建善后逻辑,但句柄仍应在 `onDisable` 显式回收(防御性,14.38)。

### 3.2 `switchMode`:框架的一等方法(两阶段算法)

```java
package com.hydrokarbs.engine.session;

public interface SessionService {
    Session create(SessionSpec spec);
    Optional<Session> sessionOf(UUID player);          // 玩家 → 所属会话
    Optional<Session> session(SessionId id);
    Collection<Session> all();

    /** ★ 框架提供的「切换模式」方法。主线程发起;准备阶段可异步,执行阶段主线程单 tick 原子。 */
    CompletableFuture<SwitchResult> switchMode(SessionId id, MatchModeSelection target, Handoff payload);

    JoinResult join(SessionId id, UUID player);        // 名册登记 + 实例入场裁决(经 JoinAdmission 端口,§3.2.1)
    void leave(UUID player, LeaveReason reason);
    void dissolve(SessionId id, DissolveReason reason);
}
```

#### 3.2.1 `join`:入场裁决经组件端口(★v3.2:JoinPolicy 从 meta 下放为组件)

v2/v3 把入场策略放在 `MatchModeMeta.joinPolicy`(OPEN/SPECTATE/CLOSED 枚举)。v3.2 拆掉它,理由与"引擎三迁"同源:**入场路由是行为**(可能依赖阶段、人数、队伍状态,且未来会越来越细),meta 静态枚举把它写死成了三个名字——这正是 §14.12 警惕的"把行为编码进数据枚举"。机制与端口:

```java
package com.hydrokarbs.engine.port;

/**
 * 实例入场裁决端口(★v3.2)。L3 组件可实现本接口;SessionService#join 经当前实例
 * 按组件声明序查询第一个实现者。引擎只认识「裁决」这个机制结果(ADMIT/REJECT
 * 是结构词汇:对应收为参赛/拒绝),不认识任何具体入场策略。
 */
public interface JoinAdmission {
    JoinDecision admit(UUID player, JoinContext ctx);   // ctx:触发点(INITIAL_PLACEMENT / MID_JOIN)与会话只读视图
}

public record JoinDecision(Kind kind, String reason) {
    public enum Kind { ADMIT, REJECT }
}
```

```java
package com.hydrokarbs.engine.session;

/** 裁决结果(与 SwitchResult 同住 session 层):一种结果格式贯穿;拒绝原因走 reason/detail,不是可编程契约。 */
public sealed interface JoinResult {
    record Joined(SessionId session) implements JoinResult {}
    record Rejected(String reason, String detail) implements JoinResult {}
}
```

裁决在两个触发点被消费,同一端口、同一组件:

| 触发点 | 时机 | 无实现者时(默认) |
|---|---|---|
| ① 初始摆放 | 切换阶段 B4 名册原地位移,成员成为 Participant 之前逐人询问 | 全员 ADMIT |
| ② 运行中加入 | `SessionService#join` 在名册登记后、并入当前实例前询问 | ADMIT |

规则:**REJECT 时会话不收**(join 返回 `Rejected`,名册不登记);ADMIT 登记名册并成为参赛者;观战安置非引擎词汇,归组件层。无实例、`ENDING`/`SWITCHING` 期间的 join:名册照常登记,入场裁决推迟到新实例 B4 的触发点①。**不挂任何实现 = 大厅等模式零配置即全接纳**——"不介入"的表达是不声明,与"不挂组件即不介入"的组件挂载口径同一。L3 侧的标准实现是 `JoinControlComponent`(§6.1-#24:按阶段门控的 ADMIT/REJECT 数据声明)。

> ★v4:**会话侧容量/入场裁决列为候选**(未决——候选清单见 §2.8-决断一 v4 修订版,仲裁入口见变更指示 §11);**第一版不变**:入场裁决仍由当前实例的实例级组件承担(上方 `JoinAdmission`/`JoinControlComponent`),会话层不做容量裁决。

`MatchModeSelection` 与 `SwitchResult`(错误语义统一,学 api-and-interface-design 的一条纪律:一种结果格式贯穿):

```java
/** 目标选择。mapId 为空 → 按 mode 支持的 tag 经 MapSelectionStrategy(RANDOM/ROTATION)挑。 */
public record MatchModeSelection(String modeId, Optional<String> mapId, boolean force) {
    public static MatchModeSelection of(String modeId) { return new MatchModeSelection(modeId, Optional.empty(), false); }
}

public sealed interface SwitchResult {
    record Succeeded(SessionId session, String fromMode, String toMode, EndResult cause) implements SwitchResult {}
    record Rejected(Reason code, String detail) implements SwitchResult {}
    /** ★v3.1:拒绝码收缩为 3 个——只保留"调用方要据此做决定"的语义,诊断信息一律走 detail。
     *  v3 的 11 个码(CAPABILITY_MISSING/MAP_*/TOO_*_PARTICIPANTS/MIN_DWELL_NOT_MET/
     *  COMPONENT_RESOLUTION_FAILED/WORLD_PREPARE_FAILED/FALLBACK_FAILED)全部并入
     *  REJECTED_BY_TARGET_MODE:它们枚举的是"目标模式的声明为什么拒绝",那是声明侧检查管线
     *  的内部词汇,不是切换契约的公共词汇——码表越富,调用方越被诱惑去 switch 细目,
     *  而细目恰恰是框架不认识的"内容"。 */
    enum Reason {
        /** 要的模式 id 不在注册表(调用方写错了 id)。 */
        MODE_NOT_FOUND,
        /** 会话正处于切换中,重入被拒(时序冲突,稍后重试)。 */
        SWITCH_IN_PROGRESS,
        /** 其余一切拒绝:目标侧(能力标签〔★v1.7 历史口径:该来源随标签机制退场,25 号——
         *  目标侧校验余人数窗/依赖校验/checkMap 地图适配/世界副本准备〕/人数窗/依赖校验/checkMap 地图适配/世界副本准备)
         *  或切换防护(min-dwell)不满足。detail 携带人读原因清单,只进日志与提示,不是可编程契约。 */
        REJECTED_BY_TARGET_MODE
    }
}
```

#### 触发 switchMode 的三个入口(优先级从高到低)

1. **外部调用**:管理命令 `/sm switch <mode> [map] [force]`、第三方插件经 `MiniGameApi`、BungeeCord 消息——直接调 `switchMode`,可带 `force`。
2. **EndGate 显式意图**:`EndGateComponent` 求值命中 → `svc().self().end(new EndResult(intent))`(判定器产出的 `GateVerdict` 自带去向;大厅倒计时到点 → 票选的模式)。由 EngineTicker 在结束后的下一 tick 代为调用。
3. **无显式去向回落回退(★v1.13/31 号)**:`EndResult` 无意图时,**一律回落 `session.fallback-mode` 配置的回退模式**(默认 = 出厂空模式 `limbo`,经 SPI 注册兜底;引擎不认识任何具体 id,见 §3.2 回退表)。驱动层三步(§3.5 回退节流):回退配置空串 → 直呼 `fallbackSwitch`(SEVERE + 即时解散);驻留不足 → 结束请求回填下一拍重试;驻留已满 → force 切回退。**(★v1.11 前历史口径:本入口曾读 `mode.meta().defaultTransition()` 的 FALLBACK/STAY/ROTATION 三值枚举——缺省去向管线已随 v1.13 整体退场,`MatchModeMeta` 收敛为三分量,31 号/ADR-0019)**

> 三个入口殊途同归——都汇到 `SessionService#switchMode` 一个方法。**引擎里不存在第二种切换路径**,这是"切换语义只有一份"的机械保证。

### 3.3 `Handoff`:模式间的类型化交接袋

与 `Handoff` 自身的键值模式一致(命名空间 + 名字 + 类型;★ADR-0016:属性袋退场后本条不再引 `AttributeBag` 作类比),杜绝"用 Map<String,Object> 传交接数据、接收端强转炸裂"的写法:

```java
package com.hydrokarbs.engine.session;

/** 模式间交接载荷。★v3.1:命名空间 = 写入方自己的 id(模式 id / 组件 id / 第三方插件 id);
 * 框架不写任何键、不保留任何命名空间——v3 的 HandoffKeys 与 "framework" 保留段已删除(§0.5.3)。 */
public final class Handoff {
    public record Key<T>(String namespace, String name, Class<T> type) {
        public static <T> Key<T> of(String ns, String name, Class<T> t) { ... }
    }
    public <T> void put(Key<T> key, T value);
    public <T> Optional<T> get(Key<T> key);
    public static Handoff empty();
    /** 合并:external 的同名键覆盖 outgoing(外部指令优先于旧实例自报)。 */
    public static Handoff merge(Handoff outgoing, Handoff external);
}
```

> **★v3.1:交接键随主人,框架不设保留键。** v3 的 `HandoffKeys`(VOTE_RESULT / LAST_SUMMARY / RETURN_REASON)把投票结果、战报、离开原因这些**玩法语义**定义成引擎的类型化常量——违反「框架不认识内容」。现在的归属:
>
> | 键 | 主人(公开常量) | 说明 |
> |---|---|---|
> | 投票结果 | `VoteComponent.HANDOFF_RESULT`(namespace `"vote"`;选模式用例见 Shdf具体玩法设计案/04-大厅模式.md §4.5) | 谁生产谁持有;大厅选模式与局末选图共用 |
> | 上局战报 | `StatsComponent.LAST_SUMMARY`(namespace `"stats"`,§6.1-#13) | 产出者 StatsComponent,消费者大厅 Display;"为何离开"(ABORTED/ADMIN 等)随 MatchSummary 携带,不再单设 RETURN_REASON |
> | 其他 | 各模式/组件在自己命名空间下自定义 | 跨组件引用交接键常量是合法协作——Handoff 本就是跨模式通道,命名空间只标识写入方来源,不构成写入归属限制(★ADR-0016:原「与 AttributeBag 的不得写他人命名空间是两回事」的类比随属性袋退场改写,§14.20) |

**典型交接流(一整个循环;模式/地图 id 均为占位示意)**:

```
modeA(等待/票选类模式)倒计时结束
  → ModeACountdownEndCondition 产出 GateVerdict(MatchOutcome(NEXT), intent={target=票选的 modeB@mapB,
                                                payload=VoteComponent.HANDOFF_RESULT})
  → switchMode(modeB, mapB, payload)
  → modeB 的开局阶段读 svc().self().handoff().get(VoteComponent.HANDOFF_RESULT) 播报"本场模式由投票选出"
  → 一局打完,EndGateComponent 产出 MatchOutcome(WIN, winnerId, 无 intent)→ svc().self().end(EndResult.nowhere())
  → 无显式去向 → 回落 session.fallback-mode(★v1.13:单通道,驻留节流见 §3.5)
  → switchMode(modeA, modeAMap, payload={StatsComponent.LAST_SUMMARY=上局摘要(内含结局与原因)})
  → modeA 结算展示统计摘要,然后开下一轮投票
```

### 3.4 结束与转移:EndGate 组件 → EndResult → 下一站

```java
package com.hydrokarbs.engine.session;

/**
 * ★v3.1:框架的结束货币只有「去向」,没有「剧情」。v3 的 kind 枚举(WIN/DRAW/NEXT/ABORTED)、
 * 胜队、reason 都是玩法语义——引擎不该枚举"游戏有哪些结局"(跑酷/极简大厅没有 WIN/DRAW)。
 * 结局词汇 MatchOutcome 归内容层(component/endgate,下);引擎只执行 TransitionIntent。
 */
public record EndResult(Optional<TransitionIntent> transition) {
    /** 无显式去向(★v1.13:一律回落 session.fallback-mode 单通道——引擎自兜底结束如
     *  quarantine 也走同一路径;原 meta.defaultTransition 管线已退场,31 号)。 */
    public static EndResult nowhere() { return new EndResult(Optional.empty()); }
}

public record TransitionIntent(MatchModeSelection target, Handoff payload) {}
```

```java
package com.hydrokarbs.component.endgate;

/**
 * ★v3:结束判定从引擎降级为组件。它持有 EndCondition 列表(纯函数数据),
 * update() 里按 priority 降序求值,命中即 svc().self().end(...) —— 主动声明,不被轮询。
 * 引擎不认识 EndCondition;不想要结束判定的模式(极简测试模式)就不挂这个组件。
 * ★v3.1:玩法结局的词汇(WIN/DRAW/NEXT/ABORTED、胜者、reason)也住在这里——内容归内容层。
 */
public record MatchOutcome(Kind kind, @Nullable String winnerId, String reason) {
    /** 玩法结局词汇(内容层共享词汇,引擎零认知)。 */
    public enum Kind { WIN, DRAW, NEXT, ABORTED }
}

/** 判定器的产物:结局(内容)+ 可选去向(框架货币)。 */
public record GateVerdict(MatchOutcome outcome, Optional<TransitionIntent> intent) {}

/** 纯函数判定器(数据,不是组件):给定实例视图,返回判定。可离线单测。 */
public interface EndCondition {
    int priority();
    Optional<GateVerdict> evaluate(MatchModeInstanceView ctx);
}

public final class EndGateComponent extends MatchModeComponent {

    public static final class Spec extends MatchModeComponent.Specification<EndGateComponent> {
        public Spec(List<EndCondition> conditions) { ... }   // priority 在 EndCondition 上
        @Override public EndGateComponent create(String id, MatchModeInstanceServices svc) { ... }
    }

    private MatchOutcome lastOutcome;   // 状态唯一:命中后保存,供统计/战报读取

    @Override public void update() {
        conditions.stream()
                .sorted(Comparator.comparingInt(EndCondition::priority).reversed())
                .map(c -> c.evaluate(view()))
                .flatMap(Optional::stream)
                .findFirst()
                .ifPresent(v -> {
                    lastOutcome = v.outcome();                       // 结局留在内容层
                    svc().self().end(new EndResult(v.intent()));     // 只有去向交给引擎
                });
    }

    /** 强类型读口:StatsComponent/Display 从这里取结局(引擎不知道它存在)。 */
    public Optional<MatchOutcome> outcome() { return Optional.ofNullable(lastOutcome); }

    @Override public void onHandoff(Handoff.Builder out) { /* 可选:把结局写进自己命名空间,供下一实例展示 */ }
}
```

**谁决定下一站——三层优先级,每一层都可独立测试(★v1.13/31 号:第③层自「模式缺省数据」改为「无显式去向回落回退」):**

| 层 | 产出者 | 例子 | 测试方式 |
|---|---|---|---|
| ① 显式意图 | `EndCondition`(EndGate 持有的判定器自己带,经 `GateVerdict.intent`) | 大厅倒计时 → 票选结果;跑酷"全员到终点" → 下一图 | 给定实例状态,断言 `evaluate()` 产出的 GateVerdict(intent + MatchOutcome) |
| ② 外部指令 | 管理命令 / `MiniGameApi` 调用方 | `/sm switch <modeId>` 强切 | 直接调 `switchMode` 断言结果 |
| ③ 无显式去向 | 引擎回落(§3.2 回退表/触发入口③) | 竞技模式打完无意图 → 驻留已满后 force 切 `session.fallback-mode`(默认 = 出厂空模式 limbo;驻留窗内结束请求回填重试,§3.5) | `NeutralDefaultsSemanticsTest`/`SwitchStormGuardTest`(回退落位与节流,★68) |

引擎对"下一站"本身**零理解**——它只执行 `MatchModeSelection`。投票、轮换、管理员指定,全部是产出 `MatchModeSelection` 的不同上游,引擎不区分。v2 的 `TransitionPolicy` 策略对象已删除,其遗骨——v3~v1.12 的 `MatchModeMeta.defaultTransition` 三值枚举(FALLBACK/STAY/ROTATION)——**已随 v1.13 缺省去向管线整体退场删除**(STAY/ROTATION 从未被引擎真实消费;无显式去向的缺省去向只有一条 = 回退,31 号/ADR-0019;`MatchModeMeta` 现形状见 §2.3)。

### 3.5 切换防护(四类事故的机械闸门)

| 事故场景 | 防护机制 |
|---|---|
| **切换风暴**:新模式的 EndCondition 立即又命中(如入场门槛极低、结束条件瞬时满足),一秒切几百次 | `min-dwell-ticks`(会话属性,默认 100):驻留不足时,来源①③的自动切换被拒并 `WARN`;来源②(外部 force)可豁免。返回 `REJECTED_BY_TARGET_MODE`,detail 注明"驻留不足,剩 N tick"(★v3.1:防护是框架内部节律,不占独立码)。**★v1.13/31 号:节流范围扩至回退链**——无显式去向的回退虽带 force(豁免人数下限),驱动层仍先经 `dwellRemaining`(与防护①共用同一公式)预检:驻留不足 → 结束请求回填下一拍重试,驻留已满才 force 切回退——「结束→切回退→再结束」风暴每窗口至多一轮(防回退环风暴是机制保证,不靠回退模式零组件的配置巧合;回退配置为空串的先行即散不经驻留,见 §3.2 触发入口③) |
| **重入**:某条 Rule / `onHandoff` / 组件回调里又调 `switchMode`(直接或间接) | ① 状态机 `SWITCHING` 期间一切切换请求 → `Rejected(SWITCH_IN_PROGRESS)`;② 纪律:自动切换只能由 EngineTicker 在 `ENDING` 后的下一 tick 发起(测试冻结:断言 `switchMode` 的自动调用栈必经 ticker) |
| **准备期人数漂移**:阶段 A 校验过了,B 执行时人走了 | 阶段 B 前置重校验 A4;不满足且非 force → 中止,旧实例未动 |
| **世界准备失败/超时** | 阶段 A 整体失败,旧实例未动,成员无感知;`WorldPort` 内部有准备超时(默认 30s) |
| **会话组件引发的切换**:会话级组件经 `requestSwitch()` 请求换模式(§3.8) | 与 `switchMode` 同一实现,按来源②口径计入 `min-dwell`——驻留不足即 `REJECTED_BY_TARGET_MODE`(detail 注明"驻留不足,剩 N tick");请求口不带 `force`,即无豁免路径;`SWITCHING` 期间同样受重入拒绝(★v4) |

### 3.6 部署拓扑:rotation / arena / hub(引擎零感知)

```
rotation(默认,单会话轮换):
  启动 → 建唯一常驻 Session(初始 lobby,永不空场解散)
  全员进它;lobby ⇄ 玩法 循环。适合:小服、固定人群、想开即玩。
```

### 3.7 `WorldPort`:世界生命周期(补上 v1 的空白)

v1 假设地图世界"已经在那"。通用框架必须回答:同图并发怎么办、打完怎么还原、谁负责卸载。

```java
package com.hydrokarbs.engine.port;

public interface WorldPort {
    /** 为地图获取就绪世界。同一 map 在不同会话得到独立副本(目录名 = mapId + "-" + sessionId 短码)。
     *  模板复制 = 文件 IO(虚拟线程);Bukkit 加载世界 = 主线程。 */
    CompletableFuture<WorldHandle> acquire(MapDefinition map, SessionId forSession);
    /** 引用计数归零 → 按句柄的 ResetStrategy 处置副本。幂等,重复 release 无害。
     *  (★v1.5:REUSE_DIRTY 在会话存活期归零仍保留副本目录——切换换图的复用语义原样) */
    CompletableFuture<Void> release(WorldHandle handle);
    /** ★v1.5 新增:会话解散时销毁该会话名下全部世界副本(复用窗口 = 会话生命周期,
     *  ★v1.5-D1)。三类全覆盖:①计数表该会话的存活条目:卸载不存档 + 删目录,
     *  策略无关(会话已死,复用收益失效);②曾切换离开而保留在磁盘的副本目录
     *  (按「会话曾发放 mapId 集」精确名删除);③迟到的 in-flight 获取
     *  (其后的归零处置见「已死短码集」判据,无论策略一律删)。幂等,重复调用无害。 */
    CompletableFuture<Void> discardSession(SessionId session);
}

public record WorldHandle(World world, String instanceName, MapDefinition map, ResetStrategy reset) {}
public enum ResetStrategy {
    /** 打完不重建,靠 CleanupComponent 把方块/实体还原(快,适合回合制连续开局;
     *  ★v1.5:复用只在会话存活期成立——存活期归零保留目录,解散后名下副本随 discardSession 全部销毁) */
    REUSE_DIRTY,
    /** 切走时删除副本,下次 acquire 从模板重新复制(慢但绝对干净,适合破坏性玩法;★v1.5 行为原样) */
    TEMPLATE_RESTORE
}
```

规则表:

| 规则 | 内容 |
|---|---|
| 谁调用 | **只有 SessionService**(acquire 在切换阶段 A6;释放 = 切换完成时 release + 解散时 discardSession)。模式/组件只消费 `ctx.map().world()`,不知道世界从哪来 |
| 引用计数 | 同一 (map, session) 重复 acquire 幂等返回同句柄;切换到同图同策略时复用(回合制连打同图零复制成本) |
| 释放时机 | 换图切换完成之后(新世界已就绪)释放旧句柄;dissolve 的 finally 里兜底释放(★v1.5:解散路径改经 `discardSession`,名下副本一并销毁——见下行)。**泄漏由 `WorldRefCountTest` 冻结**(切换 100 次后断言无未释放句柄)。**★v1.9(27 号)切换清场时序注**:清场经会话内核注入函数 `worldClearer`(`Builder` 两法之一,`WorldPort` 接口零改动)——同世界复用走 B3.5、先行于 B4;异图走 B5 finally 殿后,时序 = **完成事件(`ModeSwitchCompleted`/`future.complete`)之后、release 之前**(事件订阅者可见同 tick 内事件派发时遗留人员尚未清);清场/释放均前置(dissolve 则先清场后 `discardSession`),release/`discardSession` 原时机不变 |
| 副本销毁(★v1.5) | 会话解散经 `WorldPort#discardSession(session)` 销毁该会话名下全部副本,三类全覆盖:①计数表该会话的存活条目——卸载不存档 + 删目录,策略无关(会话已死,复用收益失效);②曾切换离开而保留在磁盘的副本目录——端口记「会话曾发放 mapId 集」,解散时按目录名(`<mapId>-<短码>`)精确删除;③迟到的 in-flight 获取——解散把会话短码记入「已死短码集」,其后的归零处置无论策略一律删。删除仍唯一走 `deleteCopyDir` 入口 + 路径形态断言;卸载/删除失败 best-effort 保留 + WARN/SEVERE。**复用窗口 = 会话生命周期,窗口关闭即回收**(★v1.5-D1,23 号);切换路径对 REUSE_DIRTY 保留目录的复用语义与 TEMPLATE_RESTORE 归零删副本均原样(**验收 = ★58**;`WorldPort` 为 engine 内部口,不进 `MiniGameApi` 冻结面,★49/★44 口径不变) |
| 模板 | ~~`maps/templates/<mapId>/`(世界目录副本),随地图包分发~~(**★v1.8(26 号)按新基准改写**:模板根约定退场——复制源 = **声明自带 `worldDirectoryPath`**(构造期规范化绝对路径,可指任意位置;注册前路径已就位,14.39),副本目录名 = 路径派生 id + "-" + 会话短码;~~`MapDefinition` 的 `reset-strategy` 字段声明策略~~——resetStrategy 分量随瘦身删除,策略读声明约定键 `map.reset-strategy`(缺省 REUSE_DIRTY;★ADR-0016/0017:约定键与门面退场,策略回到声明字段 `resetStrategy`——三字段之一,二参构造缺省 REUSE_DIRTY;第三分量为 `AttributeBag` 纯容器);策略的**消费**仍在本端口归零处置,管线零改动) |
| v1 遗留 | v1 `config.yml` 的 `world-unload-on-close` 并入 `ResetStrategy`,配置项删除 |

> ★v4 未决(变更指示 §11-Q5):世界预取/释放调度是否可插拔——本版不变:`WorldPort` 的 acquire/release 调用点仍只在内核(D7:"WorldPort 调用时点与引用计数"仍属切换/解散算法的一部分),调度不组件化;问题登记于此,待裁决。

### 3.8 会话级组件层(★v4:两级挂载的会话侧)

v4 把组件的挂载级从**一级扩为两级**:实例级 `MatchModeComponent`(随实例 `close()` 全灭,§2.4)与**会话级 `SessionComponent`**(随会话 `create` → `dissolve`,**每会话一份**、跨模式切换存活,§2.5.1)。会话的*策略与行为*(第一波:空场解散)从此可插拔——判据是 §2.8-决断一 v4 修订版的两问(机制还是策略);完整决策见 ADR-0004(D1~D11),类型契约与包结构见 §12.2。

**装配(唯一装配点:`SessionService.create` 内,先于首个实例)**

```
create(spec):
  建 Session 骨架 → SessionComponentRegistry.bind(逐 Spec freeze 快照,id 去重)
  → verifyDependencies()        // 缺会话级必需依赖 → 抛,会话创建失败(L0 SEVERE)
  → 按声明序 create(id, svc) → awakeAll() → startAll()
  → 发 SessionCreated → 走首次 switchMode(初始模式)
  (会话组件先于首个实例就绪——首实例的组件才能查到它们)

dissolve:
  DISSOLVING →(若有实例)close() → 会话组件逆序 stop + reclaimRegisteredResources()
  → 成员传送回主城出生点 → 释放世界句柄 + 销毁名下副本(discardSession,★v1.5-D1)
  → 从注册表摘除 → 发 SessionDissolved
```

> ★v1.9(27 号)dissolve 流程加注:成员传送(名册,`hubRelocator`)之后、销毁名下副本(`discardSession`)**之前**,finally 内存在**世界清场口**——`heldWorld` 非 null 时经 `hubWorldClearer` 把地图世界内遗留人员(`getPlayers()`,不以名册为界)传往主世界出生点(与 `hubRelocator` 共用 `hubSpawn()` 单一来源),「先名册后世界」、每人至多一次;清场失败 WARN 不阻塞,`discardSession` 照发(世界已空 → 卸载如期,「卸载失败保留目录」防线仍为最后兜底);`heldWorld` 为 null(如初始切换失败即解散)跳过、无害。

- 装配来源:会话级组件表由 `SessionSpec` 携带(`List<SessionComponent.Specification<?>>`,有序 = 装配序 = 派发序),由 **L0 装配期按配置构建**(例:rotation 不挂空场组件;arena 挂 `EmptyArenaComponent`,§6.4);**模式无权注册/增删会话级组件**(第一版)。(**★v1.3-D5 修订:L0 构建者废止**——`SessionSpec` 由宿主构造并传入 `create`,会话组件表由**宿主组装**(挂不挂空场组件、`after` 给多少都是宿主声明);「装配来源唯一、模式无权」的纪律不变,来源主体自框架 L0 移宿主,21-D5)
- `svc`(`SessionServices`,两成员封闭)构造期注入,四条件照抄实例级:注入先于一切钩子 / `final` 只注一次 / 未注入即抛 / 创建点唯一。
- 容器:`SessionComponentRegistry`(会话版 `ComponentRegistry`)——装配期依赖校验 + 声明序派发 + 登记资源回收 + 故障隔离。

**生命周期五钩子(与实例级同名对齐,语义按会话重定义)**

| 钩子 | 时机 | 语义 |
|---|---|---|
| `awake()` | 会话装配期,`create` 之后 | 只解析**会话级**依赖并缓存引用;幂等;无可见副作用 |
| `start()` | 会话创建完成、**首个实例装配之前** | 生效:订阅会话/实例事件、登记显示、初始化会话级数据 |
| `update()` | 每 tick,**与"当前是否有实例"无关** | 会话策略推进(空场计时等)。禁止阻塞、禁止 IO |
| `onEvent(SessionEvent)` | 会话事件中央总线广播 | 与订阅二选一皆可;订阅随 `stop` 自动回收 |
| `stop()` | dissolve(或隔离)时 | 与 `start` 严格对称;返回后框架自动回收本组件登记的资源(订阅/延时任务/显示) |

派发规则与实例级一致:**按声明序**广播、`stop` **逆序**;`stop` 由框架**无条件**调用(无单例豁免条款——这正是"组件"与"内核机制"的分界,§2.8-决断一)。

> ★v4 待裁决(落盘期登记,变更指示 §2-D2 与 §3 骨架的差异):上表 `start()` 行的"**订阅实例事件**"在本版契约骨架中**无接口落点**——会话侧订阅面只有 `SessionPort.events()`(仅覆盖会话事件,§12.2),`MatchModeInstanceAccess`/`SessionView` 均无 `events()`。本版按骨架现状落盘(无实例事件订阅面);"删该半句或补订阅面"提请上游裁决,未静默决定。同登记见 ADR-0004 D2 落盘注、施工计划 2.6。

**每会话一份**

会话级组件在**会话生命周期内**是单例:同一会话内 `Specification#create` 至多调用一次,此后一切查询(实例组件、会话组件互查、会话内核)恒返回同一实例;**跨会话不共享**(arena 拓扑下 N 个会话各一份)。机械保证:注册表挂在 `Session` 上,**不是进程级静态**;`SessionComponentSingletonTest` 冻结(★27)。共享的只能是不可变声明(Spec/Snapshot),有状态实例永不跨会话共享。

**派发节拍(`EngineTicker.tickAll`,每 tick、每会话;★顺序是规格的一部分)**

```
① 会话事务:runPendingSwitch()             // 机制,不变
② 当前实例 tick:instance.tick()            // 若有实例;派发实例组件 update,不变
③ 会话组件派发:tickSessionComponents()     // ★每 tick 必调,与实例有无无关;逐组件 try/catch → D9 隔离
④ 内核 sweep:断线宽限等                    // 机制,不变
```

③ 步在切换间隙照常执行——**实例侧组件不 tick,会话组件照常 tick**(时序见 §11)。会话组件表**不参与模式切换**,切换前后其实例恒等(§3.2-阶段 B 注,★33)。

**故障隔离(会话级 quarantine,D9)**

`update`/`onEvent` 抛异常 → 记日志(会话 id / 组件 id / 原因)→ 对该组件 `safeStop` + 打标 quarantined(此后跳过其派发)→ 发会话事件 `SessionComponentQuarantined` → **会话不解散**,其余组件照常。与实例级的差异:**实例级**隔离 → `end()` → 回退模式(模式坏了有兜底);**会话级**没有回退目标、解散代价过大——停用单个策略组件是可接受的降级(空场策略停用 = 行为退回"永不解散"并留日志)。装配期 `awake/start` 抛 → 会话创建失败(L0 SEVERE;arena 则该竞技场不启动)。

**请求端口(跨级干预只走端口,D8)**

```java
void requestSwitch(MatchModeSelection target, Handoff payload);   // 与 switchMode 同一实现;受 min-dwell 与重入约束(§3.5)
void requestDissolve(DissolveReason reason);                      // 幂等;空场策略组件的动作落点
```

两个行动口镜像实例级的 `switchTo()`/`end()`:`requestSwitch` 与 `switchMode` **同一实现**(受 `min-dwell` 与重入约束,§3.5);`requestDissolve` **幂等**。**不新增其他影响力端口**。

**跨级查询(互相只读,写只走端口;D5)**

| 方向 | 通道 | 授权 |
|---|---|---|
| 实例组件 → 会话组件 | `svc().self().session()`(`MatchModeInstancePort` 新增方法)→ `SessionView#component(Class<T extends SessionComponent>)` | **只读**;不得订阅会话事件(第一版) |
| 会话组件 → 实例组件 | `svc().self().currentInstance()` → `Optional<MatchModeInstanceAccess>`;`MatchModeInstanceAccess#component(Class<T extends MatchModeComponent>)` | **只读**;无实例或 `ENDING/SWITCHING` 间隙 → `empty`;**现取不缓存**,不得越过切换缓存实例组件引用 |
| 会话组件 → 实例干预 | 只有 `requestSwitch()` / `requestDissolve()` + 事件 | 等价于实例级 `end()`/`switchTo()` 的口径 |
| 实例组件 → 会话干预 | 只有原有 `end()` / `switchTo()`;会话级干预**不提供**(模式无权解散会话,第一版) | — |

类型 token 一律是**接口**;跨级写回不存在——"只读"是架构纪律 + review 条款(§14.29)。五个类型(`SessionComponent` / `SessionServices` / `SessionPort` / `MatchModeInstanceAccess` / `SessionView`)的完整签名见 §12.2;`SessionComponentRegistry`(会话版 `ComponentRegistry`)的职责见 §12.1,装配/回收接线见 §12.2 的接线伪码(§12.2 未设它的独立签名块)。★v4 类型总账待裁决:本行按指示 §1 口径(含 `SessionComponent`);§6.1-01/§6.2-12 的 `engine/port` 五类型另含 `SessionComponentLookupPort`,§3 骨架另有 `SessionEventPort`——差异登记见 00 §0.5.5 注。

### 3.9 进程级服务层(★v4.1:与组件并列的另一类对象)

v4.1 新增第三类对象:**进程级服务(Service)**——进程生命周期(`onEnable` 装配 → `onDisable` 关停),不随任何 Session/Instance 生灭;不挂进会话/实例、不进组件表(A10 不破:服务不是第三级*组件*),彼此经 `ServiceRegistry` 两阶段装配(`install` 声明 → `seal` 校验 + 拓扑序创建 + 启动)。**组件体系与服务互不可见**:组件/模式不得 import 服务,服务不得 import `mode/**` 与 `component/**`;`MatchModeInstanceServices` 三成员 / `SessionServices` 两成员**不加成员**(服务不经 svc 注入组件)。完整决策见 18-v4.1 修正案(D1~D12)与 ADR-0006(`docs/adr/0006-process-service-registry.md`;修正案原文编号 0005,因冲突顺延为 0006),契约骨架见 §12.2(v4.1 增补)。

**服务 ↔ 会话:三条通道,无第四条**

| 通道 | 方向 | 授权 |
|---|---|---|
| **订阅 `SessionEventBus`**(`SessionCreated / MemberJoined/Left / ModeSwitchStarted / ModeSwitchCompleted / SessionDissolved / SessionComponentQuarantined`) | 会话 → 服务 | 感知生灭的官方通道(§3.1 事件行既有定位"给跨切面逻辑用"——本版兑现:服务是其第一类正式居民);订阅句柄在服务 `stop` 中注销 |
| **只读快照**(`MiniGameApi.sessions()` 不可变 record;引擎内代码可经 `SessionService` 遍历 + `MatchModeInstanceAccess`) | 会话 → 服务 | 只读;**不得持有活实例/活组件引用跨切换**(镜像 ★29 的"现取不缓存"纪律) |
| **受控命令**(`SessionService#switchMode / dissolve / createSession`) | 服务 → 会话 | 服务属**外部调用方(切换来源②)**,与 `/sm` 命令同权;`force` 是显式选择,走 review 条款;无其他影响力端口。★v1.1-D10 注:通道③受控命令清单不变——跨 jar 外部调用方(命令/监听/伴随插件/玩法插件)经 `MiniGameApi` 的成员操作(`joinSession`/`leaveSession`,19-D2)**不构成第四通道**(调用方阵营不同:那是外部执行权的扩充,不是服务通道;服务仍不得经 `MiniGameApi`,14.37) |

- **服务属切换来源②,与 `/sm` 命令同权**(§3.4 三层之"外部指令");`min-dwell` 的 `force` 豁免是显式选择,走 review 条款(§3.5:来源②可豁免,①③被拒)。
- **服务不参与切换装配**(§3.2 阶段 A/B 零改动)、**不占 `tickAll` 四步**(§3.8 派发节拍 ①~④)——服务自行经 `ServiceLifecycle#start` 订阅事件驱动。

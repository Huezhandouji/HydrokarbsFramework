## 目标

本子阶段结束时新增了:

1. `data/**` 基建四件:`Database`(HikariCP 全参数)、`AsyncExecutor`(虚拟线程+背压+超时)、`MigrationRunner`(`schema_version` + 追加式迁移)、`DatabaseState` 三态降级——全部离线可测;

4. 密钥不进版本控制(§14.11)。
5. 本子阶段**不写任何业务 SQL**(SELECT/UPSERT 归 5.4 仓储)。

## 施工步骤

### 步骤 1|依赖与打包 —— `build.gradle.kts`

- 增补 `implementation("com.zaxxer:HikariCP:5.1.0")` 与 `implementation("com.mysql:mysql-connector-j:8.4.0")`,经 shadow 打进插件 jar(§12.1 依赖块及其★注:**不 shade → 运行期 `ClassNotFoundException`**)。
- 版本基线不动:Java 21 / `io.papermc.paper:paper-api:1.21.11-R0.1-SNAPSHOT`(compileOnly)/ Gradle Kotlin DSL。

### 步骤 2|配置解析 —— `src/main/java/com/shdf/match/data/DbConfig.java`

- record:`host / port / database / username / passwordEnv / maxPoolSize / minIdle / flushIntervalSeconds / queryTimeoutSeconds`,自 `config.yml` 的 `database:` 块解析(§15.2 逐键:`enabled / host / port / database / username / password-env / max-pool-size: 10 / min-idle: 2 / flush-interval-seconds: 30 / query-timeout-seconds: 8`)。
- `enabled: false` → 整个 data 层不装配,等价永久 MEMORY_ONLY(A4)。
- 容错三铁律适用:缺键给默认值、非法值降级 WARN 不崩(§15.2)。

配置块骨架(逐键含义见 §15.2;数值即本阶段默认):

```yaml
database:
  enabled: true
  host: 127.0.0.1
  port: 3306
  database: hydrocarbs
  username: hydrocarbs
  password-env: HYDROCARBS_DB_PASSWORD   # ★ 密码不落 config(§14.11)
  max-pool-size: 10
  min-idle: 2
  flush-interval-seconds: 30       # 5.4 的 write-behind 周期读这里
  query-timeout-seconds: 8         # 5.3 的 orTimeout 读这里
```

### 步骤 3|密码方案(§14.11)

- `config.yml` 只放环境变量**名**(`password-env: HYDROCARBS_DB_PASSWORD`,§15.2);真实密码放环境变量或 `plugins/HydroKarbs/secrets.properties`(**加入 .gitignore**,§15.2 文件分工)。
- 解析顺序:环境变量 → secrets.properties;都缺 → **不建池**,直接 `DEGRADED` + 醒目 WARN(§14.11)。
- 自查:仓库内 grep 不得出现明文密码;`.gitignore` 含 `secrets.properties`。

### 步骤 4|连接池 —— `src/main/java/com/shdf/match/data/Database.java`(§10.4 代码为蓝本,逐项照抄)

| 参数 | 值 | 出处/理由(§10.4) |
|---|---|---|
| jdbcUrl 参数串 | `useSSL=false & allowPublicKeyRetrieval=true & characterEncoding=utf8 & connectionCollation=utf8mb4_unicode_ci & serverTimezone=Asia/Shanghai & useServerPrepStmts=true & cachePrepStmts=true & prepStmtCacheSize=250 & prepStmtCacheSqlLimit=2048 & rewriteBatchedStatements=true & tcpKeepAlive=true` | MySQL 8 caching_sha2 必需;**`rewriteBatchedStatements=true` 是批量 UPSERT 提速关键**;utf8mb4 三处一致之三 |
| maximumPoolSize | cfg(默认 10,8~12 区间) | 虚拟线程≠连接,池是背压阀(§14.3) |
| minimumIdle | cfg(默认 2) | 同上 |
| connectionTimeout | 5_000 | 快速失败让上层降级为内存模式 |
| validationTimeout | 2_000 | — |
| idleTimeout | 60_000 | — |
| maxLifetime | 1_500_000(25min) | 短于 MySQL `wait_timeout`,留余量 |
| keepaliveTime | 120_000 | 防中间件静默断连 |
| leakDetectionThreshold | 10_000 | 抓"借出忘 close" |
| connectionInitSql | `SET NAMES utf8mb4` | utf8mb4 三处一致之三(§10.3.4★) |
| initializationFailTimeout | **-1** | 只建池不建连,onEnable 不卡(§14.2-1) |
| poolName / registerMbeans | `HydroKarbsPool` / false | — |

- 对外仅:`dataSource()` / `isReady()` / `close()`;取连接一律经池,**禁用 DriverManager**(§10.4 要点表)。

### 步骤 5|三态降级 —— `src/main/java/com/shdf/match/data/DatabaseState.java`

- 三态 `CONNECTING / READY / DEGRADED`(§14.2-2),原子持有(volatile + 原子引用),全进程可查。
- 探针:装配完成后在 AsyncExecutor 上执行首次 `getConnection()` + `SELECT 1`——成功 → `READY`;失败 → `DEGRADED` + WARN + 退避重试(重试成功自动回 READY)。顺带记录 `SELECT VERSION()` 供 5.4 的 UPSERT 方言回退(§10.3.4 注)。
- 消费契约(5.4 兑现):`DEGRADED` 时一切写口跳过+节流 WARN、读口返回空——**对局照跑**(§14.2-3、A4);禁止因库失败 `setEnabled(false)`。

### 步骤 6|执行器 —— `src/main/java/com/shdf/match/data/AsyncExecutor.java`(§10.3.2 代码为蓝本)

- `Executors.newVirtualThreadPerTaskExecutor()` + `Semaphore` 背压(maxInflight 建议 2× 池大小)+ `orTimeout(query-timeout-seconds)`;`opName` 进失败日志。
- 进程内一切 JDBC 与文件 IO 走它;`runTaskAsynchronously` 完全弃用(§15.3 结论表);`close()` 有界关闭。

### 步骤 7|迁移 —— `src/main/java/com/shdf/match/data/MigrationRunner.java`(§10.3.6)

- 启动期(异步、虚拟线程,§14.15)执行:确保 `schema_version` 表(§10.1-0 的 DDL,由 runner 自建)→ 读已应用版本集 → 逐条应用未应用迁移。
- 迁移清单:`MIGRATIONS = List.of(new Migration(1, "初始表结构(v2 含 session_id / end_kind)", "sql/001_init.sql"))`(§10.3.6 原文)。
- 每条迁移在**独立事务**里执行(DDL + 写 `schema_version` 同事务);失败 → 整条回滚、`DEGRADED`、SEVERE 日志。
- 纪律:**追加式**——任何表变更新增 `002_xxx.sql`,永不修改已发布迁移(§14.15、§16.2-★12);迁移文件只增不改列入评审 checklist。

### 步骤 8|初始 DDL —— `src/main/resources/sql/001_init.sql`

- §10.1 **六张业务表 DDL 全文照抄**(含全部列/索引/外键/表注释):`player_profile`、`player_stats`、`player_stats_mode`、`role_stats`、`match_history`(含 `session_id` 与 `end_kind`)、`match_participant`。
- 每表 `ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci`,与库默认、连接 `SET NAMES` 构成三处一致(§10.3.4★)。
- 不含 `schema_version`(步骤 7 由 runner 建);不增删改 §10.1 的任何列。`end_kind` 取值 WIN/DRAW/ABORTED(§10.1-5 注)。

### 步骤 9|onEnable 接线(§14.2 三原则逐条落实)

| 原则 | 落点 |
|---|---|
| 1 不阻塞建池 | `initializationFailTimeout=-1`;主线程只 `new HikariDataSource`(不建连、不 `getConnection`) |
| 2 重活异步 | 探针 + 迁移提交到 AsyncExecutor;完成前 `DatabaseState=CONNECTING`,其余装配不等待 |
| 3 DEGRADED 照常 | 迁移失败/密码缺失/探针不通 → WARN 后继续启用,会话系统正常(内存模式) |

- 主类装配顺序:data 基建(Database → DatabaseState → AsyncExecutor → MigrationRunner)→ 其余照阶段1/2 既有顺序;`onDisable` 的 `database.close()` 放在 5.4 定义的完整关停序(Flusher 冲刷之后)。

## 关键实现要点

- **utf8mb4 三处一致清单**:①库 `CREATE DATABASE` 默认 utf8mb4;②每表 DDL 的 CHARSET/COLLATE(§10.1);③连接串 `characterEncoding/connectionCollation` + `connectionInitSql SET NAMES`(§10.3.4★/§10.4)。缺一处即中文乱码。
- `initializationFailTimeout=-1` 的推论:**首次 `getConnection()` 才真正建连**——任何主线程路径都不得提前取连接,探针必须异步(§14.2-1)。
- 池大小 10 的纪律:不因虚拟线程放大池(§14.3);Semaphore 背压与连接池构成双闸。
- 调试期统一加 `-Djdk.tracePinnedThreads=short`,观察 `synchronized` 钉扎虚拟线程(§10.4 末行)。
- `GlobalRegionScheduler` 与 Bukkit 调度纪律(初始 delay=1L)属引擎层(阶段1);本子阶段的重活一律走 AsyncExecutor,不走 Bukkit 异步调度(§15.3)。

## 陷阱与纪律

- **§14.2 onEnable 阻塞 IO**(建池/迁移/拉数据):watchdog 杀服的头号来源。
- **§14.3 池大小按虚拟线程数设**:MySQL `Too many connections` / 服务端 OOM。
- **§14.11 DB 密码进 config.yml 并提交版本控制**。
- **§14.15 无版本迁移 / 修改已发布迁移**:演进能力(★12)直接作废。

## 测试与验收

- `data/MigrationRunnerTest`(Testcontainers MySQL 8 或本地 MySQL):空库 → 六表 + `schema_version` 就位;断言 `schema_version` 恰有一行 version=1;重复运行幂等(不重复执行、不重复建表);人为改坏 001 → 状态 DEGRADED 且不写版本、服务照常启用。
- `data/DatabaseStateTest`(假 DataSource):失败 → DEGRADED;恢复 → READY;密码缺失 → DEGRADED 且不抛;三态对外只读(消费方不能置态)。
- `data/AsyncExecutorTest`:并发超 maxInflight 时排队不丢单;`orTimeout` 按时失败并带 opName;`close()` 后再 submit 得到有序拒绝。
- **§16.2-★12 迁移演练(首建)**:追加 `002_add_dummy_column` 演练迁移 → 重启 → 旧数据完好、版本递增到 2;回滚 002 文件不存在的情况不适用(追加式,只前进)。
- **§16.2-★10 机制面(手动)**:`database.host` 改为不存在地址起服 → 插件正常启用、大厅可进、日志仅 WARN(无堆栈刷屏,重试带退避);恢复后重启自动 READY。(端到端"对局+结算跳过落库"在 5.4 合流后复验,见 5.4。)

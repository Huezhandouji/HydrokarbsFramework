## 施工步骤

### 步骤 1|值对象 —— `src/main/java/com/shdf/match/data/model/`(§12.1 data/model 行)

- `StatsDelta`(§10.3.4 形状):`(uuid, modeId, accumulate Map<StatColumn,Long>, extremum Map<StatColumn,Long>, matchesPlayedDelta, matchesWonDelta)` + `merge()`(同键合并:SUM 相加、MAX 取大)。
- `StatColumn`:KILLS/DEATHS/DAMAGE_DEALT/DAMAGE_TAKEN/OBJECTIVES_DONE/BOSS_KILLS/PLAY_SECONDS/BEST_SCORE(§10.3.4)。
- `PlayerProfile / PlayerStats / MatchRecord / LeaderboardRow`:不可变 record(§12.1),字段对齐 §10.1 表列。
- UUID↔`BINARY(16)` 转换工具放 `util/Serde`(§12.1 util 行),全部仓储统一经它——禁止各写各的字节序。

### 步骤 2|玩家仓储 —— `data/repo/PlayerRepository` + `impl/PlayerRepositoryImpl`(§10.3.3)

- `load(uuid, username)`:**一次往返拿全**(档案 + 分模式统计;JOIN 或同事务两查)——登录路径只此一次(§10.3.3 注)。
- `touch(uuid, username)`:局部更新 username/last_seen,不覆盖 settings。
- `saveSettings(uuid, settings)`:写 `player_profile.settings` JSON(§10.1-1;统计数字禁入 JSON——无法索引聚合,§10.1 设计说明)。

### 步骤 3|统计仓储 —— `data/repo/StatsRepository` + impl(§10.3.3)

- `applyDeltas(List<StatsDelta>)`:批量 UPSERT,**单事务**(§10.3.3;一局 20 人不得产生 20 次提交,§10.4 表)。
- `modeId="TOTAL"` → 只写 `player_stats`;否则写 `player_stats_mode`(§10.3.4;注意 `player_stats` 无 best_score 列,extremum 仅对分模式表生效,§10.1-2/3)。
- `top(modeId, column, limit)`:走 `idx_stats_mode_rank`(§10.1-3);`load(uuid, modeId)`。

### 步骤 4|UPSERT SQL(§10.3.4 全文为蓝本)

- 累加列 `col = col + n.col`;**`best_score = GREATEST(best_score, n.best_score)`**——SUM 与 MAX 两张 map 分离是本步核心,把 best_score 写成加法会"越刷越高"(§10.3.4 引语、§10.1-3 注)。
- `VALUES (?,…) AS n` 别名语法需 **MySQL 8.0.19+**(§10.3.4 注):启动期用 5.3 探针记录的 `SELECT VERSION()` 判断,低于 8.0.19 → 回退 java.sql 层拼装旧语法;回退实现只住 repo impl,不外溢。
- 批量提速前提是连接串 `rewriteBatchedStatements=true`(5.3 已配,§10.4)。

### 步骤 5|对局历史仓储 —— `data/repo/MatchHistoryRepository` + impl(§10.3.3)

- `record(MatchRecord)`:头表 `match_history`(含 `session_id`,§10.1-5 ★v2)+ 明细 `match_participant` **单事务**,返回生成的 match_id;`end_kind` 只取 WIN/DRAW/ABORTED(NEXT 不入表,§10.1-5 注)。
- `recent(uuid, limit)`:走 `idx_participant_uuid` 按 match_id 倒序(§10.1-6)。

### 步骤 6|端口实现 —— `src/main/java/com/shdf/match/bridge/persistence/PersistencePortImpl.java`(§12.1 bridge/persistence 行、§10.3.1 图)

- 实现 `engine/port/PersistencePort`(L1 实现 L2 接口;L1 禁依赖 L3/L4,§1.2),内部委托三仓储与 Flusher:
  - `stats/top` → AsyncExecutor 上的仓储查询 + **LRU 缓存 TTL 60s**(§10.2 排行榜行);flush 成功后失效同 mode 缓存,防脏读;
  - `accumulate(StatsDelta)` → `StatsFlusher.accumulate`(**主线程同步入队,零阻塞**,§10.3.1/§10.5);
  - `flushNow()` → Flusher;
  - 对局历史写入口:实例结束路径组装 `MatchRecord`——结局读 `EndGateComponent.outcome()` 强类型读口(§3.4),时长/人数/`session_id` 齐备——再交仓储 record。触发方设计未明示,见文末待裁决。
- **recordsHistory 门槛在调用侧**:`meta.recordsHistory=false` 的模式(lobby)整条落库路径不触发(§2.3、§10.1-3/5 注)——不在 SQL 里做 mode 排除,repo 层不出现任何 mode id 字面量。
- `DEGRADED` 行为:accumulate 照常入队(内存),flush 时检测 `DatabaseState≠READY` → 丢弃 pending + 节流 WARN(§14.2-3 内存模式语义);读口返回空/空 future,不抛给调用方。

### 步骤 7|write-behind —— `src/main/java/com/shdf/match/data/StatsFlusher.java`(§10.3.5 代码为蓝本)

- `pending: ConcurrentMap<StatKey, StatsDelta>`;`accumulate` 主线程纯内存 merge,零阻塞(§10.5)。
- 定时:单平台 daemon 线程 scheduler(`"hydrocarbs-flush"`,与 10-数据库.md §10.3.5 代码一致),周期 = `database.flush-interval-seconds`(默认 30,§15.2);`flushSafely` 吞单次失败不中断定时器(§10.3.5)。
- `flushNow()`:drain → `applyDeltas`;调用点=实例结束、玩家退出、`/stop`(§14.8)。
- `drainAndShutdown(Duration budget)`:onDisable 专用,**budget = `engine.shutdown-flush-budget-seconds`=3s**(§15.2;§10.5 末行);超时放弃剩余并 WARN,绝不挂死 watchdog(§14.9)。
- 写放大核算写进 javadoc(§10.3.5 末):每杀一写 ≈400 次/局 → write-behind 30s 一次+结束一次 ≈41 次,崩溃损失窗口 30s。

### 步骤 9|线程边界纪律(§10.5 全表照抄——框架基线部分,评审与 code review 对照用)

> 宿主扩展线 API(如角色系统桥接的 `RoleFacade#*`)不在本表展开——它们同受「触碰玩家实体状态 ⇒ 主线程」铁律约束,逐方法线程口径见 Shdf具体玩法设计案/08-角色桥接.md §8.10(框架基线无此 API;v4.1 原表的 `RoleFacade` 三行——`setRole/clearRole`、`operate`、`lastDamagerUuid`——已随玩法线迁出,原文完整存于彼处对照表)。

| 操作 | 必须在哪个线程 | 为什么(§10.5) |
|---|---|---|
| 读 `Session`/`SessionRoster`/实例状态/`AttributeBag` | 主线程 | 非线程安全且每 tick 在变 |
| 改会话/实例状态(比分、阶段、目标进度、切换) | 主线程 | 同上,且可能连锁触发事件派发 |
| 发 `MatchModeInstanceEvent` / `SessionEvent` | 主线程 | 派发是同步的,订阅者会改状态 |
| 世界操作(生成实体、放置、传送、改方块、加载/卸载世界) | 主线程 | Bukkit API 铁律 |
| 发消息/BossBar/Sidebar/音效/粒子 | 主线程 | Adventure & 实体 API |
| 注册/注销 Bukkit 监听器 | 主线程 | `registerEvents` 内部碰服务端状态 |
| 读 `config.yml`、解析 `maps/*.yml`+`modes/*.yml` | 虚拟线程 → 回主线程注册 | 文件 IO + 反序列化 |
| 世界模板复制(切换阶段 A6) | 虚拟线程 → 主线程加载世界 | 复制纯 IO;`WorldCreator` 必须主线程 |
| 迁移 DDL、`schema_version` 查询 | 虚拟线程 | 纯 IO |
| 统计读取、排行榜查询、对局历史写入 | 虚拟线程 | 纯 IO |
| `StatsFlusher#accumulate` | 主线程(仅内存合并) | 输入来自主线程状态,且必须零阻塞 |
| `flushNow` 的 SQL 执行 | 虚拟线程 | 纯 IO |
| `onDisable` 的 `drainAndShutdown` | 主线程发起,有界等待 ≤3s | 主线程被服务端等待;久等触发 watchdog |

三条铁律(§10.5 末):①`thenAccept` 回调运行在完成线程上,碰玩家必经 `Threads.runOnMain`;②已在主线程用 `runOnMain` 免调度;③主线程不得 `future.get()` 等 DB——唯一例外 onDisable 有界冲刷。

## 关键实现要点

- 分层即依赖:L4/L3 只见 `PersistencePort`;`PersistencePortImpl`(bridge)做翻译;`data/**` 只写 SQL(§10.3.1)。组件/模式 import `data/**` 即越界(§1.2 L4 禁止列)。
- UPSERT 幂等(`ON DUPLICATE KEY UPDATE`)→ 重放安全:applyDeltas 失败重试不会双倍计数(§14.9)。
- `accumulate` 在主线程只做内存合并;一切 SQL 在虚拟线程;查询结果回主线程必须经 `Threads`(§14.1)。
- lobby 零落库行是 `recordsHistory=false` 的机械后果;若发现需要在 repo 过滤 lobby,说明调用侧门槛漏了——回去修调用侧,不让内容词渗进 data 层(§14.12 精神)。
- 新模式要新指标(如"夺旗数")= 加一列 + 一条**追加式**迁移,不改 001(§13.2、§14.15)。

## 陷阱与纪律

- **§14.1 异步回调碰 Bukkit**:欢迎语/偏好应用必须回主线程。
- **§14.8 每杀一写(写放大)**:一切采集只进内存账本,落库只走 Flusher。
- **§14.9 进程退出丢写**:`drainAndShutdown` 有界;UPSERT 幂等保证重放安全。
- **§14.15 表结构演进不走迁移**:新指标必须新增迁移文件。

## 测试与验收

- `data/StatsRepositoryImplTest`(Testcontainers MySQL 8 或本地 MySQL):①累加列 SUM 正确;②best_score 重复应用同一 delta 不增长(GREATEST);③TOTAL/分模式分表正确;④中途异常整事务回滚无半写。

- **§16.2-★11 停服不丢(手动,首建)**:打完一局立即 `/stop` → 重启查库:该局 delta 全部在库(30s 窗口内的 pending 被 onDisable 冲刷兜住)。
- **§16.2-★10 端到端复验**:拔库跑完整一局(复放 5.2 脚本;玩法线端到端脚本,`Shdf具体玩法设计案/施工计划/阶段5-TDM首模式/5.2-端到端验收-大厅到对局.md`)→ 对局照常、结算正常、日志仅 WARN;恢复库后下一局落库自动恢复。

- **阶段出口总验**(施工计划总览 §1 阶段5 行):2 人实测 + 落库可查 + 停服不丢 + 降级内存 + lobby 零落库行,四句全部成立。

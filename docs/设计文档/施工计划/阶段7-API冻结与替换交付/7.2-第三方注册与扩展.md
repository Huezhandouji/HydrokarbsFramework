## 目标

1. 第三方插件**不改我们的 jar**:`getServicesManager().register(MatchModeProvider.class, provider, this, ServicePriority.Normal)`(§13.4)注册的模式被我们监听 `ServiceRegisterEvent` 收录——`build()` + `verifyDependencies`,坏模板跳过并 SEVERE,不进注册表(§7.2 表);
2. `ServiceUnregisterEvent` 摘除该提供者的模式,相关会话回退 fallback 模式(§13.4);
3. A9 三限制与第三方约束写进 javadoc(§0.2-A9、§13.4);
4. 示例工程 `examples/TheirPlugin` 完整可编译可运行(注册 → 目录 → 可切换 → 卸载回退四步闭环);
5. `ThirdPartyModeRegistrationTest`(★20)首建全绿。

## 关键实现要点

1. **为什么注册工厂不注册成品**:聚合根是 final 类不是接口,Builder 即声明语言,工厂接口即 SPI(§7.2 表);`verifyDependencies` 在注册表做注册前闸(§2.6),坏声明在注册期就被拒,永远到不了运行期——"坏声明在 `verifyDependencies`/`checkMap` 就被拒"(§7.2 表注)。
2. **事件过滤要严**:ServicesManager 上还有 `MiniGameApi.class`(我们自己,7.1)与 `RoleAPI`(角色系统)的注册——不按 `getType()` 过滤会把它们当模式工厂收进来。
3. **重复 id 双口径**:启动期 `discover()` 维持 §12.1 抛异常(响亮失败);运行期事件路径 SEVERE + 忽略后来者(Bukkit 事件回调抛异常会中断派发)。两口径写进 `registerProvider` javadoc。
4. **摘除映射用 `IdentityHashMap`**:同一 provider 实例只 build 一次;按 equals 混淆不同实例会摘错。
5. **注册/摘除全程主线程**:ServicesManager 事件在主线程派发;`SessionService` 读写主线程(§10.5)——监听器内不做任何异步包装。
6. **TheirPlugin 关键代码**(§13.4 的可编译版):

```java
public final class TheirPlugin extends JavaPlugin {
    @Override public void onEnable() {
        // 注册工厂,不是注册成品(§13.4)——早于/晚于 HydroKarbs 启动都安全:事件收录兜底
        getServer().getServicesManager().register(
                MatchModeProvider.class, new TheirModeFactory(), this, ServicePriority.Normal);
    }
}
public final class TheirModeFactory implements MatchModeProvider {
    @Override public String id() { return "their_mode"; }
    @Override public MatchMode build(MatchModeConfig cfg) {
        return new MatchMode.Builder("their_mode")
                .displayName(Component.text("Their Mode"))
                .icon(Material.BELL)
                .mapTags(Set.of("indoor"))
                .meta(new MatchModeMeta(Set.of(), false, 1, 16,
                        MatchModeMeta.DefaultTransition.STAY))
                .addComponent("banner", new TheirBannerComponent.Spec())
                .build();
    }
}
```

   `TheirBannerComponent`(展示"基类纪律照抄到位"的最小样例,§2.4):

```java
public final class TheirBannerComponent extends MatchModeComponent {
    public static final class Spec extends MatchModeComponent.Specification<TheirBannerComponent> {
        public Spec() { super("their_banner"); }
        @Override public TheirBannerComponent create(String id, MatchModeInstanceServices svc) {
            return new TheirBannerComponent(id, svc);
        }
    }
    private TheirBannerComponent(String id, MatchModeInstanceServices svc) { super(id, svc); }
    @Override public void start() {   // 玩家可见副作用最早在这里(§2.4 钩子注释)
        svc().self().participants()
            .forEach(p -> /* 播报,仅示例 */ { });
    }
}
```

   **注册时序两种情况都成立**(事件收录的意义,§13.4):

   | 启动顺序 | 发生什么 |
   |---|---|
   | HydroKarbs 先启 | TheirPlugin `onEnable` 注册 → `ServiceRegisterEvent` → 我们当 tick 收录,目录即含 |
   | TheirPlugin 先启 | 它注册时我们还没监听 → 我们 `onEnable` 的 `discover()` 跑 `ServicesManager.loadAll(MatchModeProvider.class)`(§12.1)补收录;反向场景(第三方中途卸载)由 `ServiceUnregisterEvent` 兜住 |
   | 热重载(reload 插件) | 第三方插件 disable→enable 循环 = 摘除 + 再收录各走一次事件,目录最终一致;期间正用其模式的会话按摘除路径回退 |

   为什么不用轮询兜底:事件即权威(§15.1 `CapabilityListener` 同款先例);轮询会掩盖"摘除未触发回退"的真缺陷。

## 陷阱与纪律

- **§14.13 让模式在引擎里注册自己**:收录是"注册表被动收",不是模式 import 引擎;TheirPlugin 全部文件在 `examples/TheirPlugin/**`,主仓 `src/` 不出现 `their_mode` 字面量(§16.2-4 禁词精神)。
- **§14.16/§14.17 风暴与重入**:摘除回退走入口①+force;引擎不认识 `their_mode`,回退目标永远是配置的 fallback-mode(§14.21:不写 `if (mode=="their_mode")`)。
- **§14.12 if-else 反弹**:`registerProvider` 不得按 provider 来源(本 jar/第三方)分支——发现面不同,注册后一律同构(§12.1 discover 两来源汇合同一 `register`)。
- **§14.24 引擎不长内容**:registry 只认 `MatchModeProvider` 类型与 id 字符串,不认任何玩法词汇(EnginePurityTest 持续守)。
- 施工计划 §3 纪律 5:动工前通读本节引用的 §14 条目。

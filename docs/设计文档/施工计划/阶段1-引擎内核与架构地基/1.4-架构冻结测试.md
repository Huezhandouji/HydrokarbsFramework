## 关键实现要点

1. **锚定修正的理由再说一遍**:
   §16.2 的 `..mode..`/`..component..` 是命题的口语化写法;
   ArchUnit 的 `..` 匹配零个或多个包段,`com.shdf.match.engine.mode` 同样命中——照抄会拿假阳性;
   锚定到 `com.shdf.match.mode../component..` 后命题不变,这是检验方式的技术修正(已在阶段 README §4 与待裁决清单记录)。
2. **源码扫描测试的工程事实**:
   Gradle test 工作目录 = 工程根,相对路径直接可用;
   扫描含注释与字符串——这是特性不是缺陷:注释里写 "Phase" 的诱惑正是要拦的。
3. **★3 的"规则先建"**:
   宿主桥接包与宿主插件在本阶段都不存在(框架基线不含宿主扩展,见 Shdf具体玩法设计案/),规则通过是空集;
   价值在于 Shdf 侧阶段 3 第一行越界 import 就红,而不是事后补网(§16.2 映射表)。
4. **AggregatePurityTest 别扫 Builder**:
   `getDeclaredMethods()` 只取 MatchMode 自身;Builder/ComponentEntry 是嵌套类,各有自由;
   冻结面 = §2.8 列出的 9 个,一个不多。
5. **ComponentResolutionTest 的 fake 落点**:
   放测试源集内(engine 包可共享的最小 StubSpec);
   1.5 的 `TestComponent` 是另一个更重的生命周期记录件——两者不要混用。

## 陷阱与纪律

- **§14.12 阶段/规则里的 if-else 反弹**:
  EngineHasNoModeStringsTest 是它的机械化下半身(禁 mode id);
  上半身纪律(不按阶段 id 分支)在 1.5 的组件里执行。
- **§14.21 大厅特判反弹**:
  禁词含 `lobby` 的唯一目的;fallback 是配置项,引擎按 id 查表、不认识任何具体 id。
- **§14.23 / §14.24 / §14.25**:
  分别由 AggregatePurityTest / EnginePurityTest / MatchModeInstanceServicesMembersTest 冻结;
  三条测试失败时的唯一正确动作是"把行为还给组件 / 把词汇赶出引擎",不是改断言。
- **§14.26 状态主人唯一**:
  AttributeNamespaceTest 是执法点;组件 Key 常量的包私有可见性从阶段 4 的第一个组件开始执行。

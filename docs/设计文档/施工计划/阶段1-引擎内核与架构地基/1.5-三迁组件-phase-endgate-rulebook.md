## 目标

本子阶段结束时,v3 的"引擎三迁"以 L3 组件形态落地(§16.1-P0.5),引擎对三者零认知(★24):

- 阶段状态机:`component/phase/PhaseComponent` + `PhaseSpec`(Timed/Await 阶段表)+ `PhaseChanged`(事件住组件包);
- 结束判定门:`component/endgate/EndGateComponent` + `EndCondition` + `GateVerdict` + `MatchOutcome`(§3.4);
- 声明式规则簿:`component/rule/RuleBookComponent` + `Rule`(纯函数,离线可测)。

并用 `TestComponent` 假组件离线跑完一次实例 `awake → start → update → stop` 全生命周期——**P0 出口闸门**(§16.1-P0)。

三件全部"要就挂、不要不挂":判定一个模式要不要阶段/结束判定/规则簿,与要不要队伍是同一件事——Builder 里加不加一行 `addComponent`(§6.1 尾注)。

## 施工步骤

三个组件包都在 L3(`com.shdf.match.component.*`),依赖面只有 L2 契约;**互相之间不 import**。

1. **`component/phase/PhaseSpec.java`**(纯数据;Shdf具体玩法设计案/04-大厅模式.md §4.2 `lobbyPhases` 的用法即签名)

   - `record PhaseSpec(String id, Kind kind, Predicate<MatchModeInstanceView> entryWhen, Integer durationTicks)`;
   - `enum Kind { AWAIT, TIMED }`;
   - 构造口径照 Shdf具体玩法设计案/04-大厅模式.md §4.2:AWAIT 给 `entryWhen`(为真即进入,如 `ctx -> 成员数 >= min`)、duration 为 null;
     TIMED 给 `durationTicks`、entryWhen 为 null;
   - ★ Kind 只有两枚——CONTEXT.md(权威)只列 Timed/Await;
     §6.1-#4 提到的"Objective 阶段表"由 AWAIT 的 entry 谓词覆盖进度检查(已列待裁决)。

2. **`component/phase/PhaseComponent.java`**(`final class extends MatchModeComponent`;状态唯一:当前索引/进入 tick 全在组件内)

   - `static final class Spec extends MatchModeComponent.Specification<PhaseComponent>`:
     构造持 `List<PhaseSpec>`(声明序 = 推进序)+ `boolean loopOnFinish`(默认 false = 停在末阶段);
     `create(id, svc)` 返回组件实例(svc 构造期注入,§2.4)。
   - `start()`:进入首阶段(AWAIT 未满足就停在首阶段等待;TIMED 直接起表),发布 `PhaseChanged`。
   - `update()`(每 tick):
     - 当前 AWAIT → 求值 `entryWhen`,为真转下一阶段;
     - 当前 TIMED → `durationTicks` 耗尽转下一阶段;
     - 末阶段到点 → `loopOnFinish` 决定循环回首阶段或停留(大厅 STAY 语义靠它,§4.1 表——大厅为玩法侧示例模式,见 Shdf具体玩法设计案/04-大厅模式.md);
     - 每次转场发布 `PhaseChanged`。
   - `jump(String phaseId)`:显式跳转(Rule 的 then 跨组件驱动阶段推进需要它;玩法侧跳阶段调用用例见 Shdf具体玩法设计案/05-四模式矩阵.md §5.2 与 Shdf具体玩法设计案/04-大厅模式.md §4.2 Rule 的 then);不存在即抛 `IllegalArgumentException`(响亮失败)。
   - 读口(Shdf具体玩法设计案/04-大厅模式.md §4.2 与 §6.2 的消费面):
     - `currentId()` / `currentExpired()`(Shdf具体玩法设计案/04-大厅模式.md §4.2 `LobbyCountdownEndCondition` 用法);
     - `countdown()` → `Optional<PhaseCountdown>`;
       组件自有 `record PhaseCountdown(int remainingTicks, int totalTicks)`——
       阶段 4 的 `DisplayModel.Countdown` 由 DisplayComponent 翻译,不让 phase 反向依赖 display(★v1.3:display 已迁 Shdf 侧 10,翻译随宿主 display 组件;phase 零依赖 display 的方向不变,21-D2)。
   - **`component/phase/PhaseChanged.java`**:
     `record PhaseChanged(String fromPhaseId, String toPhaseId, long elapsedTicks) implements MatchModeInstanceEvent`
     (带时间组件,§12.2 缩写注记的处理同 1.3;事件词汇跟发布者走——住本包,不进 engine/event)。
   - 阶段状态只有一个写者 = 本组件;其他组件经读口或订阅 `PhaseChanged` 消费(§14.24 的两条合法路径)。

3. **`component/endgate/MatchOutcome.java`**(§3.4 第一代码块逐字)

   - `record MatchOutcome(Kind kind, @Nullable String winnerId, String reason)`;
   - `enum Kind { WIN, DRAW, NEXT, ABORTED }`;
   - ★ 玩法结局词汇,住 component/endgate,引擎零认知(v3.1 从引擎侧结束货币中拆出;CONTEXT.md"EndCondition/GateVerdict/MatchOutcome"行)。

4. **`component/endgate/GateVerdict.java` + `EndCondition.java`**(§3.4)

   - `record GateVerdict(MatchOutcome outcome, Optional<TransitionIntent> intent)`——判定产物:结局(内容)+ 可选去向(框架货币);
   - `interface EndCondition { int priority(); Optional<GateVerdict> evaluate(MatchModeInstanceView ctx); }`——
     纯函数数据,不是组件;可离线单测(★9 的判定器半边)。

5. **`component/endgate/EndGateComponent.java`**(§3.4 第二代码块逐字)

   - `Spec(List<EndCondition> conditions)`(priority 在 EndCondition 上);`create(id, svc)`。
   - `update()`(§3.4 算法逐字):
     - `conditions` 按 `priority` 降序(同 tick 命中取高优先级,表注见 Shdf具体玩法设计案/05-四模式矩阵.md §5.2);
     - `evaluate(view())` → `flatMap(Optional::stream)` → `findFirst()`;
     - 命中则:`lastOutcome = v.outcome()`(结局留内容层)+ `svc().self().end(new EndResult(v.intent()))`(只有去向交给引擎);
     - `end` 置 ENDING 后下一 tick 由 ticker 处置(§3.1);重复 end 被 `requestEnd` 的幂等护栏挡掉(1.3)。
   - 强类型读口 `Optional<MatchOutcome> outcome()`——Stats/Display 消费,引擎不知道它存在(§3.4)。
   - `onHandoff` 可选:把结局写进**自己命名空间**的交接键,供下一实例展示(§3.4;
     键 = `EndGateComponent.HANDOFF_OUTCOME`,namespace "endgate"——键随主人,§3.3)。
   - 状态唯一:`lastOutcome` 是本组件唯一状态字段(§3.4 注"状态唯一:命中后保存")。
   - ★ 不加"防抖/冷却"之类的自创逻辑——切换风暴防护是会话层 min-dwell 的事(§3.5,阶段 2)。

6. **`component/rule/Rule.java`**(Shdf具体玩法设计案/04-大厅模式.md §4.2、Shdf具体玩法设计案/05-四模式矩阵.md §5.2 用法即签名)

   - `record Rule(String id, Predicate<MatchModeInstanceEvent> trigger, Predicate<RuleContext> when, Consumer<RuleContext> then)`;
   - trigger/when/then 全纯函数(§11.3"规则可离线测"的载体);
   - 配套 `component/rule/RuleContext.java`:
     `interface RuleContext extends MatchModeInstanceView { MatchModeInstanceEvent event(); <E extends MatchModeInstanceEvent> E eventAs(Class<E> type); }`
     (`eventAs`/`tick` 两用法合集;玩法侧调用用例见 Shdf具体玩法设计案/05-四模式矩阵.md §5.2 与 Shdf具体玩法设计案/04-大厅模式.md §4.2 `ctx.tick()`)。

7. **`component/rule/RuleBookComponent.java`**(§6.1-#6)

   - `Spec(List<Rule>)`;`create(id, svc)`。
   - `onEvent(ev)`(基类中央总线钩子,§2.4):按 Rule 声明序求值——
     `trigger.test(ev)` → `when(ctx)` → `then(ctx)`;
   - **逐条** try/catch 隔离:WARN + 继续下一条
     (总线隔离的是订阅者,规则簿把隔离再下探一层——与 §11.3"一个坏规则不会毁掉整局"同精神);
   - 可选件:不要规则簿的模式不挂(§6.1"非引擎必备")。

8. **测试件 `TestComponent`**(test 源集,全阶段共用)

   - `extends MatchModeComponent` 的假组件:按序记录钩子调用
     (`awake/start/update/onEvent/onHandoff/stop` 各自追加到共享 `List<String>`);
   - 可构造时声明 `requires`/`requiresOptional`(与 1.4 `ComponentResolutionTest` 的口径一致);
   - 提供 `Spec` 工厂(含 descriptorLabel);
   - **禁止** import 任何 Bukkit 类型。

9. **离线全生命周期测试(test/component/;P0 出口闸门,§16.1-P0)**

   - 装配假模式:`MatchMode.Builder("test_mode")` 挂 `phases`/`endgate`/`rules`/`test`(TestComponent);
   - 离线环境:1.3 的 Session 壳 + 测试用 `MapDefinition` + Map 背后 `MatchModeConfig`(1.2 的 test 实现)

## 关键实现要点

1. **"事件词汇跟发布者走"是本子阶段的第二主题**(§12.2):
   `PhaseChanged` 住 component/phase,不在 engine/event——引擎事件族因此保持纯净;
   后续组件照此办理(ScoreChanged/TeamChanged/RoleKillEvent 各归其包,§12.2 注)。
2. **EndGate 的 update 是 §3.4 代码块的逐字翻译**:
   排序 → 求值 → findFirst → 记结局 → 交去向;一行不多、一行不少。
3. **三组件互相零 import**:
   阶段推进到"结束判定"的协作只经实例事件(`PhaseChanged` 订阅)或 `getComponent`,
   不经彼此包依赖;模式层(阶段 2+)负责把它们拼进同一张表。
4. **TestComponent 的钩子记录是 P0 闸门的度量衡**:
   断言的是"容器按声明序、无条件广播"(§2.4 生命周期 javadoc),不是断言任何玩法语义。
5. **离线装配的最小假件清单**:
   Session 壳(1.3)+ MapDefinition / Map 背后 MatchModeConfig(1.2 的测试实现)+ `Handoff.empty()` + 假 EngineServices;
   全部 test 源集,不允许任何 fake 反向进 main(引擎不沾测试思维)。

## 陷阱与纪律

- **§14.24 引擎重新长出状态机**:
  本子阶段是 P0.5 存在的全部理由——三件事必须以组件形态**先于**任何真实模式成型
  (§16.1 尾注:否则模式开发期一定出现"顺手在引擎加回调"的回流);
  写完复跑 1.4 的 EnginePurityTest 确认零污染。
- **§14.12 阶段/规则里的 if-else 反弹**:
  三组件内部不得按具体阶段 id/规则名分支——阶段是数据(`PhaseSpec`),规则是数据(`Rule`),
  模式差异只在 Builder 声明里。
- **§14.26 绕过状态主人裸写**:
  EndGate 写交接键只用 namespace "endgate";
  Rule 的 then 里跨组件读写一律走 `ctx.component(X)` 的强类型读口,不碰他人 AttributeBag。
- **§14.17 切换重入(前置纪律)**:
  Rule 的 then 与 EndGate 命中路径里**禁止**直接发起切换——结束只有 `end()` 一个口,
  切换由 ticker 在 ENDING 后的下一 tick 代为发起(§3.2 触发入口 ②、§3.5)。

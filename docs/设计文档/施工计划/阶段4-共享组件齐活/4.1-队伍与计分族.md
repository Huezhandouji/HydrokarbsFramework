> HydroKarbs MiniGame Framework · v1.0(自 SHDFMatch 设计案 v4.1 剥离玩法重构;玩法实现见 Shdf具体玩法设计案/)
> 对应设计案:06-共享组件 §6.1(#1/#2/#3/#18/#19)、12-代码骨架 §12.1(team/score/respawn 包);玩法侧用法权威(大厅/各玩法的实现见 Shdf具体玩法设计案/):Shdf具体玩法设计案/05-四模式矩阵.md §5.1(队伍模型/重生/计分载体矩阵)、§5.2(回合循环与阶段回跳)、§5.3(复用切分表);路线图:16-路线图与验收 §16.1-P3;前置:阶段1 全部(组件基类/svc/事件总线/Phase+EndGate)、阶段2 的 2.4(MapDefinition 与出生点)、**4.2(`component/objective/Objective` 接口,推荐执行序在 4.1 之前)**。

## 目标

本子阶段结束时,新增五个可独立装配、离线可测的组件(六个新类 + 三个支撑类型):

- 挂 `TeamComponent.Spec` 即获得队伍定义/分配/平衡/换队限制/队伍敌对读口(§6.1-#1);
- 挂 `ScoreComponent.Spec` 即获得按队/按人计分、加权重、连杀 streak 与 `ScoreChanged` 事件(§6.1-#2);
- 挂 `RespawnComponent.Spec(RespawnPolicy.*)` 即获得禁/定时/限次三种重生策略(§6.1-#3;各玩法取用哪一策略与参数区间,见 Shdf具体玩法设计案/05-四模式矩阵.md §5.1);
- 挂 `RoundComponent.Spec` 即获得回合循环(Prep/Live/RoundEnd 阶段回跳、回合重置、累计比分),且回合结束不产生面向框架的 EndResult(Shdf具体玩法设计案/05-四模式矩阵.md §5.2;§6.1-#18);
- 挂 `EconomyComponent.Spec` 即获得局内货币/购买菜单/装备重置(§6.1-#19;可选挂载的玩法取舍见 Shdf具体玩法设计案/05-四模式矩阵.md §5.3 责任切分表)。

> 各玩法对本族组件的挂载取舍(✅/➕/➖/✖ 与独有载体归模式侧)是玩法线口径,统一见 Shdf具体玩法设计案/05-四模式矩阵.md §5.3 责任切分表;本子阶段只交付与模式无关的组件本体,矩阵落位不改变 §6.1 任何一行的职责定义。

## 施工步骤

1. **`src/main/java/com/shdf/match/component/team/TeamId.java` —— `record TeamId(String value)`**
   - 队伍标识值类型(§12.1 team 包清单)。
   - 不内置 `SPECTATOR` 之类约定常量:观战队 id 来自模式声明(§12.1 工厂示例 Spec 的第二参数)——组件禁一切内容词汇(★4/★24:"进攻方/防守方"不得出现于 `component/**` 源码)。

2. **`component/team/TeamComponent.java` —— `TeamComponent extends MatchModeComponent`**
   - **Spec 构造数据**:基础形如 §12.1 中性示例(`new TeamComponent.Spec(List.of("ALPHA","BRAVO"), List.of("SPECTATOR"))`);追加:`maxSize`、换队限制 `maxSwitchesPerMatch`/`switchCooldownTicks`(缺省 0 = 不限,对应 §6.1-#1"切换限制")——数值由模式工厂从 `modes/*.yml` 取(玩法侧键与取值示例见 Shdf具体玩法设计案/05-四模式矩阵.md §5.4)。数据缺键给默认并 WARN(§15.2 三铁律)。
   - **状态(状态唯一,§2.8-决断三)**:`Map<UUID, TeamId> assignment`(全实例唯一真值);换队计数 `Map<UUID,Integer>`;冷却时间戳表。
   - **职责逐项(§6.1-#1 五项)**:
     1. 定义:队伍清单/观战队来自 Spec;
     2. 分配:`assign(uuid, TeamId)` 显式 + `autoAssign()`(内部调 TeamBalancer);
     3. 平衡:委托 TeamBalancer(步骤 3);
     4. 切换限制:`switchTeam(uuid, to)` 校验换队计数与冷却,拒绝时返回响亮的失败值(不抛到实例级);
     5. 敌对:`areEnemies(UUID a, UUID b)`——同队 false,其余 true(未分配者互为敌,与宿主角色系统"没有阵营 ⇒ 敌人"的默认口径一致;对照原文已迁玩法线,见 Shdf具体玩法设计案/08-角色桥接.md)。
   - **事件**:`TeamChanged(uuid, from, to)` 住本包(事件词汇跟发布者走,§12.2)。
   - **敌对口径层级**:宿主扩展的角色包装组件(SHDF 扩展线)在场时,最终敌对以它的统一封装读口为准(非对称口径的唯一封装点,见 Shdf具体玩法设计案/09-角色组件层.md §9.5);TeamComponent 只提供队伍面读口。两层读口并存,由消费方(规则/保护监听器)选择口径——TeamComponent 不 import 任何桥接类型,也不 import 宿主扩展组件包 `component/role`(★23 的消费面纪律)。
   - **读口**:`teamOf(uuid): Optional<TeamId>`、`membersOf(TeamId)`、`teams()`、`spectators()`。

3. **`component/team/TeamBalancer.java` —— 纯函数类(非组件)**
   - 输入(现分配, 容量表, 候选 uuid 集),输出完整分配方案(§12.1 team 包清单)。
   - 策略:容量约束内最小化人数差(`|size(a)-size(b)| ≤ 1`);候选按 uuid 字典序处理,保证同输入同输出(确定性 = 离线可测的前提)。
   - 半场换边复用它做整体交换(步骤 6 的 `halfSwapAfter`,§15.2)。
   - 不持状态、不碰 Bukkit API——它只是"分配算法"本身,挂不挂都行的是 TeamComponent。

4. **`component/score/ScoreComponent.java` —— `ScoreComponent extends MatchModeComponent`**
   - **Spec 构造数据**:阈值(§12.1 中性示例:`new ScoreComponent.Spec(exampleCfg.scoreLimit())`——阈值是整场结束判定(EndCondition)的输入数据;玩法侧"回合分到顶即整场 WIN"的用法见 Shdf具体玩法设计案/05-四模式矩阵.md §5.2/§5.8)、权重表(来源类型 → 分值,§6.1-#2"支持加权重")。权重表由模式工厂从 `modes/*.yml` 取。
   - **状态**:按队 `Map<TeamId,Integer>`、按人 `Map<UUID,Integer>`、连杀 `Map<UUID,Integer>`——三个唯一真值都在本组件。
   - **读口(方法名与玩法侧消费用法逐字对齐,勿另起名;原文见 Shdf具体玩法设计案/05-四模式矩阵.md §5.6)**:`of(TeamId)`、`of(UUID)`、`teams()`(按分排序)、`streakOf(UUID)`。
   - **写口**:`add(TeamId, int, String reason)`、`add(UUID, int, String reason)`、`addWeighted(source, baseAmount)`(按 Spec 权重表换算)、`resetStreak(UUID)`(死亡时由消费规则调用)。
   - **连杀维护**:订阅引擎结构事件 `ParticipantKilled`(§12.2,自带 victim/killer/cause)驱动连杀——对 victim `resetStreak`、对 killer 自增;宿主扩展若另发布合成击杀事件(`RoleKillEvent`,事件词汇住 `component/role`,合法消费,§12.2),是否叠加消费属玩法线取舍(见 Shdf具体玩法设计案/09-角色组件层.md §9.5)。**禁用 `player.getKiller()`**(§14.4)。
   - **事件**:`ScoreChanged(scope, id, newValue, reason)` 住 `component/score`(§12.2 迁移清单)。
   - **依赖声明**:`requiresOptional(TeamComponent.class)`(按队计分挂队伍组件;纯个人计分可不挂,§2.4 可选依赖语义)。

5. **`component/respawn/RespawnPolicy.java` + `component/respawn/RespawnComponent.java`**
   - **RespawnPolicy**(§12.1 respawn 包):三策略的密封类型——`NONE`(禁重生)/ `TIMED(int delayTicks)`(定时重生,延迟为构造数据)/ `LIMITED(int lives)`(限次重生,配额为构造数据)。纯数据无行为;各玩法对策略与参数区间(含缺省值)的取用见 Shdf具体玩法设计案/05-四模式矩阵.md §5.1(§6.1-#3)。
   - **Spec**:`new RespawnComponent.Spec(RespawnPolicy.NONE)`(§12.1 中性示例同款;玩法工厂原样用例见 Shdf具体玩法设计案/05-四模式矩阵.md §5.8)。
   - **状态**:排队表 `Map<UUID, Long> reviveAtTick`(TIMED)/ 剩余生命 `Map<UUID,Integer>`(LIMITED)。
   - **推进**:`update()` 按 1-tick 节拍推进倒计时(§6.3 节拍口径;**不自起周期任务**,§14.6)。
   - **复活执行**:落点 = `svc().self().map().spawns(与队伍 id 同名的键)`(§15.2 地图约定;键名示例随玩法地图,见 Shdf具体玩法设计案/05-四模式矩阵.md §5.4);查空 = 配置错误,由模式的 `checkMap` 在装配期拒绝(`checkMap` 前置地图需求的玩法侧同类先例见 Shdf具体玩法设计案/05-四模式矩阵.md §5.2)。程序化触发口选型动工时以 papermc-plugin-dev 技能 references/04 实查为准,必须主线程(§15.3 线程表)。
   - **死亡拦截不在本组件**(§15.1:"拦下原版死亡要在伤害事件做")——若某策略需要拦死亡,由模式侧规则处理,组件只管排队与复活。
   - **配额语义**:LIMITED 耗尽 → 不再排队;读口 `remainingLives(UUID)`、`queued()`——"配额耗尽型结局"的整场判定(EndCondition)要读"重生配额为 0"才能成立(玩法侧判定用例见 Shdf具体玩法设计案/05-四模式矩阵.md §5.2),这是它必须提供读口的原因。

6. **`component/score/RoundComponent.java` —— `RoundComponent extends MatchModeComponent`**
   - **Spec 构造数据**:`new RoundComponent.Spec(cfg)`:`bestOf`、`halfSwapAfter`(§15.2 `rounds:` 块)等;玩法工厂的原样声明用例见 Shdf具体玩法设计案/05-四模式矩阵.md §5.8。
   - **状态切分(关键)**:回合比分真值在 **ScoreComponent**(显示构建函数经读口 `score.of(t)` 直接取;玩法侧显示用例见 Shdf具体玩法设计案/05-四模式矩阵.md §5.6);RoundComponent 只持回合序号与回合内标志——"内部消费 #4/#5"(§6.1-#18),不复制状态。
   - **回合级判定器**:回合级结束条件集合(哪些条件、什么优先级——玩法侧数据,见 Shdf具体玩法设计案/05-四模式矩阵.md §5.2 优先级表)以 `EndCondition` 同构形态由**本组件持有并在 `update()` 求值**(组件声明序先于 endgate 保证求值次序);命中 → `getComponent(ScoreComponent.class).add(胜队, 1)` + `getComponent(PhaseComponent.class).jump("ROUND_END")`。**不调用 `svc().self().end()`**("回合结束走 RoundComponent 的阶段回跳,不触发 switchMode"——玩法线口径,见 Shdf具体玩法设计案/05-四模式矩阵.md §5.2)。归属张力见文末「待裁决问题」。

   - **半场换边**:`halfSwapAfter` 达到时调 TeamBalancer 整体交换并发布 `TeamChanged`(§15.2)。

   - **依赖声明**:`requires(PhaseComponent.class)`、`requires(ScoreComponent.class)`、`requires(TeamComponent.class)`(缺一装配期响亮失败,§2.6)。

## 关键实现要点

- **比分真值单点**:玩法侧显示构建函数(原文见 Shdf具体玩法设计案/05-四模式矩阵.md §5.6)都从 `ScoreComponent` 读分——RoundComponent 不复制比分、Economy 不碰比分;谁加分的"语义"(击杀/目标/回合胜)由模式规则(RuleBook)决定,组件只提供记账读口(§14.12 防 if-else 反弹)。
- **判定器是数据**:回合级与整场级判定器(玩法侧实例见 Shdf具体玩法设计案/05-四模式矩阵.md §5.2/§5.8)都是纯函数(§3.4),给定状态可离线断言;实现为不可变记录 + `evaluate(ctx)`,不持实例引用。
- **重生与队伍解耦**:RespawnComponent 经 `getComponent(TeamComponent.class)` 查队伍拿出生点键;未挂队伍组件(理论可配)时退化为 map 缺省出生点——`requiresOptional` + 运行期自查(§2.4)。
- **数值边界不发明**:连杀不做时间衰减(设计未定义;如需,模式在 Rule 里调 `resetStreak`);货币无利息、无转账(设计未定义)。
- **全部主线程**:状态读写、Bukkit 调用、GUI、复活触发都在主线程(§15.3 线程表);组件内零 IO。

## 陷阱与纪律

- **§14.4 击杀归属**:ScoreComponent 连杀与击杀分严禁 `player.getKiller()`;以事件为准(结构 `ParticipantKilled` / 宿主扩展合成 `RoleKillEvent`),双源交叉验证属宿主扩展包装组件合成层职责(SHDF 扩展线,见 Shdf具体玩法设计案/09-角色组件层.md §9.5),不在这里重复。
- **§14.26 组件间裸写**:禁止直接写他组件命名空间;加分一律 `getComponent(ScoreComponent.class).add(...)`——状态主人提供读口。
- **§14.12 阶段 if-else 反弹**:RoundComponent/EconomyComponent 不写 `if (phase.equals("LIVE"))`;阶段感知 = 订阅 PhaseChanged 或模式 Rule。
- **§14.6 每实例周期任务**:重生倒计时/回合推进走 `update()` 节拍;需要延后一拍用 `svc().self().later()`(句柄自动回收)。
- **§14.18 SessionMember/Participant 不混用**:队伍/比分/生命的键是 uuid,属于 Participant 视图;不许把会话成员表当计分对象。
- **§14.7 跨局残留**:所有 `Map<UUID,…>` 状态随 stop 清空;不得依赖 close 的顺序假设(stop 与 start 严格对称,§2.4)。
- **§14.16/§14.17 切换风暴与重入**:RoundComponent 的回合回跳只 `jump` 阶段,永不触碰 `end()`/`switchTo()`;回合制整场结束交给 EndGate 单点。

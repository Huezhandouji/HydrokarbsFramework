# 4.5 生命周期辅助组件(含入场控制)

> HydroKarbs MiniGame Framework · v1.0(自 SHDFMatch 设计案 v4.1 剥离玩法重构;玩法实现见 Shdf具体玩法设计案/)
> 对应设计案:§6.1-#15/#16/#24 与 §12.1 lifecycle/visibility/join 包、§3.1(ConnectionTracker 会话级宽限)、§3.2 三级回退(leaveAll 兜底清安全态)、§3.2.1(★v3.2 JoinAdmission 端口与 JoinControlComponent)、§3.7(ResetStrategy 与 CleanupComponent 的配套关系)、§14.7(跨局残留);路线图:P3(§16.1);前置:4.1(Respawn/Team 读口)、4.2(Interaction 通道读口)、阶段2 的 2.3(JoinAdmission/JoinDecision 端口)与 2.4(ResetStrategy/WorldHandle)。本子阶段还负责**出口闸门的收口**:把 21 行 L3 组件的生命周期幂等回归套件(LifecycleIdempotencyTest)建齐。

## 目标

本子阶段结束时:

- 挂 `DisconnectComponent.SPEC` 即获得实例内断线善后(会话级宽限仍归 SessionService,§6.1-#15 的两层分工);
- 挂 `VisibilityComponent.SPEC` 即获得隐身/观战/创造安全态与碰撞体开关,且 stop 后零残留——旧插件"下一局带着上一局状态(创造模式、隐身)"事故的结构性解(§14.7);
- 挂 `CleanupComponent` 即获得方块/实体还原,配套 `REUSE_DIRTY` 地图(§3.7);
- 挂 `JoinControlComponent.Spec(…)` 即获得完整入场控制(★v3.2):不挂 = 默认全接纳(§3.2.1);
- 21 行 L3 组件全部并入统一生命周期幂等回归套件,阶段4 出口闸门可机械核验。

组件挂载矩阵(§6.1)在框架侧只定通用组件本体;各模式行的挂法落位属玩法侧口径,见 Shdf具体玩法设计案/(Shdf 侧 05 矩阵)。CleanupComponent 无独立矩阵行(§12.1 lifecycle 包;REUSE_DIRTY 图的配套件,§3.7)。

## 施工步骤

1. **`component/lifecycle/DisconnectComponent.java` —— 实例内断线善后**
   - `SPEC` 无参常量(§12.1 工厂引用:`DisconnectComponent.SPEC`)。
   - **两层分工(§6.1-#15 原文)**:会话级断线宽限(`disconnect-grace-seconds`,默认 60)在 SessionService 的 `ConnectionTracker`(§3.1);本组件只管**实例内**善后,不复制连接态、不反向查会话(§14.18:连接态要活过切换,是会话的事)。
   - **触发**:订阅 `ParticipantLeft`(真正退出,含宽限超时后的移除)。
   - **善后清单**(全部经他组件读口或本组件自有状态):
     1. 重生队列移除(`getComponent(RespawnComponent.class)` 读口);
     2. 活跃读条通道取消(4.2 的 InteractionComponent 读口);
     3. 本组件"离场参与者"登记表打标——比分/队伍名额**保留**(重连恢复语义,§3.1"重连即恢复");
     4. 显示注销由 DisplayComponent 订阅同一事件自愈(4.3;★v1.3:display 迁 Shdf 侧 10 后由宿主侧 display 组件自愈,本组件仍不代劳),本组件不代劳。
   - **回归**:订阅 `ParticipantJoined`(宽限内重连)执行 `reapply(uuid)`:按登记表恢复个人视图并清除打标。
   - `stop()` 清登记表,幂等。

2. **`component/visibility/VisibilityComponent.java` —— 安全态与碰撞体**
   - `SPEC` 无参常量(§12.1 工厂引用:`VisibilityComponent.SPEC`)。
   - **职责四件(§6.1-#16)**:隐身、观战、创造安全态、碰撞体开关。
   - **`awake()`**:记录全员进入实例前的**原始态**(GameMode/allowFlight/invulnerable/collidable)——还原依据,唯一地住本组件(此步零可见副作用,§2.4)。
   - **API**(全部主线程,§15.3):
     - `applySafety(uuid)`:按 Spec 缺省安全态(GameMode、飞行策略是 Spec 构造数据);
     - `spectate(uuid)`:SPECTATOR + `setCollidable(false)`;
     - `conceal(uuid)` / `reveal(uuid)`:对其他参与者 hide/show(Paper 的 hide 带 plugin 参数,签名以 papermc-plugin-dev 技能 references/05 实查为准);
     - `setCollidable(boolean)` 直通读口。
   - **`stop()`**:全员还原原始态 + 全量 reveal + collidable 复位(与 start 严格对称,§9.4);幂等(已还原的跳过)。
   - **与框架兜底的关系**:三级回退的 `SessionService#leaveAll` 清 gamemode/隐身(§3.2 三级)是第二道兜底——两层各自幂等,谁先谁后都收敛;本组件不得假设兜底存在。

3. **`component/lifecycle/CleanupComponent.java` —— 方块/实体还原(REUSE_DIRTY 配套)**
   - **职责出处**:§3.7 `ResetStrategy` 注释——REUSE_DIRTY 图"打完不重建,靠 CleanupComponent 把方块/实体还原(快,适合回合制连续开局)";TEMPLATE_RESTORE 图不必挂(世界整体删建)。
   - **登记读口**(写世界前必须登记——这是模式侧 code review 检查项):
     - `recordBlock(Position, BlockState before)`:记录原貌;
     - `registerEntity(Entity)`:生命周期归实例的实体(Boss/掉落物/盔甲架)。
   - **`stop()`**:逆序还原——先清登记实体(discard),再按记录还原方块(后写先还原);同 tick 完成为缺省(回合制场景区域小),大区域分帧还原是 Spec 构造数据 `batchRestore=true` 的增强项,非缺省。
   - **与 4.2 区域保护的协同**:保护区内的改动本就不该发生(ProtectionListener 已取消),Cleanup 是最后防线不是日常路径。
   - **不碰 `WorldPort`**(世界生命周期只有 SessionService 调用,§3.7 规则表):本组件只还原**世界内容**,不加载/卸载世界。

4. **`component/join/JoinControlComponent.java` —— 入场控制(★v3.2,§3.2.1、§6.1-#24)**
   - `implements JoinAdmission`(引擎端口,2.3 落地)——本组件是端口在 L3 的**标准实现**;模式挂载即接管入场裁决。
   - `Spec(MidJoin midJoin)`:嵌套 `enum MidJoin { ADMIT_WHEN_RUNNING, SPECTATE_WHEN_RUNNING, REJECT_WHEN_RUNNING }`(对局进行中的入场策略;Warmup/无实例阶段一律 ADMIT)。可选构造参数 `allowedPhases`(List<String> 阶段白名单):`requiresOptional(PhaseComponent.class)`(§9.2 同款可选依赖纪律;组件不在场或阶段不在白名单时按 midJoin 兜底)。
   - **裁决逻辑(纯数据驱动,零模式分支)**:`REJECT` → `JoinDecision(REJECT, "对局进行中,回合结束后可进")`(reason 人读、进 detail 不进契约);`SPECTATE` → 观战位安置经 `getComponent(VisibilityComponent.class).spectate` 与 TeamComponent 的 SPECTATOR 队;`ADMIT` → 参赛位(队伍分配归 TeamComponent)。
   - **两个触发点同一入口**(§3.2.1):B4 初始摆放(`ctx.trigger()==INITIAL_PLACEMENT`)与运行中 join(`MID_JOIN`)——按 ctx 数据分支,不按模式分支。
   - **无长住状态**:裁决是纯函数(读 Spec + 阶段读口),占用/名额真值归 TeamComponent(状态唯一,§2.8-决断三);`stop()` 幂等。
   - **矩阵落位**(§6.1-#24):本组件行的各模式挂法示例(MidJoin 取值与挂/不挂)属玩法侧口径,见 Shdf具体玩法设计案/(Shdf 侧 05 矩阵 #24 行);不挂 = 默认全接纳。

5. **统一回归套件:`src/test/java/com/shdf/match/architecture/LifecycleIdempotencyTest.java`**
   - **覆盖对象**:§6.1 矩阵中住 `component/**` 的 21 行(下表),参数化逐组件跑:
     - `awake×2`:依赖解析幂等,零玩家可见副作用(fake 世界/玩家记录零调用);
     - `start×2`:可见副作用(传送/装备/显示登记)恰好一次;

## 关键实现要点

- **还原的对称性是测试目标不是口号**:Visibility/Cleanup 的 stop 都以"记录→逆序重放"实现;原始态记录在 awake(不可见,§2.4)、应用在 start、还原在 stop——三段幂等各自独立可测。
- **善后不删真相**:Disconnect 保留队伍/比分等实例状态(重连恢复),只清理"瞬态过程"——瞬态判据 = "重连后是否应自动恢复",与 §3.1 会话级语义对齐。
- **Cleanup 的登记口是纪律不是机制**:组件无法拦截他人直接 `setBlock`;因此本子阶段 PR 必须在 `component/**` 全包 grep `setBlockData|setType` 确认所有世界写入都过登记口(模式侧写入在 5.1/6.x 用同一检查项)。
- **无自建调度**:善后/还原一律事件或 `update()` 节拍;`svc().self().later()` 的句柄框架自动取消(§14.6)。

## 陷阱与纪律

- **§14.7 跨局残留(本子阶段的主题陷阱)**:清场散在多处、靠"延迟 1 tick"约定,是旧插件事故的直接成因;本组件三件 + close 单入口 + ENDING 下一 tick 处置(§3.1)构成结构性封闭。
- **§14.18 两层身份**:断线宽限的真相在 `ConnectionTracker`(会话);本组件绝不复制在线态,只消费实例事件。
- **§14.26 裸写**:善后动作全部经各组件读口;本组件无 attrs 写入需求(如有,namespace=`disconnect` 组件 id)。
- **§14.6 周期任务**:无自建任务。
- **§14.17 重入**:善后路径不得触发 `switchTo`/`end`;退出引发的实例结束是 EndGate/框架的事。
- **§15.3 线程**:hidePlayer/GameMode/方块还原全部主线程;组件内零 IO。

### 8.2 核心桥接接口(防腐层)

```java
package com.shdf.match.bridge.role;

/**
 * 角色系统的防腐层。全工程「唯一」允许 import com.shadowHunterRolesPlugin 的类。
 * 设计纪律:本类方法签名只使用 JDK / Bukkit 类型,绝不泄漏 RoleAPI 的类型(如 RoleInfo)。
 * 因此角色系统升级换签名时,只改这一个文件。
 */
public final class RoleFacade {

    private final RoleAPI api;   // 唯一引用点(懒解析,见 §8.8)

    // ── 查询:已有角色 / 描述 ──────────────────────────────────────────
    public Set<String> knownRoleIds();                       // → api.getAllRoleIds()
    public List<RoleDescriptor> catalog();                   // → api.getRoles(),转成自家 record
    public boolean isValidRole(String roleId);               // → api.isValidRoleId()
    public Component roleDisplayName(String roleId);         // → api.getRoleDisplayName()
    public List<Component> roleDescription(String roleId);   // → api.getRoleDescription()
    public Material roleIcon(String roleId);                 // → api.getRoleIcon()(缺失回 AIR 而非 null!)

    // ── 查询:玩家当前角色 ────────────────────────────────────────────
    public String roleIdOf(UUID uuid);                       // → api.getPlayerRoleId(),无则 null
    public boolean hasRole(UUID uuid);                       // → api.hasRole()
    public Component playerRoleDisplayName(UUID uuid);       // → api.getPlayerRoleDisplayName()

    // ── 阵营(★ 角色系统没有阵营 API:一律经组件操作面 componentId = "faction")──
    /** 该玩家**自己**那份实例的当前阵营 → operate(uuid,"faction","faction");无实例 ⇒ RoleFaction.UNKNOWN。 */
    public RoleFaction playerFaction(UUID uuid);
    /** 该玩家**当前所持角色声明**的默认阵营 → operate(uuid,"faction","declared");无实例 ⇒ UNKNOWN。 */
    public RoleFaction declaredFaction(UUID uuid);
    /** ★ 必须主线程。只影响该玩家 → operate(uuid,"faction","set <名>");RoleFaction.OTHER ⇒ false 且不发起操作。 */
    public boolean setPlayerFaction(UUID uuid, RoleFaction faction);
    /** ★ 必须主线程。复位为声明值(幂等)→ operate(uuid,"faction","reset")。 */
    public boolean resetPlayerFaction(UUID uuid);
    /** ★ **非对称**:在 **a 的实例**上 operate(a,"faction","hostile <b>");a 无实例(回 null)⇒ true("没有阵营 ⇒ 敌人")。 */
    public boolean areHostile(UUID a, UUID b);

    // ── 设置 / 清除 ──────────────────────────────────────────────────
    /** ★ 必须主线程调用:内部会重建热键栏物品并写入背包。 */
    public boolean setRole(UUID uuid, String roleId);        // → api.setPlayerRole()
    /** ★ 必须主线程调用。幂等——清场单闸门 `RoleComponent.stop` 全员清角依赖这一点(v3.1 已删除引擎级 B3 兜底,../03 §3.2-B3 勘误注;09 §9.7)。 */
    public boolean clearRole(UUID uuid);                     // → api.clearPlayerRole()

    // ── 击杀归属 ─────────────────────────────────────────────────────
    /** ★ 唯一正解。禁用 player.getKiller()。参数必须是 Player(LivingEntity 重载不存在)。 */
    public UUID lastDamagerUuid(Player victim);              // → api.getLastDamagerUuid(player)

    // ── 角色数据操作(字符串协议 → 类型化) ───────────────────────────
    public String operate(UUID uuid, String componentId, String payload);  // → api.executeComponentOperation()
}
```

**自家值对象**(不泄漏 `RoleInfo`):
```java
public record RoleDescriptor(
        String id,
        Component displayName,
        List<Component> description,
        Material icon
        // ★ 不含阵营:角色目录已没有阵营来源(RoleInfo 只有这四个成分);
        //   需要"某角色声明的默认阵营"只能从正持该角色的玩家实例上读(declaredFaction)
) {}

public enum RoleFaction { SHADOW, HUNTER, UNKNOWN, OTHER }   // OTHER 兜住未来的新阵营名
// 映射口径:读方向 = 组件操作面返回的**字符串** → RoleFaction(认不出 ⇒ OTHER,null/空 ⇒ UNKNOWN);
// 写方向 = RoleFaction → 阵营名(OTHER 无对应名字 ⇒ 拒绝,且不发起操作)。外部 enum core.Faction 不参与。
```

### 8.3 `RoleStateAccess`:把字符串协议包成类型化 API

`executeComponentOperation` 返回 `String`,语义是"`null` = 未识别/拒绝,`""` = 已识别无回值,非空 = 规范化值"。直接在模式里拼字符串必然出事故。包一层:

```java
package com.shdf.match.bridge.role;

/** 角色数据的类型化读写。所有方法都必须在主线程调用(会触碰玩家状态)。 */
public final class RoleStateAccess {

    private final RoleFacade role;
    private static final String ENERGY = "energy";
    private static final String SANTE  = "sante";
    private static final String BUFFS  = "buffs";

    public OptionalInt energy(UUID u)          { return readInt(u, ENERGY, "current"); }
    public OptionalInt setEnergy(UUID u, int v){ return readInt(u, ENERGY, "set " + v); }
    public OptionalInt addEnergy(UUID u, int v){ return readInt(u, ENERGY, "add " + v); }
    public boolean     consumeEnergy(UUID u, int v) { ... "consume " + v ... }

    public OptionalInt sanTe(UUID u)           { return readInt(u, SANTE, "current"); }
    public OptionalInt setSanTe(UUID u, int v) { return readInt(u, SANTE, "set " + v); }
    public OptionalInt gainSanTe(UUID u, int v){ return readInt(u, SANTE, "gain " + v); }

    /** buff 用 `buffs` 组件的动词面;具体动词表见角色系统 BuffComponent#onOperationCommand。 */
    public boolean applyBuff(UUID u, String buffType, int ticks) { ... }

    private OptionalInt readInt(UUID u, String componentId, String payload) {
        String raw = role.operate(u, componentId, payload);
        if (raw == null || raw.isEmpty()) return OptionalInt.empty();   // ★ 不抛,不给模式 NPE 的机会
        try { return OptionalInt.of(Integer.parseInt(raw.trim())); }
        catch (NumberFormatException e) { return OptionalInt.empty(); }
    }
}
```

**为什么返回 `OptionalInt` 而不是 `int`**:角色系统的 `null` 有**双重语义**(未识别 vs 组件主动拒绝),且组件内部异常也被吞成 `null`。桥接层必须把"读不到"这一态显式建模,让模式自己决定是兜底还是放弃。

### 8.4 角色事件合成:因为角色系统不发事件,所以我们合成(★v3.1:合成器住 `component/role`)

角色系统不发布任何 Bukkit 事件,所以模式**不可能**订阅"技能释放"。三种合成手段,按可靠性排序:

| 手段 | 信号来源 | 能拿到什么 | 线程 | 成本 | 适用 |
|---|---|---|---|---|---|
| **① 原版事件翻译** | `EntityDamageByEntityEvent` / `PlayerDeathEvent` / `ProjectileHitEvent` | 伤害事实、死亡事实、击杀归属(`lastDamagerUuid`) | 主线程(事件原生线程) | 极低 | **所有模式都该用**:计分、回合判定、Boss 仇恨 |
| **② 状态采样差分** | 每 N tick 对参赛者调 `RoleStateAccess`(energy / sante / buffs) | 能量/理智值的**变化**(不是变化原因) | 主线程(采样必须主线程) | 低(N=5~10,人数 × 4 次字符串调用) | 需要"能量耗尽""理智崩溃"这类**状态型**触发 |
| **③ 待推动的角色系统改动** | 角色系统新增公开事件通道 | 精确的"技能 X 被 C 施放" | — | — | 若模式必须精确感知技能。**需推动角色系统在 `RoleAPI` 冻结面之外新增事件出口**(`RoleApiSurfaceTest` 只冻结 `RoleAPI`,新增独立事件类不受其约束) |

> **★v3.1:事件类型与合成逻辑住 `component/role`,不住桥接。** 原因是两条分层纪律夹出来的:①`RoleKillEvent` 若定义在 `bridge/role`,模式规则(如 §5.2 的 `ev.is(RoleKillEvent.class)`)就没法 import 它——★23 只放行 `component/role` 触碰桥接;②若定义在 `engine/event`(v3 的做法),引擎就认识了"角色"这个内容词汇。唯一同时满足两边的位置是 `component/role`:它是桥接的消费面、又是模式可见的 L3。桥接层退回到"纯原语供应商"。

```java
package com.shdf.match.component.role;   // ★v3.1:合成器随事件词汇一起,住在消费面

/**
 * 角色事件合成(RoleComponent 的无状态协作者,包私有):
 * 输入 = 原版事件 + RoleFacade 原语;输出 = 本包的 RoleKillEvent(实现引擎的 MatchModeInstanceEvent 开放根)。
 * 调用链:listener/RoleSignalListener(LOWEST)→ RoleComponent#onVanillaDeath → 本类 → 实例总线。
 */
final class RoleEventSynth {

    /** ① 读死前状态(必须在角色系统 NORMAL 清角之前,故监听器用 LOWEST)。 */
    static Optional<RoleKillEvent> onDeath(RoleFacade role, PlayerDeathEvent e, int tick) {
        Player victim = e.getEntity();
        UUID killer = role.lastDamagerUuid(victim);               // ★ 不是 getKiller()
        String victimRole = role.roleIdOf(victim.getUniqueId());  // 必须在角色系统 clearRole 之前读
        if (killer == null) return Optional.empty();              // 无归属(如摔死/箭矢)→ 不计分
        // 队伍上下文不带在事件上:消费者经 getComponent(TeamComponent.class) 自查(引擎/桥接不认识队伍)
        return Optional.of(new RoleKillEvent(killer, victim.getUniqueId(), victimRole, tick));
    }

    // ② 采样差分:"调度"(何时采、对谁采、快照存哪)在 RoleComponent#update(§9.4),
    //    本类只做"采一帧 + 差分"的无状态纯函数——防腐层不持有实例状态的纪律,沿用 v3。
    static List<MatchModeInstanceEvent> diffSample(RoleStateAccess state,
            Map<UUID, RoleSnapshot> lastSeen, Collection<Participant> who) { ... }
}
```

**采样成本核算**:20 人 × 每 5 tick × 3 次 `executeComponentOperation`。每次调用是一次 HashMap 查表 + 字符串解析,微秒级。20×3/5 = 12 次/tick,可忽略。**不要**做成每 tick 采样——那才是真成本。

### 8.5 数据与运行时分离

| 数据类别 | 归属 | 存放 | 谁写 | 何时落库 |
|---|---|---|---|---|
| 玩家当前角色 id | **角色系统权威** | 角色系统内存(本插件不缓存) | `RoleFacade#setRole/clearRole` | 不落库(角色系统重启即清,这是它的既定语义) |
| 玩家的角色**偏好**(上次选的谁) | 本插件 | MySQL `player_profile.settings` JSON | `PlayerPreferenceService` | 玩家离开 / 对局结束 |
| 本局角色 → 玩家的占用表 | **MatchModeInstance 运行时** | `RoleComponent`(组件内状态,§9) | `RoleComponent` | 不落库(实例关闭即弃) |
| 角色累计战绩 | 本插件 | MySQL `role_stats` | `StatsComponent` → `StatsFlusher` | 对局结束 + 定时 flush |

> **原则**:角色系统是"角色是什么/玩家当前是谁"的权威;本插件是"这局谁表现如何"的权威。两边都不缓存对方的权威数据,除非是只读快照(`RoleCatalog`)且明确标注 TTL。

### 8.6 模式如何请求改变角色系统的规则(例如"允不允许重复角色")

**机制 = 声明,不是命令。** 模式不写 `if (allowDuplicate) ...`,而是在 Builder 里给 `RoleComponent` 的 Spec 传一个 `RolePolicy` 值对象(纯数据),由该组件统一执行(执行骨架与生命周期见 §9,本章只定义数据形状)。

```java
package com.shdf.match.bridge.role;

/**
 * 模式对角色系统的「规则请求」。纯数据,是 RoleComponent.Spec 的构造参数,
 * 由 RoleComponent 的 Loadout facet 解释执行。
 * ★ 模式永远不直接调 RoleAPI 来做策略判断——策略只在这一处集中生效。
 */
public record RolePolicy(
        /** false = 同一角色全场唯一(含跨队),true = 允许重复 */
        boolean allowDuplicates,
        /** 每队可用角色池;空集 = 该队不限制(用全量目录) */
        Map<String, Set<String>> poolByTeam,
        /** 全局禁用列表(无论池子怎么写都不允许) */
        Set<String> globallyBanned,
        /** 必须在场人数达到此值后才允许选角(防单人偷跑) */
        int minParticipantsBeforeSelect,
        /** true = 选角只记录,**部署/复活时**才真正 setRole(旧插件即此口径) */
        boolean applyOnDeployOnly,
        /** true = 死亡时立刻 clearRole,重生再 setRole */
        boolean clearOnDeath,
        /** 未选角的参赛者如何兜底 */
        AssignmentStrategy autoAssign,
        /** 每个玩家整局内可换角色的次数上限(-1 = 不限) */
        int maxReselectsPerPlayer
) {
    public enum AssignmentStrategy { NONE, RANDOM_AVAILABLE, FIRST_AVAILABLE, BALANCED }

    /** 大厅/无角色模式的"不介入"策略——组件直接不挂,这里只是显式表达。 */
    public static final RolePolicy NONE = new RolePolicy(
            true, Map.of(), Set.of(), 0, false, false, AssignmentStrategy.NONE, -1);
}
```

三个竞技模式的声明示例(常量在各自工厂里;Spec 冻结后跨模式共享安全,照抄角色系统 Spec 语义):

```java
// 炸弹攻防:不允许重复,按队各有池子,部署时才应用,死亡即清
private static final RolePolicy BOMB_POLICY = new RolePolicy(
        /* allowDuplicates */ false,
        /* poolByTeam */ Map.of("ATTACKER", Set.of("red", "canglu"),
                                "DEFENDER", Set.of("sinThorn", "remoteness")),
        /* globallyBanned */ Set.of("selfUpdateExample"),
        /* minParticipants */ 4,
        /* applyOnDeployOnly */ true,
        /* clearOnDeath */ true,
        /* autoAssign */ AssignmentStrategy.RANDOM_AVAILABLE,
        /* maxReselects */ 1);

// 团队死斗:允许重复,全员池,复活即应用(快速迭代手感)
private static final RolePolicy TDM_POLICY = new RolePolicy(
        true, Map.of(), Set.of(), 2, false, false,
        AssignmentStrategy.FIRST_AVAILABLE, -1);

// 首领战:强制指定角色(保证 Boss 机制可解),禁用换角
private static final RolePolicy BOSS_POLICY = new RolePolicy(
        false, Map.of("RAIDERS", Set.of("meiqihezi", "sinThorn")), Set.of(),
        3, true, false, AssignmentStrategy.NONE, 0);

// 大厅:不挂 RoleComponent——"不介入"的表达就是不声明,而非挂一个 NONE 策略的组件
```

> **回答"模式如何请求改变角色系统的规则"**:模式只**声明** `RolePolicy`,不写判断。加一个新模式若需要新规则,是给 `RolePolicy` 加一个字段(一处),所有模式共用同一套执行逻辑(一处,住在 `RoleComponent`)。v2 的 `RoleLoadoutComponent` 执行骨架已并入 §9.3/§9.4,本章不再重复。

### 8.7 模式如何通过 RoleAPI 介入角色行为

| 介入面 | 手段 | 例子 | 线程 |
|---|---|---|---|
| **改角色数值** | `RoleStateAccess` → `executeComponentOperation` | 炸弹拆成功后给拆弹者 `addEnergy(+20)`;Boss 每阶段给全员 `gainSanTe(10)` | 主线程 |
| **给角色上状态** | `RoleStateAccess#applyBuff`(`buffs` 组件) | 团灭倒计时中给玩家施加沉默 | 主线程 |
| **影响角色可用性** | `RoleComponent` + `RolePolicy`(Spec 构造数据,§9) | 首领战锁定角色池 | 主线程(GUI 交互链) |
| **响应角色后果** | 订阅 `RoleKillEvent` / `RoleStateChangedEvent`(§8.4 合成) | 击杀计分;能量归零触发"力竭" | 主线程 |
| **权限/敌对判定** | `RoleFacade#areHostile(a, b)`(数据源 = 阵营组件操作 `hostile <uuid>`,★ **非对称**:在 **a 的实例**上判) | 决定是否友伤、是否计分 | 主线程 |
| **造成伤害** | ★ **走原版 `LivingEntity#damage(...)`**,由角色系统的 `DamageHookListener` / `DamageTrackerListener` 统一结算 | Boss 的 AoE 伤害、陷阱伤害 | 主线程 |
| ❌ 不做 | 监听角色系统内部组件监听器 | 那些 `addListener` 的 `owner` 必须是 `RoleComponent`,跨插件拿不到实例 | — |
| ❌ 不做 | 自己写第二套伤害管线 / 缓存角色数值 | 会与角色系统的权威状态漂移 | — |

> ★v4 硬边界:**会话级组件(`SessionComponent`)同样不得接触 `bridge/role`;角色接入唯一落点仍是 `RoleComponent`(实例级)。**

### 8.8 ★ Capability 与软依赖(v2 新增,落实 A2 修订)

v1 是 `depend` 硬依赖:角色插件缺席 → 本插件拒绝启用。这对"对局引擎"合理,对"通用框架"不合理——**大厅与未来的无角色模式不该陪葬**。v2 机制:

```java
package com.shdf.match.engine.session;

/**

### 8.9 监听器骨架:`RoleSignalListener`(自框架侧 12-代码骨架 §12.2 迁入,原文完整)

// ═══════════════════════════════════════════════════════════════
// listener/RoleSignalListener.java —— ★ 优先级是正确性的一部分;监听器只路由,不合成
// ═══════════════════════════════════════════════════════════════
package com.shdf.match.listener;

public final class RoleSignalListener implements Listener {

    private final SessionService sessions;

    /**
     * ★ 必须 LOWEST。
     * 角色系统的 PlayerListener#onPlayerDeath 在 NORMAL 会上 clearRole,
     * 若我们在 NORMAL 之后读 roleIdOf(victim),拿到的一定是 null(角色已被清)。
     * 想读"死前是谁",只能在它之前。★v3.1:合成逻辑在 RoleComponent(v3 的 RoleEventSource
     * 已并入 component/role,§8.4)——本监听器只把事件路由给它。
     */
    @EventHandler(priority = EventPriority.LOWEST, ignoreCancelled = true)
    public void onDeath(PlayerDeathEvent event) {
        sessions.sessionOf(event.getEntity().getUniqueId())
                .flatMap(Session::currentInstance)
                .map(i -> i.component(RoleComponent.class))
                .ifPresent(role -> role.onVanillaDeath(event));   // 合成 RoleKillEvent → 实例总线
    }
}
```

### 8.10 与角色系统 `RoleAPI` 的对照表(桥接层实现清单;自框架侧 16-路线图与验收 §16.3 迁入,原文完整)

**（一）`RoleAPI` 冻结面:14 个方法**

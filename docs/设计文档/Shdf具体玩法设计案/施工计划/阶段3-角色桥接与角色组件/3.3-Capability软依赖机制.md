## 目标

本子阶段结束后,框架对角色系统正式是**软依赖**:

- `CapabilityRegistry`(引擎侧纯机制,字符串标签)上线;词汇 `"role"` 由桥接层注册,**引擎零字面量**(§8.8);
- 角色插件中途装/卸(PlugMan 类操作)能动态刷新注册表并失效 RoleFacade 缓存(§8.8"动态感知"行);
- `strict.require-role: true` 的服主可恢复"缺角色即拒启用"旧行为(§8.8 strict 行);
- 切换阶段能力校验接线完成:`"role"` 缺席时大厅照常、需它的模式开局被拒,detail 列缺失标签(§16.2-★21);
- `plugin.yml` 为 `softdepend: [ShadowHunterRolesPlugin]`(§8.8 表第 1 行)。

## 施工步骤

1. **建 `CapabilityRegistry`(引擎侧,纯机制)**。
   - 文件:`src/main/java/com/shdf/match/engine/session/CapabilityRegistry.java`(§12.1 包结构;§8.8 代码骨架)。
   - `public final class`;内部 `Set<String> available = ConcurrentHashMap.newKeySet()`(§8.8)。
   - 三方法:`Set<String> available()`(返回不可变视图)、`void register(String tag)`、`void unregister(String tag)`(§8.8)。
   - 边界行为:重复 register 同一标签幂等;unregister 未注册的标签静默返回;标签串 trim、空串拒绝(机械防御,注册方是受信代码,口径从宽)。
   - **不含任何具体标签、不含 "role" 字面量**——未来接经济插件就是 L1/第三方注册 `"economy"`,引擎零改动(§8.8 javadoc)。
   - 调用方契约写进 javadoc:L1/第三方在**启动时**与 ServiceRegisterEvent/ServiceUnregisterEvent 时调(§8.8 register 行注释)。
   - **★v4.1 注(18-v4.1修正案 §8、§4-§8.8 语义扩注):能力标签注册者扩为三类——L1 / 第三方插件 / 服务(seal 期注册,随 `ServiceRegistry#shutdown` 摘除);机制与字符串口径不变,本步骤三方法签名不动。**

2. **桥接层补两个成员**。
   - 文件:`src/main/java/com/shdf/match/bridge/role/RoleFacade.java`(3.1 已建,追加,不动既有 14 方法):
     - `public static final String CAPABILITY_ROLE = "role";`——标签词汇的唯一权威住桥接层(§8.8 register 行:"常量定义在 bridge/role";§8.8 strict 行:"经 bridge/role 暴露的常量,引擎零字面量");
     - `public static boolean handles(Class<?> service)`:返回 `service == RoleAPI.class`——给服务事件过滤用,把 `RoleAPI` 类型引用继续封在桥接内(维持 ★3:全仓只有 bridge/role 依赖 `com.shadowHunterRolesPlugin`)。
   - 注册规则一句话写进 javadoc:**`"role"` 标签可用 ⇔ `RoleFacade.available()`(= ServicesManager 能 load 到 RoleAPI)**(§8.8 register 行)。

3. **建 `CapabilityListener`(监听器层,零桥接依赖)**。
   - 文件:`src/main/java/com/shdf/match/listener/CapabilityListener.java`(§15.1 优先级表已列此监听器;§12.1 的 listener/ 清单未列它,归 listener/ 包与 §12.1 不冲突)。
   - `implements Listener`;构造注入两个 `Consumer`(由 L0 装配时传入):
     - `@EventHandler(priority = NORMAL)` `onServiceRegister(ServiceRegisterEvent e)` → `onRegistered.accept(e)`(§15.1:NORMAL、不 ignoreCancelled);
     - `@EventHandler(priority = NORMAL)` `onServiceUnregister(ServiceUnregisterEvent e)` → `onUnregistered.accept(e)`。
   - 本类 **import 里不得出现任何 bridge/role 与角色插件类型**(★23/★3 守门前提);"这是不是角色 API 的服务"由 L0 回调里调 `RoleFacade.handles(e.getProvider().getService())` 完成。
   - ServiceRegisterEvent/ServiceUnregisterEvent 是**全量服务事件**(任何插件注册任何服务都发):回调体第一行就是廉价过滤(`handles`),未命中立即返回——不做任何重活(§15.1"监听器不做重活"行)。

4. **L0 装配与动态刷新**。
   - 文件:`src/main/java/com/shdf/match/SHDFMatchPlugin.java`(阶段1/2 主类,onEnable 内追加;L0 允许依赖 L1/L2,§1.2 L0 行):
     - 构造 `RoleFacade` 与 `CapabilityRegistry`(进程级各一);
     - 启动探测:`if (facade.available()) registry.register(RoleFacade.CAPABILITY_ROLE);`(§8.8 register 行:启动时调);
     - 注册 `CapabilityListener`,回调体:
       - onRegistered:`RoleFacade.handles(e.getProvider().getService())` 命中 → `facade.invalidate()` 后重新探测,可用则 `registry.register(CAPABILITY_ROLE)`(§8.8"动态感知"行:刷新注册表 + 失效 RoleFacade 缓存——缓存里可能是 null 占位,必须洗掉);
       - onUnregistered:`handles(...)` 命中 → `facade.invalidate()` + `registry.unregister(CAPABILITY_ROLE)`(同上)。
     - L0 接触桥接的装配点依赖与 ★23 字面形式的张力 → 见文末「待裁决问题」。

5. **`strict.require-role` 强校验分支**。
   - 文件:`SHDFMatchPlugin.java`(onEnable,放步骤 4 探测**之后**)。
   - 读 `config.yml` 的 `strict.require-role`(默认 false,§15.2 config 结构 strict 块)。
   - 为 true 且 `!registry.available().contains(RoleFacade.CAPABILITY_ROLE)` → `log.severe(...)` + `setEnabled(false)`——恢复 v1"缺失即拒绝启用"行为,给"全玩法都要角色"的服主(§8.8 strict 行)。
   - 为 false 且探测失败 → 只 WARN,照常启用(懒解析 + 动态感知兜着,§8.8)。

6. **切换阶段能力校验接线**。
   - 文件:`src/main/java/com/shdf/match/engine/session/SessionServiceImpl.java`(阶段2 产物;若阶段2 已留校验桩则替换桩,否则在准备阶段校验管线增设一条)。
   - 规则:`mode.meta().requiredCapabilities()` 中任一标签 ∉ `registry.available()` → 拒绝 `REJECTED_BY_TARGET_MODE`,detail 形如 `"模式 bomb_defusal 需要角色系统 ShadowHunterRolesPlugin"`(§8.8"开局校验"行原文口径);detail **列缺失的标签集合**(§0.5.3 拒绝码收缩行:细目走 detail,不占独立码)。
   - 引擎只做集合包含比较,不认识任何具体标签——"role" 字面量只存在于 bridge/role 与各模式的 meta 声明里(§8.8;§0.5.3 能力标签行)。
   - 拒绝后玩家仍在当前模式(大厅)收到明确提示,由既有拒绝路径承担(§8.8"开局校验"行末)。
   - 大厅的 `requiredCapabilities` 为空集 → 永远放行,**引擎不需要任何"lobby 特判"**(§8.8 大厅行;§2.3 MatchModeMeta)。
   - 自检问题清单(接线完逐条过):
     - 校验发生在**准备阶段**(世界复制之前还是之后,按阶段2 管线现状,不为此新建阶段);
     - 拒绝走 `REJECTED_BY_TARGET_MODE` 而非新码(§0.5.3 收缩口径);
     - detail 是纯数据(缺失标签集合),不含"去大厅吧"这类流程指令——去向由 defaultTransition 管(§2.3)。

7. **`plugin.yml` 改 softdepend**。
   - 文件:`src/main/resources/plugin.yml`。
   - 确认/改为 `softdepend: [ShadowHunterRolesPlugin]`(v1 是 `depend`;§8.8 表第 1 行;§12.2 plugin.yml 样例即此形状)。
   - 注释一行:softdepend 只保证"若它在,先于我加载",**不保证 onEnable 时它已注册服务**——这正是懒解析存在的原因(§8.8"RoleFacade 懒解析"行理由)。

8. **引擎零字面量核查**。
   - `grep -rn "\"role\"" src/main/java/com/shdf/match/engine/` → 必须零命中(★24 EnginePurityTest 内容词汇纪律在此的具体化)。
   - `grep -rn "com.shadowHunterRolesPlugin" src/main/java | grep -v "bridge/role"` → 仍零命中(★3 回归)。

## 关键实现要点

- **三层各管一段**(§8.8 表 + §9.5 分工行):
  - 引擎(`CapabilityRegistry`):只认字符串集合的交并,零内容词汇;
  - 桥接(`RoleFacade`):`"role"` 词汇与 RoleAPI 存在性的唯一裁判;
  - L0:只做装配与 strict 分支。
  - 任何一层越位(引擎写死 "role"、桥接读 config、L0 拼操作动词)都破坏"框架不认识内容"(§0.5.3)。
- **null 占位缓存必须失效**:3.1 的懒解析把"插件缺席(null)"也缓存了——插件中途上线时若不 `invalidate()`,Facade 永远看不到它。这就是 §8.8"动态感知"行把"刷新注册表"与"失效 Facade 缓存"并列为一条的原因。
- **为什么过滤逻辑放桥接的静态方法**:监听器若直接 import `RoleAPI.class` 判服务类型,★3 当场红;`RoleFacade.handles(...)` 让类型引用留在桥接内,监听器只依赖 JDK/Bukkit。
- **卸载语义从简**:ServiceUnregister 到来即注销标签并失效缓存;**正在运行的实例不追杀**——运行中实例的后续 RoleAPI 调用拿到 null,按 3.1"缺席不抛"语义降级;角色清场唯一闸是 `RoleComponent.stop`(§9.4),不在此新增兜底。
- **探测时机**:onEnable 时角色插件按 softdepend 应已加载,但不保证已注册服务(§8.8 懒解析行理由)——启动探测失败在 strict=false 时只 WARN,不算 fatal。
- **监听器只注册一次**(§15.1"监听器注册时机"行):不随切换/热重载反复 registerEvents。
- **词汇演进零成本是验收标准之一**:自问"明天接一个经济插件要改几处?"——答案必须是"经济方注册一个 `'economy'` 标签,引擎与桥接零改动"(§8.8 javadoc)。若接线方案需要引擎认识新标签名,方案错了。
- **strict 分支做成纯函数便于单测**:把"给定 available 集合与 strict 开关 → 是否停用"抽成无副作用判定,L0 只负责读 config 与执行停用——config IO 留在 L0,判定逻辑可离线测(§16.2-9 同款思路)。
- **启动顺序固定**:探测(strict 判定的事实基础)必须先于 strict 分支;CapabilityListener 注册先于潜能插件的 ServicesManager 注册窗口关闭——onEnable 内三行的先后次序写进注释。
- **detail 文案是给服主看的**:缺失标签的提示要落到"哪个插件没装"(§8.8"开局校验"行示例文案),不是干巴巴的标签名——拒绝发生在切换期,玩家只看到"模式暂不可用",诊断信息进日志。
- **大厅内涉及角色的活动自行降级**:§8.8 大厅行点名 `IdleActivitiesComponent` 的技能试放区类活动——那是阶段4/5 的组件职责,本子阶段只保证"注册表缺席时它查得到"这个机制面;别在大厅里预写角色分支。

## 陷阱与纪律

- **§14.22 软依赖时序**:本子阶段的存在意义——懒解析(3.1)+ 动态感知(步骤 3/4)+ strict(步骤 5)三件套逐条对应它的规避清单。
- **§14.21"大厅特判"反弹的反面**:大厅无需任何特判就能在角色缺席时可用——因为它的 `requiredCapabilities` 是空集(§8.8 大厅行)。若发现自己在引擎写 `if (lobby) skip`,即为越界。
- **§14.13 引擎不知内容**:能力校验是集合运算,不是 id 白名单;新增能力标签零改引擎(§8.8 javadoc)。
- **§14.6 调度**:本子阶段无周期任务;ServiceRegister/Unregister 是低频事件,回调体做廉价判断先行(§15.1"监听器不做重活")。
- **§14.1 线程**:ServiceRegisterEvent 在主线程派发,回调体无需调度;不引入异步。

## 测试与验收

测试类:`src/test/java/com/shdf/match/bridge/role/CapabilitySoftDependTest.java`(§12.1 测试树既有名字;离线,不起服):

1. **注册表机制**:`register/unregister/available` 基本语义;`available()` 返回视图,外部改不动内部集合;重复 register/unregister 幂等不炸。
2. **★21 机械部分**(§16.2-★21):构造 `requiredCapabilities={"role"}` 的假 meta 与空集 meta 各一:
   - 空注册表时:前者被"缺失标签 → REJECTED_BY_TARGET_MODE + detail 含缺失项"规则拒绝,后者(大厅形状)放行;
   - `register("role")` 后:前者放行;
   - `unregister("role")` 后:前者再拒(动态语义,§8.8 动态感知行)。
3. **`RoleFacade.handles`**:对 `RoleAPI.class` 返回 true;对任意其他类(`Plugin`、`Object`)返回 false。
4. **缓存失效联动**:假 Supplier 先回 null(缺席)→ `available()` 缓存 null → 注入真实现 → 模拟"注册事件回调"等价序列(invalidate + register)→ 再探测可得(§8.8 动态感知行)。
5. **引擎零字面量**:断言 `engine/session/CapabilityRegistry.java` 源文件不含 `"role"` 串(轻量源码断言;正式守门是 ★24 EnginePurityTest,持续验证)。
6. **strict 判定纯函数**:strict = true + 空注册表 → 停用;strict = true + 含 "role" → 放行;strict = false + 空注册表 → WARN 放行(§8.8 strict 行三态)。

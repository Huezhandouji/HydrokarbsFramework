# 3.2 类型化访问与策略数据件

> SHDF 玩法线;框架施工线见 ../../../施工计划/
> 对应设计案:§8.3 RoleStateAccess、§8.5 数据与运行时分离、§8.6 RolePolicy 与三策常量、§8.4 RoleSnapshot 差分帧;路线图:§16.1-P2;前置:3.1 完成(RoleFacade / RoleDescriptor / RoleFaction 已就位)。
> 引用口径注:「§8.x」= `../../08-角色桥接.md`;「§16.3」= RoleAPI 对照表(即 `../../08-角色桥接.md` §8.10,随其维护);「§16.1/§16.2」= `../../../16-路线图与验收.md`;「§14.x」= `../../../14-陷阱清单.md`。

## 目标

本子阶段结束后,桥接层补齐"数据件",角色系统终于可以被**安全地**读写:

- `RoleStateAccess`:字符串协议包成类型化 API——`null` 三重含义(未实现动词/无实例或拒绝/内部异常被吞,§14.14)被 `OptionalInt` 显式建模,**绝不抛**(§8.3);
- `RoleCatalog`:角色目录只读快照,**显式 TTL**(§8.5"只读快照且明确标注 TTL"原则);
- `RolePolicy` record:§8.6 全字段 + `AssignmentStrategy` + `NONE` 常量——模式对角色系统的"规则请求"纯数据;
- `BOMB_POLICY / TDM_POLICY / BOSS_POLICY` 三策常量:§8.6 示例值逐项落地,3.4 的 `RoleComponent.Spec` 直接以它为构造数据;
- `RoleSnapshot`:采样差分帧 record(§8.4 `diffSample` 签名中的载体)。

全部离线可测(复用 3.1 的假 RoleAPI 打桩)。

- 依赖 3.1:`RoleFacade`(operate / knownRoleIds / catalog)、`RoleDescriptor`、`RoleFaction`、假 RoleAPI 测试打桩手法。
- 依赖阶段1 的构建链(`build.gradle.kts` 已在 3.1 加过角色插件 testImplementation)。

  - §14.14(null 三重含义;`componentId` 支持 `energy#2` 下标消歧——桥接层提供带下标签名,**别让上层自己拼 `#`**);
  - §8.5(数据与运行时分离表:角色系统是"角色是什么/玩家当前是谁"的权威,本插件不缓存对方权威数据,除非只读快照且标注 TTL);

## 施工步骤

1. **建 `RoleStateAccess`**。
   - 文件:`src/main/java/com/shdf/match/bridge/role/RoleStateAccess.java`,`public final class`。
   - 字段:`private final RoleFacade role;`(构造注入,§8.3)。
   - 组件 id 常量:`ENERGY = "energy"` / `SANTE = "sante"` / `BUFFS = "buffs"`(§8.3;id 清单出处 §0.1 体检表"角色数据读写"行:`energy/sante/buffs/vitals/hotbarRender/tasks/faction`)。
   - 能量面(§8.3 逐条):`OptionalInt energy(UUID)`(payload `current`)、`OptionalInt setEnergy(UUID,int)`(`set v`)、`OptionalInt addEnergy(UUID,int)`(`add v`)、`boolean consumeEnergy(UUID,int)`(`consume v`)。
   - 理智面:`OptionalInt sanTe(UUID)`(`current`)、`OptionalInt setSanTe(UUID,int)`(`set v`)、`OptionalInt gainSanTe(UUID,int)`(`gain v`)。
   - buff 面:`boolean applyBuff(UUID,String buffType,int ticks)`——走 `buffs` 组件动词面;**动工前读角色系统 `BuffComponent#onOperationCommand` 的 javadoc 再写**(§8.3 注明动词表在那里,勿凭空猜)。
   - 下标消歧:每个读/写方法提供带 `int instanceIndex` 的重载,内部拼 `"energy#" + idx` 形式组件 id(§14.14:`energy#2` 语法;同 id 多份未给下标时角色系统拒并回 null)。**下标拼接只住这一层**。
   - 私有 `OptionalInt readInt(UUID, String componentId, String payload)`(§8.3 逐字):
     - `role.operate(...)` 回 `null` 或空串 → `OptionalInt.empty()`——★ 不抛、不给上层 NPE 的机会;
     - 非空串 `trim()` 后 `Integer.parseInt`;`NumberFormatException` → `empty()`。
   - 写型方法的成功口径:回非空串(**含 `""`**)即 true,`null` 即 false——`""` = 已识别无回值也是成功(§8.3 返回值三态)。
   - 类头 javadoc:**所有方法必须主线程调用**(会触碰玩家状态,§8.3)。

2. **建 `RoleCatalog` 只读快照**。
   - 文件:`src/main/java/com/shdf/match/bridge/role/RoleCatalog.java`。
   - 不可变 record:`(Set<String> roleIds, List<RoleDescriptor> roles, long fetchedAtMillis)`(§16.3(一)knownRoleIds/catalog 两行"缓存进 RoleCatalog"口径;「角色目录只读快照」定义见 §8.5/§9.4——框架侧 01 自 v1.0 起已无 RoleCatalog 行,本线 08/09 为定义所在)。
   - `static RoleCatalog fetch(RoleFacade role)`:经 `role.knownRoleIds()` + `role.catalog()` 取;入参做防御性拷贝(`Set.copyOf` / `List.copyOf`)。
   - `boolean isExpired(long ttlMillis, long nowMillis)`:纯函数判过期。
   - 常量 `DEFAULT_TTL_MILLIS = 30_000`:**显式标注**(§8.5 原则原文"只读快照(RoleCatalog)且明确标注 TTL");数值设计未定,施工取 30s,消费方(3.4 awake)可传参覆写。
   - 纪律:快照无任何写口;刷新 = 重新 `fetch` **整体替换**,不做增量(§8.5)。

3. **建 `RolePolicy` record**。
   - 文件:`src/main/java/com/shdf/match/bridge/role/RolePolicy.java`。
   - 八个组件,字段名与 §8.6 逐字一致:
     - `boolean allowDuplicates`(false = 同一角色全场唯一含跨队);
     - `Map<String, Set<String>> poolByTeam`(每队可用池;空集 = 该队不限,用全量目录,§8.6);
     - `Set<String> globallyBanned`(全局禁用,无论池子怎么写都不允许);
     - `int minParticipantsBeforeSelect`(在场人数达标才许选角,防单人偷跑);
     - `boolean applyOnDeployOnly`(true = 选角只记录,部署/复活才真正 setRole);
     - `boolean clearOnDeath`(true = 死亡立刻 clearRole,重生再 setRole);
     - `AssignmentStrategy autoAssign`(未选角者的兜底策略);
     - `int maxReselectsPerPlayer`(整局换角上限;-1 = 不限)。
   - 内嵌 `enum AssignmentStrategy { NONE, RANDOM_AVAILABLE, FIRST_AVAILABLE, BALANCED }`(§8.6)。
   - 静态常量 `RolePolicy NONE = (true, Map.of(), Set.of(), 0, false, false, NONE, -1)`(§8.6:大厅/无角色模式的"不介入"策略——组件直接不挂,这里只是显式表达)。
   - record 零行为——策略的解释执行全在 3.4 的 Loadout facet(§8.6:"模式永远不直接调 RoleAPI 来做策略判断")。

4. **建三策常量持有类 `RolePolicies`**。
   - 文件:`src/main/java/com/shdf/match/component/role/RolePolicies.java`(`public final class`,私有构造)。
   - 三个 `public static final RolePolicy`,值逐项照抄 §8.6 示例:
     - `BOMB_POLICY`:`allowDuplicates=false`;`poolByTeam={ATTACKER→[red, canglu], DEFENDER→[sinThorn, remoteness]}`;`globallyBanned=[selfUpdateExample]`;`minParticipants=4`;`applyOnDeployOnly=true`;`clearOnDeath=true`;`autoAssign=RANDOM_AVAILABLE`;`maxReselects=1`。
     - `TDM_POLICY`:`true, Map.of(), Set.of(), 2, false, false, FIRST_AVAILABLE, -1`(允许重复/全员池/复活即应用,§8.6"快速迭代手感")。
     - `BOSS_POLICY`:`false, {RAIDERS→[meiqihezi, sinThorn]}, Set.of(), 3, true, false, NONE, 0`(锁定池/禁换角,§8.6"保证 Boss 机制可解")。
   - **为什么住 `component/role` 而非模式工厂或 bridge**:§16.2-★23 的 ArchUnit 规则禁止 `component/role`、`bridge/role` 之外任何类依赖 `bridge/role`——模式工厂(阶段5/6)import `bridge/role.RolePolicy` 即红;`component/role` 是唯一既被模式合法 import、又合法依赖桥接的位置(模式将来只 `import com.shdf.match.component.role.RolePolicies`)。此处理与 §8.6"常量在各自工厂里"的散文表述存在机械冲突 → 已列文末「待裁决问题」。
   - 大厅**不挂** RoleComponent——"不介入"的表达是**不声明组件**,而非挂一个 NONE 策略(§8.6 末行;§9.6 接入矩阵大厅列)。

5. **建 `RoleSnapshot` 采样帧**。
   - 文件:`src/main/java/com/shdf/match/bridge/role/RoleSnapshot.java`。
   - record 两字段:`(OptionalInt energy, OptionalInt sanTe)`。
   - 出处:§8.4 `diffSample(...)` 签名里的 `Map<UUID, RoleSnapshot> lastSeen`;§9.2 状态唯一行"采样快照(`uuid → RoleSnapshot`)住本组件"。
   - buffs **不入帧**:§8.3 未提供 buff 的类型化**读**口(只有 `applyBuff` 写);未来角色系统给出读动词时在此扩字段——桥接只改一处。

6. **构建与分层验证**。
   - `.\gradlew.bat build`:新四类编译通过。
   - `bridge/role` 内无任何新增对 `engine/**`、`component/**` 的依赖(L1 纪律,§1.2:桥接禁止依赖 L3/L4)。
   - `RolePolicies` 在 `component/role`,依赖方向是它 import 桥接——合法(★23 豁免包)。

## 关键实现要点

- **OptionalInt 是语义不是便利**:角色系统 `null` 有三重含义(§14.14),`""` = 已识别无回值(§8.3)。桥接把"读不到"显式建模,由消费方决定兜底还是放弃——**抛异常或回哨兵 -1 都是把三重含义压扁成一种**,必炸(§14.14 后果:某角色没实现某动词 → 对局崩溃)。
- **字符串动词面只存在于本层**:组件 id 与动词 token(`current/set/add/consume/gain`)全收进私有常量;3.4 的 facet 只见 `energyOf()` 这样的类型化方法。grep 纪律:`grep -rn "\"energy\"\|\"sante\"" src/main/java --include=*.java` 只允许 `bridge/role` 命中。
- **RoleCatalog 与 RoleFacade 的分工**:Facade 是"怎么问"(无状态翻译),Catalog 是"答案存多久"(带 TTL 的只读快照)。快照过期只影响**目录展示类**消费(选角 GUI 列表);**玩家当前角色/能量永远现问不走快照**(§8.5 表第 1 行:本插件不缓存)。
- **三策常量冻结共享**:record 不可变 + `Map.of/Set.of` 天然只读,同一常量被多个模式的 Spec 引用安全(§8.6:"Spec 冻结后跨模式共享安全,照抄角色系统 Spec 语义";共享行为由 3.4 的 `RoleComponentPolicyTest` 验证)。
- **poolByTeam 的键是队伍 id 字符串**(如 `ATTACKER`),值是角色 id 集合;键词汇随队伍组件的模式声明走,桥接层不认识任何具体队伍 id(内容盲,同 §14.12 纪律)。
- **TTL 常量是文档化承诺不是摆设**:每个用到快照的地方必须写明"数据可能滞后 ≤ TTL",这是 §8.5"明确标注"的含义。
- **下标消歧是角色系统的既有协议,不是新发明**(§14.14;RoleAPI javadoc):同 id 命中多份而未给下标 → 角色系统拒并回 null,**绝不静默取第一份**——桥接提供带下标签名就是为了让消费方能显式表达"我要第 N 份",而不是被静默拒绝后排查半天。
- **`RoleSnapshot` 放 bridge 而非 component**:它出现在 `RoleStateAccess`(bridge)的方法面与 `diffSample` 签名里,是桥接词汇;§12.1 的包结构表也把它列在 `bridge/role`(持有者是 3.4 的组件——形状在桥接、状态在组件,两句话不矛盾)。
- **`consumeEnergy` 的返回口径别聪明**:它回 true 只代表"角色系统认识这条操作",**不代表能量真的扣够**——余额不足时角色系统的行为以它自己的组件语义为准,桥接不猜测、不补判断(§8.3 只定义协议层,§8.7"改角色数值"行同理)。

## 陷阱与纪律

- **§14.14 null 当异常处理**:本子阶段的核心规避对象;断言"绝不抛"要写进测试(见下);下标消歧签名由本层提供,上层禁止拼 `#`。
- **§14.22 懒解析时序**:`RoleStateAccess` / `RoleCatalog` 都只在被调用时经 `RoleFacade` 取数据,自身**不做任何启动期解析**。
- **§14.26 状态唯一**:快照(`RoleSnapshot`)的**持有者是 3.4 的组件**;本层 record 只定义形状,不持有任何按 uuid 的表(§9.2)。
- **§14.1 线程**:全部方法主线程;`RoleCatalog.fetch` 也在主线程(它调 Facade,Facade 全主线程,§8.8)。
- **§14.12 反弹预警**:三策常量的差异是**数据**;若发现自己在组件里写 `if (policy == BOMB_POLICY)` 即违规——策略差异应完全被 Loadout facet 的通用解释逻辑吸收(§8.6"声明,不是命令")。

   - 带下标重载 `energy(u, 2)` 断言组件 id 为 `"energy#2"`、无下标重载为 `"energy"`(§14.14);

   - `applyBuff` 透传组件 id `"buffs"`(动词面以 BuffComponent javadoc 为准,断言只锁组件 id 与不抛);

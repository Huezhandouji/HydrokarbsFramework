## 14. 设计陷阱与规避建议

> HydroKarbs MiniGame Framework · v1.3(现行;v1.2 于 2026-10-23 地图注册通道;v1.1 于 2026-10-23 框架独立插件化拆分与 API 面扩充;v1.0 于 2026-10-22 自 SHDFMatch 设计案 v4.1 剥离玩法重构;玩法实现见 Shdf具体玩法设计案/)
>
> 文档版本:v1.3(2026-10-25,框架基础设施瘦身——14.9 规避列加「write-behind 随持久化迁宿主线」注(21-D1);v1.2 于 2026-10-23 地图注册通道——追加 14.39;v1.1 于 2026-10-23 框架独立插件化拆分与 API 面扩充——追加 14.35~14.38 跨 jar 消费陷阱;v4.1 于 2026-10-21 进程级服务层与 ServiceRegistry;会话级组件层——两级挂载)。

### 14.1 ⚠️ 在虚拟线程 / 异步回调里碰 Bukkit API

**后果**:随机 `IllegalStateException: Asynchronous ...` / 数据损坏 / 偶发崩服(最难查的一类)。
**触发场景**:`CompletableFuture` 的回调默认运行在**完成它的那个线程**。你以为是"主线程续写",其实还在虚拟线程上。
```java
// ❌ 反面:applyStats 在虚拟线程上跑,里面一旦碰 player.setScoreboard 就炸
repo.load(uuid, modeId).thenAccept(stats -> applyStats(player, stats));

// ✅ 正面:显式回主线程
Threads.supplyThenOnMain(() -> repoBlockingLoad(uuid, modeId),
                          stats -> applyStats(player, stats),
                          err   -> log.warn("加载档案失败", err));
```
**规避**:`util/Threads` 是唯一的回程口;规矩:**"凡是方法名里有 `player`/`world`/`entity`/`inventory` 的调用,必须在 `Threads.runOnMain` 块里"**。

### 14.2 ⚠️ `onEnable` 里做阻塞 IO(DB 建池 / 迁移 / 拉数据 / 世界模板预复制)

**后果**:启动卡住 → Paper watchdog 杀服(默认 60s 无响应)。
**规避**:
1. Hikari `setInitializationFailTimeout(-1)`:只建池不建连,不阻塞;
2. 迁移/预热数据放 `AsyncExecutor`,用 `DatabaseState` 三态(`CONNECTING / READY / DEGRADED`)表达;
3. **会话系统在 `DEGRADED` 时照常工作**(内存模式),结算时跳过落库并打 WARN。绝不让"库不可用"变成"服务器不可用"。

### 14.3 ⚠️ 连接池大小按虚拟线程数设

**后果**:`maximumPoolSize(500)` → MySQL `Too many connections` / 服务端 OOM。
**概念纠正**:虚拟线程解决"阻塞等待时不占用平台线程",**不是**"可以无限并发 IO"。真正的并发上限由**连接池**决定。
**规避**:`maximumPoolSize = 10`;`AsyncExecutor` 的 `Semaphore` 背压。

### 14.4 ⚠️ 用 `player.getKiller()` 做击杀归属(SHDF 扩展线)

**后果**:击杀统计全错、连杀奖励不发、回合胜负判错。
**事实**:角色系统的击杀归属写在 PDC `LAST_DAMAGER_KEY` 上,**唯一正解是 `RoleAPI.getLastDamagerUuid(Player)`**。已知边界:箭矢/弹射物击杀不入账(可能 `null`);死亡时不清账(可能陈旧值)。
**规避**(双源交叉验证,v1 原样):
```java
UUID killer = role.lastDamagerUuid(victim);
boolean trusted = killer != null
        && !killer.equals(victim.getUniqueId())          // 排除自杀/陈旧值
        && ctx.participant(killer).isPresent()           // 必须是对局内玩家
        && victim.getLastDamageCause() instanceof EntityDamageByEntityEvent ede
        && ede.getDamager().getUniqueId().equals(killer); // ★ PDC 与原生归因一致才认

if (trusted) ctx.bus().publish(new RoleKill(killer, victim.getUniqueId(), victimRoleId, killerTeamId));
else         ctx.bus().publish(new ParticipantKilled(victim.getUniqueId(), null, victimRoleId, null, causeOf(victim)));
```

### 14.5 ⚠️ 在 `NORMAL` 优先级读"玩家死亡前的角色"(SHDF 扩展线)

**后果**:`roleIdOf(victim)` 恒为 `null`(角色系统的 `PlayerListener#onPlayerDeath` 在 NORMAL 会 `clearRole`)。
**规避**:读死前状态的监听器**必须 `EventPriority.LOWEST`**;只读取、不修改。

### 14.6 ⚠️ 每实例起一个周期任务 → 任务爆炸 + `onDisable` 漏取消

**后果**:任务数随会话/实例线性增长;重载后任务翻倍(倒计时跳秒、消息发两遍)。
**规避**:全局唯一 `EngineTicker`(一个 `runTaskTimer`)驱动全部会话与实例;"稍后执行"用一次性 `runTaskLater`,句柄登记在实例上,close 统一 cancel;`runTaskTimer` 初始 delay 必须 > 0(统一 `1L`)。

### 14.7 ⚠️ 跨局残留:结束清理写散在多处

**后果**:旧插件的著名事故——玩家下一局带着上一局的状态(创造模式、隐身、卡在重生队列)。旧插件靠"延迟 1 tick"绕过,把时序问题变成隐式约定。
**本设计的做法(v1 原样 + v2 结构性加固)**:
1. `MatchModeInstance#close()` 是**唯一**清场入口,`closed` 标志保证幂等;
2. 结束判定**不立即清场/切换**,只置 `ENDING`,由 ticker 在**下一 tick** 驱动——时序显式化;
3. 组件**逆序 detach**;
4. v2 加固:**实例的全部参与者状态(attrs/team/role 视图)随 close 整体销毁,结构上不可能漏**——旧插件"死亡流程继续往已结束对局写状态"这类事故,在新结构里连"已结束对局"这个对象都不存在了。
5. v4 扩展(D10):**跨局的合法落点有两个**——实例间数据仍走 `Handoff`(随 `close()` 全灭);**跨切换存活的会话级状态寄居会话级组件**(每会话一份,随 `dissolve` 全灭)。注意实例结束 ≠ 会话级状态清空:`close()` 不回收会话组件,把状态留给"下一局的 close/create 兜底"是新的残留通道——会话级组件清自己的状态,落点是 `stop()`(与 `start` 严格对称),别指望 `close()` 替你收拾。

### 14.8 ⚠️ 战绩每杀一人写一次库(写放大)

**规避**:`StatsFlusher` write-behind(§10.3.5;★v1.3:随持久化整体迁宿主线——本条对宿主自建持久化仍有效,框架基线无 DB 写入路径,21-D1);关键点(实例结束、玩家退出、`/stop`)主动 `flushNow()`。

### 14.9 ⚠️ 异步写入的进程退出丢失

**规避**:`drainAndShutdown(budget)` 有界(≤ 3s);UPSERT 幂等(`ON DUPLICATE KEY UPDATE`),"重放"安全。

### 14.10 ⚠️ 玩家可控字符串直接喂给 MiniMessage

**后果**:玩家名注入 `<click:run_command:...>` 样式/点击事件。
**规避**:**MiniMessage 是标记语言,不是模板引擎**。玩家数据一律 `Placeholder.unparsed(...)` 或 `MiniMessage.Preset.NON_INTERACTABLE`;只有服主配置文案允许解析标签。GUI 名称、击杀播报、BossBar、**大厅战报展示(含玩家名)是重灾区**。

### 14.11 ⚠️ DB 密码写进 `config.yml` 并提交进版本控制

**规避**:`config.yml` 只放环境变量名(`password-env: HYDROCARBS_DB_PASSWORD`),真实密码放 `plugins/HydroKarbs/secrets.properties`(.gitignore)。缺失 → `MEMORY_ONLY` + 醒目 WARN。

### 14.12 ⚠️ 阶段/规则里的 `if-else` 反弹

**后果**:实现时图省事写成 `if (ctx.phase().id().equals("LIVE")) {...}`,最终变成第二个旧插件。
**规避**:
1. 组件不按阶段 id 分支——"阶段就是行为",写成 `PhaseNode` 或注册在该阶段的 `Rule`;
2. 模式选择用数据:mode id → 配置对象,不是 `switch (modeId)`;
3. `EngineHasNoModeStringsTest`:断言 `engine/**` 与 `component/**` 源码不出现任何合法 mode id 字面量(**含 `lobby`**,§16.2-4)。

### 14.13 ⚠️ 让模式在 `engine` 里注册自己

**规避**:`ServiceLoader` + `META-INF/services`(jar 内)+ `ServicesManager`(跨插件);"零改引擎"可机械验证:新增模式的 PR diff 里不出现 `engine/` 路径。

### 14.14 ⚠️ 角色系统 `executeComponentOperation` 的 `null` 被当异常处理(SHDF 扩展线)

**后果**:`null` 有三重含义(未实现/不存在/内部异常被吞),`throw` 出去会让"某个角色没实现某动词"变成"对局崩溃"。
**规避**:桥接层一律 `Optional` / `OptionalInt`;注意 `componentId` 支持 `energy#2` 下标消歧——桥接层提供带下标签名,别让模式自己拼 `#`。

### 14.15 ⚠️ 表结构没有版本迁移

**规避**:`schema_version` + 追加式 `Migration`;**永不修改已发布的迁移**;迁移在虚拟线程执行;每个迁移一个事务。

### 14.16 ⚠️ 切换风暴(v2 新增)

**后果**:新模式的 EndCondition 立即又命中(配置错误:大厅 min=1 + 倒计时 0s),一秒切换几十次,日志刷屏、玩家被反复传送。
**规避**:`min-dwell-ticks`(默认 100)——驻留不足时,自动切换(来源①③)被拒并 WARN;外部 `force` 可豁免。测试:`SwitchStormGuardTest`。

### 14.17 ⚠️ 切换重入(v2 新增)

**后果**:某条 Rule / `onHandoff` / 组件回调里(直接或间接)调了 `switchMode`,切换发生在 close 的调用栈内,清场做到一半又被要求清场。
**规避**:①`SWITCHING` 状态期间一切切换请求 → `Rejected(SWITCH_IN_PROGRESS)`;②自动切换只能由 EngineTicker 在 `ENDING` 后的下一 tick 发起;③测试冻结:断言自动切换的调用栈必经 ticker。

### 14.18 ⚠️ 把 SessionMember 当 Participant 用(或反之)(v2 新增)

**后果**:在会话层读 `member.teamId()`(不存在)或在实例层把离开的成员当参赛者计分。
**规避**:两个类型的字段集刻意不同——**SessionMember 只有 uuid/连接态/时间;team/role/state 只在 Participant 上**。编译期就不会让你犯。写代码时自问:"这个数据应该活过切换吗?"该活 → 会话;不该 → 实例。

### 14.19 ⚠️ 世界句柄泄漏(v2 新增)

**后果**:切换/dissolve 抛异常时 `WorldPort.release` 没走到,世界副本越积越多,磁盘与内存双爆。
**规避**:release 一律放 `finally`;`WorldRefCountTest`:两个测试模式间循环切换 100 次后断言未释放句柄数为 0、`Bukkit.getWorlds()` 无残留副本。

### 14.20 ⚠️ Handoff 键冲突 / 类型漂移(v2 新增;★v3.1 修订:键随主人)

**后果**:两个模式用了同一个 `(namespace, name)` 传不同类型;或接收端 `get(KEY)` 拿到旧版本类型 → `ClassCastException`。另一类事故:把"玩法语义的键"定义进框架(v3 的 `HandoffKeys` 就是)——框架重新开始认识内容。
**规避**:①★v3.1:键的 namespace = 写入方自己的 id(模式 id / 组件 id / 第三方插件 id),**框架不写任何交接键、不保留任何命名空间**——`HandoffKeys` 已删除,标准键由其主人声明为公开常量(`VoteComponent.HANDOFF_RESULT`、`StatsComponent.LAST_SUMMARY`);②`Key<T>` 携带 `Class<T>`,`get` 时类型不符返回 `empty` 而非抛;③跨组件引用交接键常量是合法协作——Handoff 本就是跨模式通道,与 AttributeBag 的「不得写他人命名空间」(§14.26)是两回事。

### 14.21 ⚠️ "大厅特判"反弹(v2 新增)

**后果**:实现时图省事,在引擎/会话层写 `if (mode.id().equals("lobby")) return fallback;`——一旦写下去,"任何模式都能当 fallback"变成"只有大厅能",通用性开始腐烂。
**规避**:fallback 模式是**配置项**(`session.fallback-mode: lobby`),引擎按 mode id 查表,不认识任何具体 id;`EngineHasNoModeStringsTest` 把 `lobby` 列入禁词;`LobbyIsJustAModeTest` 断言 lobby 的切换路径与其他模式逐字相同(同一 `switchMode` 入口、同一状态机)。

### 14.22 ⚠️ 软依赖时序:RoleAPI 晚注册(v2 新增;SHDF 扩展线,见 Shdf具体玩法设计案/08-角色桥接.md)

**后果**:软依赖提供的能力若沿用 v1 的"构造期一次性查找并缓存"写法,加载顺序不利时构造直接抛异常,不需要该能力的模式(如 fallback 模式)也开不了——软依赖名存实亡。
**规避**:可选能力一律懒解析(首次调用才查找并缓存);`CapabilityRegistry` 监听 `ServiceRegisterEvent`/`ServiceUnregisterEvent` 动态刷新可用标签;启动期强校验只在服主显式开启 `strict.*` 开关时执行(该键属 SHDF 扩展线)。角色系统接入的完整实例(懒解析、动态刷新、`strict.require-role` 配置)见 Shdf具体玩法设计案/08-角色桥接.md §8.8。

### 14.23 ⚠️ 聚合根长出行为(v3 新增)

**后果**:实现某个新模式时发现"差一个小逻辑",顺手在 `MatchMode` 上加一个方法(`getSpawnBias()`、`isRoundBased()`、`adjustConfig(cfg)`……)——第一个方法是无害的,第三个方法出现时,模式又开始"实现接口"而不是"拼组件表",v3 的整个论证塌方。
**规避**:`AggregatePurityTest` 反射冻结 `MatchMode` 的公开方法集(§16.2-★22),新增方法直接测试红;code review 的唯一正确答案是"这个行为属于哪个组件?给它加 Spec 构造数据或新组件"。角色系统 `Role` 类已经验证过这条路:它连 `getFaction()` 都拒绝了(墓志铭见 §2.8-决断二)。

### 14.24 ⚠️ 引擎重新长出状态机(v3 新增)

**后果**:某个组件需要在"阶段切换时"做事,实现者觉得"引擎加一个 phaseChange 回调最方便"——一次妥协,`PhaseChain` 就从组件回流引擎,接着规则求值、胜负判定依次回流,最终回到 v2 的"引擎口袋里揣着玩法"。
**规避**:`EnginePurityTest` 源码扫描 `engine/**` 禁词:`Phase`、`Rule`、`WinCondition`、`EndCondition`、`Role`、`Team`、`Score`、`Objective`(§16.2-★24;★v3.1 扩充——v3 的引擎事件族里就长着 `PhaseChanged`/`RoleKill`,自己撞自己的禁词);组件要感知阶段,订阅 `PhaseChanged` 事件(PhaseComponent 发的,引擎只是转发者)或 `getComponent(PhaseComponent.class)` 直接协作——**两条路都不经过引擎**。

### 14.25 ⚠️ svc 服务集成员膨胀(v3 新增)

**后果**:`MatchModeInstanceServices` 出现第四个、第五个成员("顺手把显示的便利口转发进去吧""加个 role() 便利口吧")——服务集变成上帝上下文,组件对框架的全部依赖面失控,`ComponentServicesPort` 的三成员纪律作废(角色系统在这个 record 的 javadoc 里专门写了"不为它们增设成员"的警告)。
**规避**:成员封闭(3 个);`MatchModeInstanceServicesMembersTest` 反射冻结 record 组件集;想要领域能力就 `getComponent(XxxComponent.class)`——组件协作走组件,不走服务集。

### 14.26 ⚠️ 组件间绕过状态主人裸写(v3 新增)

**后果**:组件 A 直接往组件 B 的命名空间写 `AttributeBag`("我就改一个数")——状态出现第二个写者,「状态唯一」被打破,排查"比分为什么错了"时要在两个组件里找写点(这正是 v1 的老病)。
**规避**:①`AttributeBag#set` 校验命名空间 = 调用组件 id(开发期断言);②跨组件读写一律走状态主人的强类型读口(`getComponent(ScoreComponent.class).add(...)`);③ArchUnit 规则:组件 A 不得引用组件 B 的 `AttributeBag.Key` 常量(可见性收窄到包私有即可机械保证)。

### 14.27 ⚠️ 会话级组件缓存实例组件引用(跨切换悬空)(v4 新增)

**后果**:会话级组件在 `start()` 里 `currentInstance()` 拿到 `MatchModeInstanceAccess`(或经它顺路取到的实例组件)存进字段,切换后旧实例已 `close()`,字段还指向死对象——读阶段/计分拿到陈旧值;更隐蔽的一种:间隙里 `currentInstance()` 本就该返回 `empty`,缓存的旧值把这个"当前无实例"的合法状态吞掉,空场计时、会话看板这类会话级逻辑开始按幽灵实例决策。
**规避**:①`svc().self().currentInstance()` **现取不缓存**(D5):`MatchModeInstanceAccess` 与经它取得的实例组件引用都不得越过切换存进字段;②`empty` 覆盖两种合法情况——"无实例"与 `ENDING/SWITCHING` 间隙——一律按无实例分支处理,不要回落到字段里的旧值;③真要跨切换留存,留的是**会话级**状态(记在会话组件自己身上,`stop()` 清),不是实例组件的引用。

### 14.28 ⚠️ 把机制职责塞进会话组件(名册/世界/切换)(v4 新增)

**后果**:"会话行为可插拔"被读成"会话什么都可插拔"——名册登记、成员连接态、会话状态机、switchMode 两阶段与三级回退、WorldPort 引用计数被搬进会话组件。组件一旦 quarantine 停用(D9),失守的是**可靠性底线**(名册错/世界漏/切换不原子),而且会话级没有回退目标可退:实例级隔离还能 `end()` 兜底,会话级停用一个组件就是永久降级。
**规避**:①归属拿不准先走 **D7 两问**:"它坏了会话会失守底线(名册错/世界漏/切换不原子)吗?"(是 → 内核)、"服务器主想要另一种做法吗?"(是 → 组件);②**机制/状态权威/切换或交付算法的一部分/可靠性底线**一律留 `SessionService` 内核(名册数据结构与登记、成员连接态记录、会话状态机、switchMode 两阶段与三级回退、WorldPort 调用时点与引用计数、会话事件总线、dissolve 执行、min-dwell 防护);③会话组件只接**策略/裁决/聚合/展示**(空场解散为第一波,断线宽限/跨局累计/会话看板/容量裁决为候选)——内核向组件只提供端口与事件,组件向内核只经端口请求;④会话组件表**只由 L0 装配**,模式不得注册/增删(D4)——把会话组件当"模式兼容层",就已经在滑向本条。

### 14.29 ⚠️ 跨级裸写(会话组件直接改实例组件状态,或反向)(v4 新增)

**后果**:跨级查询拿到的是**只读授权**,一旦当写口用——会话组件直接改实例组件的阶段/计分,或实例组件直接改会话组件状态——「状态唯一」跨级失守:同一条数据出现第二个写者,排查"存活数/累计分为什么错了"要在会话组件与实例组件两处找写点(14.26 的老病,只是换到跨级);更糟的是会话组件在切换间隙/实例已 `close()` 时裸写,写进死对象。
**规避**:①跨级**只读**:实例组件 → 会话组件走 `svc().self().session()`(`SessionView#component`);会话组件 → 实例组件走 `currentInstance()` → `MatchModeInstanceAccess#component`;两侧 `attrs()` 的只读约定都只有 `get`;②跨级干预**只能走端口**:实例侧仍只有 `end()` / `switchTo()`,会话侧只有 `requestSwitch()` / `requestDissolve()`(D8);事件是通知,不是写通道;③"只读"是**架构纪律 + code review 条款**(无法机械强制;实测需要再考虑 `MatchModeInstanceAccess` 返回包装视图,未决 §11-Q6);④会话 attrs 命名空间 = 组件 id(`"session"` 保留给内核),跨级往他人命名空间写与 §14.26 同级违规。**尾注(v4.1)**:跨级只读纪律同样约束服务(快照语义,见 14.31)。

### 14.30 ⚠️ 会话组件膨胀成上帝对象(每 tick 派发无豁免)(v4 新增)

**后果**:会话组件的 `update()` **每 tick 无条件派发**(与"当前是否有实例"无关,派发**无豁免**),于是有人把会话当"一个大组件"使:统计、看板、空场、容量、宽限全塞进一个组件——声明序被当成隐式初始化顺序;一个策略抛异常触发 quarantine,整块一起停用(D9 无法只停坏的那半);它还每会话一份、跨切换存活,膨胀物一路带着走,切模式也甩不掉。
**规避**:①按 **D7** 拆成多个会话级组件:策略、裁决、聚合、展示各归各的组件,各持自己的状态、各有各的 `stop()`;②组件间关系用 `requires` 显式声明,不要靠"我把两件事写在同一个 `update()` 里的先后"表达顺序——声明序 = 装配序是规格的一部分;③**派发无豁免**——别指望"我这个组件不需要 tick 就跳过",不需要做事就留空 `update()`(成本极低),重活放事件回调或 `later()`;④拆之前先过 D7 判据表:"需要跨模式存活吗"只回答了一半,第二问是"机制还是策略"——两问都过完再决定归属。

### 14.31 ⚠️ 服务缓存活实例/活组件引用跨切换(悬空)(v4.1 新增)

**后果**:服务是进程级常驻对象,活得比一切会话/实例都久。若在事件回调或快照拉取时把活实例/活组件的引用(快照里顺路取到的也算)存进字段,切换后旧实例已 `close()`,字段指向死对象——聚合、展示拿到陈旧值;更隐蔽的是,"当前无实例"的合法间隙会被缓存旧值吞掉,全局看板、配对队列开始按幽灵实例决策(14.27 的同款病,只是宿主从会话组件换成服务,悬空期从"到下次切换"延长到"到进程关停")。
**规避**:①服务触达会话只有三条通道(订阅 `SessionEventBus` / 只读快照 / 受控命令),快照通道的纪律是**只读快照、现取不缓存**——`MiniGameApi.sessions()` 的不可变 record 当场用完即弃,活实例/活组件引用(含经 `MatchModeInstanceAccess` 顺路取得的实例组件)一律不得跨切换存进字段(镜像 ★29"现取不缓存",14.27 同款禁令对服务生效);②真要跨切换留存,留的是**快照数据或聚合结果**(记在服务自己身上,`stop()` 与 `start` 严格对称地清),不是活引用;③事件订阅句柄在服务 `stop` 中注销,别让关停后的迟到回调继续往字段里写。

### 14.32 ⚠️ ServiceRegistry 长成上帝容器(install/get 之外塞方法)(v4.1 新增)

**后果**:注册表是全进程唯一的服务装配点,"顺手加一个方法"的诱惑最大——"加个事件转发吧""加个权限查询吧""加个配置读取吧"。第一个方法看似无害,第三个方法出现时,注册表已从装配容器变成进程级上帝上下文:消费面失控、职责不可测——14.25 的上帝服务集在注册表身上重演。
**规避**:①消费面**五方法封顶**:`install / seal / get / require / shutdown`,多一个都不行;②事件转发、权限查询、配置读取之类的扩需求一律**新独立机制**(事件走 `SessionEventBus` 与服务自身订阅,能力查询走 `CapabilityRegistry`,配置走 `ServiceEnv#cfg()`),不是往注册表塞方法;③code review 的唯一正确答案还是那个问题:"这个方法属于哪个既有机制?"——注册表只管"声明 → 校验 → 创建 → 关停"这一件事。

### 14.33 ⚠️ 把服务当第三级组件挂载 / 组件 import 服务(v4.1 新增)

**后果**:"服务也是常驻对象"被读成"那就挂进组件体系吧"——往组件描述符表加第三级,或让 `svc` 转发服务查询,或组件直接 import `engine/service/**` 图方便。任何一个得逞,A10"仅两级"与服务/组件的边界同时失守:`svc().components()` 查得到服务、五钩子开始派发给服务、组件对服务的依赖从装配面泄漏进类型面——服务一侧重构,组件全线编译错。
**规避**:①**服务不是第三级组件挂载级**:不进组件描述符表(`svc().components()` 查不到)、没有五钩子派发、不占 `tickAll` 任何一步;②**双向互不可见**(ArchUnit ★40):组件/模式不得 import `engine/service/**` 与 `service/**`,服务不得 import `mode/**` 与 `component/**`——双向冻结,反方向一样红;③组件要消费基础设施,走既有先例:**L1 适配器 + 包装组件**(RoleComponent 之于 RoleFacade 的同款;先例属 SHDF 扩展线,见 Shdf具体玩法设计案/08-角色桥接.md),不是加 svc 成员(★25 口径不变,14.25 同病)。

### 14.34 ⚠️ 服务间互 new 绕过注册表(v4.1 新增)

**后果**:某服务的工厂里图省事直接 `new` 另一个服务,不走 `env.dep(...)`——装配期依赖校验(缺依赖点名、依赖环检测、拓扑排序)全部被绕过,启动顺序退化成"谁先 install 谁可控",失败回滚不知道该停谁;等第二个服务也这么干,依赖图就只活在写者的脑子里,`ServiceDependencyException` 永远点不到名。
**规避**:①服务间依赖**只能经 `ServiceSpec#requires` 声明**、由注册表在 seal 期按拓扑序经 `ServiceEnv` 注入(`env.dep(Class)` 取到的依赖已保证就绪);②可选依赖用 `requiresOptional` 声明、`env.depOpt(...)` 取用(缺席 empty,不抛)——"可选"也是一种显式声明,不是"取不到再说";③禁止服务互 new:new 出来的对象不受注册表管理——不进拓扑序、不参与失败回滚、不摘能力标签。

### 14.35 ⚠️ 玩法插件把框架类 shade 进自己 jar(v1.1 新增)

**后果**:双引擎(两份 `EngineTicker`/两套注册表)、`ClassCastException`(跨 classloader 同名类不相等)、模式注册进错误注册表——跨 jar 场景下最难排查的一类事故。
**规避**:依赖纪律 = **compileOnly + 运行期 `depend: [HydroKarbs]`**;构建脚本断言消费方 jar 内无 `com.hydrokarbs.` 前缀类(消费方各用自有包根,宿主 = `com.shdf.*`,第三方伴随插件同理——与框架以 API 白名单解耦,不以包名从属,D13);CI 在打包期红,不留到运行期。

### 14.36 ⚠️ 未查 API_VERSION 就调用新面方法(v1.1 新增)

**后果**:运行期 `NoSuchMethodError`,崩在玩家路径上(入口牌子点击、看板刷新)——编译期因 compileOnly 全绿,事故只在特定版本组合的服务器上出现。
**规避**:玩法/伴随插件 `onEnable` **首行**检查:`api == null || api.API_VERSION < REQUIRED_API_VERSION` → SEVERE + `setEnabled(false)`(拒载不崩服,D7);CI 加"最低版本矩阵"编译样例(按声明的最低 API_VERSION 编译,防"顺手用了更新面");框架 `onEnable` 日志输出 API_VERSION,对每个注册的 Provider 记录其 `requiredApiVersion()`。

### 14.37 ⚠️ 服务经 `MiniGameApi` 调 `joinSession`/`leaveSession`,击穿三通道(v1.1 新增)

**后果**:服务获得"第四通道"——三通道(订阅事件/只读快照/受控命令)与"服务不经 `MiniGameApi`"的正交声明(D10)一旦被击穿,svc/端口纪律失效的先例一开,下一个服务就会直接订阅 API 事件、缓存 API 快照,14.31 的悬空病顺着新通道蔓延。
**规避**:①三通道条目原文保留 + D10 注(CONTEXT「服务↔会话三通道」):`joinSession`/`leaveSession` 扩大的是**外部调用方**阵营(命令/监听/伴随插件/玩法插件)的执行权,不构成第四通道——服务属外部调用方(切换来源②)仍走 `SessionService` 受控命令,不消费 `MiniGameApi`;②ArchUnit 增款(★40 增款):`engine/service/**` 与顶层 `service/**` 不得 import `api/**`。

### 14.38 ⚠️ 玩法插件 reload 后旧静态句柄残留(v1.1 新增)

**后果**:幽灵模式(注册表里留着已卸载插件 classloader 的 Provider)、重复事件(旧订阅句柄还挂在总线上)、句柄泄漏;PlugMan/运行期重载后症状随机出现。
**规避**:①订阅句柄(`EventSubscription`)、能力标签注册、模式注册只在**插件实例字段**中持有,`onDisable` 显式 close/unregister;②框架侧兜底:`PluginDisableEvent` 摘除该插件注册的全部模式/能力标签/provider 贡献,受影响会话走既有三级回退(D8,★47)——兜底不是免死金牌,残留句柄断言(★47)红了一样要修;③旧 Provider 的静态句柄必须随 disable 注销——静态可变状态本就是 12 §12.2-D12 禁项,这里是它在跨 jar 场景的复发面。

### 14.39 ⚠️ 地图注册的模板落盘时序错,或绕过 unregisterMap 强删磁盘模板(v1.2 新增)

**后果**:注册期"模板目录存在"校验形同虚设——注册先于解包(或运行期删/改模板),切换阶段 A6 `WorldPort.acquire` 到点才发现模板缺失:切换被拒(表面症状是"图莫名开不了局")或世界副本半态;绕过 `unregisterMap` 直接强删磁盘模板目录,注册表里留着幽灵地图,`api.maps()` 照常列出、选中即炸。
**规避**:①`onEnable` 固定顺序:**解包(`saveResource`)→ 构造 `MapDefinition` → `registerMap`**——注册期校验才有意义(20-D2/D3);②模板目录在地图注册期间视为框架托管物,宿主不得运行期改删——要换图就 unregister(正用拒绝是特性:图随会话打完自然退出)再注册新版;③摘除只走 `unregisterMap`(有会话正用 → 摘除被拒且点名会话,这是镜像 `/sm reload maps` 的既有纪律),强删磁盘不摘目录 = 幽灵地图。

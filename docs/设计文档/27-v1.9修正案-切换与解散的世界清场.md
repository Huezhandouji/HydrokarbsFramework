# 27 · v1.9 修正案:切换与解散的世界清场

> HydroKarbs MiniGame Framework · v1.9 修正案(历史存档,非现行;现行修正案见 [29-v1.11修正案-属性袋纯容器回归与声明词料三件退场.md](29-v1.11修正案-属性袋纯容器回归与声明词料三件退场.md);历史存档 17~26 见各文件)
> 变更指示(非设计章节):本修正案执行**世界清场的接缝收敛**——会话内切换地图时,立即把当前(旧)地图世界内所有**遗留人员**传送至对应地图出生点(REUSE_DIRTY 复用同一副本世界的情形同样传送);会话解散时,立即把地图世界内所有遗留人员传送至主世界出生点(与 `HydrokarbsAssembly#hubRelocator` 的目标口径同源)。**目的**:消除「世界内有玩家 → `Bukkit.unloadWorld` 返回 false → SEVERE + 目录保留」的路径,保证临时地图副本文件能如期清除(切换归零处置 / 解散 `discardSession`)。**术语裁定**:「对应地图出生点」= 目标地图副本世界的 `World#getSpawnLocation()`(v1.8 起 `MapDefinition` 无出生点字段);「主世界出生点」= 与 `hubRelocator` 同源;「遗留人员」= 物理位于该世界内的全部在线玩家(`World#getPlayers()`),**不以会话名册为界**——名册外滞留者正是当前清场失败的主因。决策记录见 [docs/adr/0015-world-clear-on-switch-and-dissolve.md](docs/adr/0015-world-clear-on-switch-and-dissolve.md)。
> 验收追加 **★65**(编号体系沿用 §16.2,只增不改不重排;框架/玩法两线同一套):世界清场——切换接缝(同世界先行 / 异图殿后)与解散接缝(先名册后世界)的注入点、时序与失败不阻塞(§5)。
> 基线:v1.8。本修正案为**内核接缝 + L0 平台函数注入,非破坏性**:公共面(`MiniGameApi`)零改动,`API_VERSION` 维持 **7**(§1-D4);`WorldPort`/`WorldPortImpl`/`WorldHandle`/`ResetStrategy` 与切换/会话/两级挂载/三通道等引擎机制零触碰。既有架构断言族(★1~★64)零放宽、冻结快照(★19/★44)零重录——新口落在 `SessionServiceImpl.Builder` 的函数注入面(非导出内部口),冻结面无涉。

## 0. 一页摘要

**变更(两条接缝、四条决策)**:

①**D1 归属 = 会话内核机制,不经 `WorldPort`**:世界清场是切换/解散算法的一部分(传送落点在 `executeB` 与 `dissolveNow` 的既有主线程路径上),不是世界端口的世界生命周期职责——`WorldPort` 面零改动(仍 `acquire`/`release`/`discardSession` 三法);平台语义(枚举世界内玩家、按出生点传送)经 `SessionServiceImpl.Builder` 新增两个 L0 函数注入口收敛:`worldClearer(BiConsumer<World, World>)`(切换清场)与 `hubWorldClearer(Consumer<World>)`(解散清场),沿用 `hubRelocator`/`safeStateCleaner` 的函数注入模式,落点 = `HydrokarbsAssembly`(铁律 6/9/10 不破)。

②**D2 切换时序裁决(显式,写入 §1)**:判据 = **`org.bukkit.World` 引用相等(`==`)**(明文语义,排除 `instanceName`/`WorldHandle.equals` 基准——REUSE_DIRTY 同世界归零后再获取经 `prepareCopyDir` 复载(`WorldPortImpl` `prepareCopyDir`)产生**新的** `World` 对象、引用必不等 → 正确走异图 B5 清场;引用相等只可能来自端口表命中同句柄(同图重开,计数不归零无卸载)——同图重开对 `REUSE_DIRTY` 与 `TEMPLATE_RESTORE` 一律成立,按策略分支是无解释分叉)。**同世界复用** → 新步 **B3.5**:清场**先行于 B4 组件摆放**(落点统一口径 = B3 合并之后、B4 造件之前的缝隙;若殿后到 B5 finally 会把 `startAll` 刚摆好的全员位次整体拽回出生点,自相矛盾);**异图切换** → 清场**殿后、紧贴释放接缝**:B5 finally 内、既有 `previousWorld != null` 守卫**之内**、`worlds.release` 之前,时序 = 完成事件(`ModeSwitchCompleted`/`future.complete`)之后、release 之前(事件订阅者可见同 tick 内事件派发时遗留人员尚未清)。两失败窗口如实登记(§1-D2,不得写「人仍留旧世界」一概而论)。

③**D3 解散合并 = 先名册后世界**:`dissolveNow` 既有结构内——名册成员传送(`hubRelocator`,try 内)先跑;新清场口在 finally 内、`WorldHandle heldWorld` 摘除(`replaceWorldHandle(null)`)之后、`worlds.discardSession(session.id())` 之前,`heldWorld` 非 null 时 `hubWorldClearer.accept(heldWorld.world())`。名册成员已被既有路径安置、清场只枚举世界内剩余人员(每人至多一次传送);任一失败均 WARN 不阻塞,finally 继续 `discardSession` → 归零卸载。目标口径:两函数与 `hubRelocator` 共用 L0 新抽的 `hubSpawn()`(主世界出生点单一来源)。

④**D4 best-effort 与公共面零改动**:清场失败 WARN 不阻塞切换/解散(沿用既有三级兜底语气),release/`discardSession` 照发;世界仍有人时既有 `disposeHandle`「`unloadWorld` false → SEVERE + 保留目录」原样保留为**最后防线**(23-D2 不被改写);`MiniGameApi` 冻结面 17 方法、`API_VERSION = 7` 零改动(本特性不经公共 API 暴露,★19/★44 零重录)。

**不动**:模式与组件无感(世界清场不经 svc 端口、不占组件钩子,组件跨局位置保留诉求自读 Handoff 坐标自理);`WorldPort` 三法/引用计数/复用窗口(★58)/`deleteCopyDir` 唯一删除口一寸不动;切换防护(§3.5 四闸)与三级回退(§3.2 末)零改动;★1~★64 断言零放宽(★65 为新增命题,§5);断线宽限期重连落位与 `safeStateCleaner` 覆盖面为非目标(§6 显式登记)。

## 1. 决策 D1~D4

### D1:归属 = 会话内核机制,不经 WorldPort(L0 函数注入)

**决策**:世界清场落在会话内核的切换/解散接缝上(与引用计数释放同一族——都是「切换/解散算法对世界面的收尾动作」);`WorldPort` 接口**零改动**,清场的平台语义(枚举 `World#getPlayers()`、`Player#teleport(出生点)`)经 `SessionServiceImpl.Builder` 两个新注入函数落 L0:

```java
Builder worldClearer(BiConsumer<org.bukkit.World, org.bukkit.World> worldClearer)   // 默认 no-op
Builder hubWorldClearer(Consumer<org.bukkit.World> hubWorldClearer)                 // 默认 no-op
```

生产装配(`HydrokarbsAssembly#assemble`)接线两行;离线测试默认 no-op,记录型假件经 `SwitchHarness` 注入(测试零 Bukkit **静态触碰**——类型签名引用 Bukkit 类型 + 动态代理占位/传 null 是既有先例(`FakeWorldPort#proxyWorld`);根 `README.md`「零 Bukkit import」措辞随本条同步为「零 Bukkit 静态触碰」,纪律不变)。

**理由**:①**判据同款「世界句柄泄漏会失守切换原子性底线」(§3.7 谁调用行)**——遗留人员不清,`unloadWorld` 返回 false,副本目录滞留、23 号销毁闭环被击穿;它是内核对世界面的职责,不是策略(两问:坏了会失守底线?是 → 内核机制);②铁律 9「世界只有 `WorldPort` 一个口」:本特性**不新增世界触点**——传送动作直接消费句柄已持有的 `World` 引用与目标世界引用,不开第二个口;塞进 `WorldPort` 反而把「玩家语义」混入世界端口并静默改写 23-D2 防线(备选否决,见 ADR-0015);③**函数注入模式既有先例**:`hubRelocator`/`safeStateCleaner`/`mainExecutor` 三口同款,L0 落点唯一(`HydrokarbsAssembly`),引擎零 Bukkit 静态触碰(`engine` import `org.bukkit.World` 有既有先例:`WorldHandle`/`EngineTicker`;★1 分层禁令只触 mode/component,不触)。

### D2:切换时序裁决(B3.5 同世界先行;B5 异图殿后;判据 = World 引用相等)

**判据(明文语义)**:`sameWorldReuse = current.world() == plan.world.world()`,其中 `current = session.worldHandle()`——比较基准是 **`org.bukkit.World` 引用相等(`==`)**,不是 `instanceName` 字符串相等、也不是 `WorldHandle.equals`(record 引用语义)。理由链:REUSE_DIRTY 同世界归零后再获取(切换离开归零保留目录),经 `prepareCopyDir` 复用目录复载产生**新的** `org.bukkit.World` 对象——引用必不等,判据判「异图」→ 走 B5 清场,**正确**(旧 `World` 对象内若有滞留者须清);引用相等只可能来自端口表命中同句柄(同图重开:同 (map, session) 键命中,计数 +1 不归零、无卸载无新 `World` 对象)——此时清的是**同一个**世界,先行清场才不与组件摆位自相矛盾。同图重开对 REUSE_DIRTY 与 TEMPLATE_RESTORE 一律成立(表命中在策略分派之前),按策略分支判「要不要清」是无解释分叉,不取。

**时序(两分支)**:

- **同世界复用 → B3.5 清场先行于组件摆放**:落点统一口径 = **B3 合并之后、B4 造件之前的缝隙**。清场对象 = 世界内全部在场者;若殿后到 B5 finally,`startAll` 刚摆好的全员位次会被整体拽回出生点——先行则组件其后摆位,终态正确。代价 = 名册成员同 tick 两次传送(客户端只见终态)+ **同图重开「原地起步 → 出生点起步」的冻结语义变更**(依赖跨局位置保留的组件须自读 Handoff 坐标自行传送——此为本变更必须走修正案流程的原因,风险段登记)。
- **异图切换 → 清场殿后、紧贴释放接缝**:B5 finally 内、既有 `if (previousWorld != null)` 守卫**之内**(首次切换 `previousWorld == null`,守卫外即 NPE)、`worlds.release` 之前;时序 = 完成事件(`plan.future.complete` / `ModeSwitchCompleted`)之后、release 之前——同 tick 内事件订阅者看到完成事件时遗留人员尚未清(§3.7「释放时机」行加注措辞)。理由:①组件先搬名册成员(B4 名册原地位移),清场只兜底名册外滞留者,每人至多一次传送;②清场与 `unloadWorld` 同 tick 顺序锁定,单 tick 原子不破。

**空值分支(防 NPE,与 dissolve 口同款)**:`current` 在 B5 换入前为 null(首次切换,含每次 `create` 的首切——句柄要到 B5 `replaceWorldHandle` 才写入)→ `current == null` → 跳过 B3.5;`sameWorldReuse = current != null && current.world() == plan.world.world()` 一次计算,供 B3.5 与 B5 finally 两处门闩(`!sameWorldReuse`)。

**两失败窗口(如实分述,不写「人仍留旧世界」一概而论)**:

| 窗口 | 时序实况 | 安全链 |
|---|---|---|
| ① B1~B4 失败(B4 造件/唤醒/生效抛) | 内层 try 未走完 → **B5 finally 未达**(清场与 release 都不发生)→ 人仍留旧世界;句柄未换入(`rollback` 不触句柄) | 回退切换自身的 B5 清场把旧世界内人员传往回退世界出生点;或解散 `hubWorldClearer` → `discardSession` 销毁。**殿后裁决避免「清场先行」在此窗口把人带进 plan.world 孤儿副本**(既有 catch → rollback 不触句柄) |
| ② B5 内层失败(落位/事件/complete 抛) | finally 清场**先于** catch → rollback 执行;此时句柄已换入(`replaceWorldHandle` 已过)——遗留人员已被清场带进 `plan.world`(非孤儿) | 回退切换自身的 B5 清场把 plan.world 内人员传往回退世界出生点;或解散 `hubWorldClearer` → `discardSession` 销毁。安全链仍闭合 |

**onWorldReady 的作废释放不挂清场口**:aborted 计划必未进 B4(`executeB` 先 `clearPendingSwitch`;`abortPending` 仅 pending 非空时生效),世界必空或即现行世界(计数未归零无卸载)——挂了也是空转,不挂。

### D3:解散合并 = 先名册后世界(单一来源 hubSpawn)

**决策**:`dissolveNow` 既有结构内——既有 `hubRelocator.accept(members)`(try 内,名册成员 → 主城)先跑;新清场口在 finally 内、`heldWorld` 摘除(`session.replaceWorldHandle(null)`)之后、`worlds.discardSession(session.id())` 之前,`heldWorld` 非 null 时 `hubWorldClearer.accept(heldWorld.world())`。合并方式(显式裁决):**「先名册后世界」**——名册成员已由既有路径安置,清场只枚举世界内剩余人员(遗留人员 = 名册超集的物理面),每人至多一次传送;`hubRelocator` 若抛(WARN 路径),清场口兜底接住仍在地图世界内的成员;清场口若抛,成员已被既有路径安置;任一失败均 WARN 不阻塞,finally 继续 `discardSession` → 归零卸载。`heldWorld` 为 null(如初始切换失败即解散)则清场口跳过、无害;回退二级解散(`FALLBACK_DISSOLVE`)与 onDisable `SHUTDOWN` 解散同走此口。目标口径:`hubWorldClearer` 与 `hubRelocator` 共用 L0 新抽的 `hubSpawn()`(主世界出生点单一来源,「与 `hubRelocator` 同源」的落法)。

**理由**:①解散的成员传送与清场是**两个覆盖面**(名册 ⊂ 世界内人员),两级覆盖合于「每人至多一次」且互为兜底——合并且有序(先名册后世界)而不是二选一;②接缝选在 `discardSession` **之前**:世界内还有人时 `discardSession` 的卸载必失败(SEVERE + 保留目录)——清场殿后于摘句柄、前置于销毁,正是把 23 号防线的触发概率压到零的顺序;③摘句柄先行(`replaceWorldHandle(null)` 既有)保证清场时句柄已不在会话上,清场失败不产生半持有态。

### D4:best-effort 与公共面零改动

**决策**:全部清场口经内核 `try/catch Throwable → WARN` 包裹(best-effort,沿用既有三级兜底语气),失败不阻塞切换/解散,`release`/`discardSession` 照发;世界仍有人时既有 `disposeHandle`「`unloadWorld` false → SEVERE + 保留目录」原样保留为最后防线(23-D2 防线不被本特性改写——清场把该路径的触发概率压到零,但防线本体一步不动)。公共面:`MiniGameApi` 冻结面 17 方法、`API_VERSION = 7` 零改动——本特性不经公共 API 暴露(无消费者诉求:清场是框架内部对副本卫生的收尾,宿主连句柄都拿不到);`WorldPort` 接口与 `WorldPortImpl` 行为零改动。

**理由**:①没有对外可观测的新能力,就没有公共面承诺可冻结(23-D3 同款判据);②★1~★64 断言零放宽——清场断言族(★65)落在 `SwitchHarness`/`ModeSwitchAtomicityTest` 既有挂点上,`WorldRefCountTest` 自建 Builder 不吃 `SwitchHarness`,默认 no-op 清场不触 ★17/★58 冻结断言。

## 3. 契约骨架(Builder 两法 + 三接缝伪码)

```java
    WorldHandle current = session.worldHandle();          // B5 换入前为 null(首切)
    boolean sameWorldReuse = current != null && current.world() == plan.world.world();
    if (sameWorldReuse) { clearWorldQuietly(current.world(), plan.world.world(), session.id()); }
    B4 next = mode.createInstance(...); next.awakeAll(); next.startAll();   // 组件其后摆位
    WorldHandle previousWorld = session.replaceWorldHandle(plan.world);
    try {
        落位;发 ModeSwitchCompleted;plan.future.complete(Succeeded);      // 完成事件在先
    } finally {
        if (previousWorld != null) {                                       // 首切 null:守卫内才安全
            if (!sameWorldReuse) {                                         // 同图重开已清,不重复
                clearWorldQuietly(previousWorld.world(), plan.world.world(), session.id());
            }
            worlds.release(previousWorld);                                 // 清场 → release 同 tick 锁序
        }
    }
} catch (Throwable t) { rollback(session, plan, t); }   // 两失败窗口见 §1-D2 表
```

```java
try {
```

## 2. 核心概念抽象

> HydroKarbs MiniGame Framework · v1.3(现行;v1.2 于 2026-10-23 地图注册通道;v1.1 于 2026-10-23 框架独立插件化拆分与 API 面扩充;v1.0 于 2026-10-22 自 SHDFMatch 设计案 v4.1 剥离玩法重构;玩法实现见 Shdf具体玩法设计案/)

> 文档版本:v1.3(2026-10-25,框架基础设施瘦身与配置中立化——21 号修正案;v4.1 于 2026-10-21,进程级服务层与 ServiceRegistry;会话级组件层——两级挂载)。

> 参照框注:本章纪律的参照物是宿主扩展线的一套已验证组件实现(参照关系属 SHDF 扩展线,见 Shdf具体玩法设计案/09-角色组件层.md),机制本身与宿主无关——正文各处"照抄角色系统 / Role*"均为这一参照关系的表述,不构成本框架的组成或依赖。

> 本章是 v3 的心脏。三句话先立住:
> **模式聚合根(MatchMode)零行为**——只有信息与组件声明(照抄角色系统 `core/Role` 的形状);
> **行为全部住在组件(MatchModeComponent)里**——svc 构造期注入、声明序派发(照抄角色系统组件基类,见参照框注);
> **引擎不提供玩法级状态机**——阶段/结束/规则是三个 L3 组件,引擎只提供端口。

### 2.2 逐个定义

| 概念 | 定义 | 生命周期 | 是否含逻辑 | 关键约束 |
|---|---|---|---|---|
| **MatchMode** | **模式聚合根**:id/名称/描述/图标/mapTags/MatchModeMeta(纯数据)+ 唯一有序组件描述符表 | 进程级,`Builder#build()` 后不可变 | ★**零**(仅 `verifyDependencies` 与 `createInstance` 两个装配方法) | 不持有任何玩家状态;**没有** plan()/rolePolicy()/transition()/validateMap() 这类行为方法——v2 有,v3 全部拆除(§0.5.2) |
| **MatchModeMeta** | 模式的元数据 record:`capabilities`(所需外部能力)/`recordsHistory`/人数窗/`defaultTransition`(★v3.2:`joinPolicy` 已下放为 `JoinControlComponent`,§3.2.1) | 随 Mode 不可变 | 无 | 全是数据;消费者是框架与组件,不产生行为 |
| **MatchModeComponent.Specification** | **装配描述符**:声明工厂、`requires`/`requiresOptional` 依赖类型、`providedType`(供给面)、`checkMap`(地图适配) | 装配期 | 仅装配逻辑 | `freeze()` 产出不可变 `Snapshot`,同一 Spec 实例被两个模式共享互不串改(照抄角色系统) |
| **ComponentEntry** | 描述符表里的条目:`(工厂, 描述符类型, 提供类型, 必需依赖, 可选依赖)` 快照 | 随 MatchMode 不可变 | 无 | 不持有 Spec 对象(只留快照)——照抄 `Role.ComponentEntry` |
| **MatchModeComponent** | **行为单元基类**:持有 id + svc(构造期注入),生命周期钩子 + 事件钩子 | 随 MatchModeInstance | 钩子体 | "基类不认识子类":不为任何具体组件设通用视图(照抄角色系统组件基类的纪律) |
| **MatchModeInstanceServices** | svc 服务集 record:`(self, components, modeInfo)` 三成员 | 随 MatchModeInstance | 无 | 成员封闭;新增成员须过设计审查(照抄 `ComponentServicesPort` 的 3 成员纪律) |
| **SessionComponent**(会话级组件) | ★v4 **会话级组件基类**:持有 id + svc(构造期注入),钩子 awake/start/update/onEvent/stop;`Specification` 经 `freeze()` 产出不可变 Snapshot | 随 Session(`create` → `dissolve`);★**每会话一份**、跨模式切换存活 | 钩子体 | 生命周期随会话不随实例;由**会话装配**声明,模式无权注册/增删;同一组件类不得兼任两级挂载(要跨级就拆两个组件,§2.8 决断一) |
| **SessionServices** | ★v4 会话组件的 svc 服务集 record:`(self, components)` 两成员 | 随 Session | 无 | **成员封闭**(2);构造期注入,四条件同实例级(§2.5.1) |
| **Session** | 跨模式常驻容器:**[内核]** 名册、连接追踪、世界句柄权威、会话状态机与切换编排;★v4 **[组件]** 会话的*策略与行为*(如空场解散)下放为**会话级组件**,挂在 Session 上 | `create` → `dissolve` | 有(编排,无模式语义) | 名册在切换时**原地位移**;一个玩家同一时刻至多属于一个 Session;★v4:会话容器**不持有**会话组件状态(§2.8 决断三) |
| **SessionPort** | ★v4 **会话自面**:会话级组件对内核的唯一入口——id/members/tick/attrs/events/currentInstance/later,加 `requestSwitch`/`requestDissolve` 两个行动口 | 随 Session | 无 | 镜像实例级 `MatchModeInstancePort`;★v4 新增的**唯一"组件影响力的面"** 只有这两个行动口(§2.8 决断四) |
| **SessionMember** | 会话级成员:uuid、连接态、加入时间 | 随 Session | 无 | **不含任何模式语义**(无 team/role/state) |
| **MatchModeInstance** | **一次模式运行的容器**:按描述符表造组件、按声明序派发、提供端口、回收登记资源 | `createInstance` → `close()`(幂等) | 有(编排,**不持有玩法状态**) | 「状态唯一」:team/score/进度/占用表全在组件里,容器按 id 现取(照抄 `RoleInstance`) |
| **MatchModeInstanceAccess** | ★v4 **会话侧只读实例面**:会话级组件查询当前实例(id/modeId/tick/participants/modeInfo/attrs/`component(s)`) | 随当前实例,**现取不缓存** | 无 | **只读**(无写口);无实例或 `ENDING/SWITCHING` 间隙 → `Optional.empty`;**不得缓存实例组件引用越过切换**(§2.8 决断四) |
| **SessionView** | ★v4 **实例侧只读会话视图**:实例组件查询会话(id/members/attrs/`component(s)`)——模式接入会话能力的**软接入**口 | 随 Session | 无 | **只读**;不得订阅会话事件(第一版,未决);硬依赖走 `requiredCapabilities` 标签 |
| **Participant** | 成员在某次实例内的视图:uuid、生命周期标记、实例 attrs | 随 MatchModeInstance | 无 | team/role 归组件所有,经持有该状态的组件强类型读口查询(队伍归 `TeamComponent`;SHDF 的角色状态归其角色组件——属宿主扩展线,见 Shdf具体玩法设计案/09-角色组件层.md)——Participant 上不再有这些字段(v2 有,v3 拆除) |
| **Handoff** | 模式间交接的类型化载荷 | 一次切换 | 无 | 命名空间 = 写入方自己的 id(模式 id / 组件 id);★v3.1 框架**不写任何交接键**(HandoffKeys 已删,键随主人,§3.3);组件经 `onHandoff(Builder)` 写、经 `svc().self().handoff()` 读 |
| **EndResult** | 结束请求:★v3.1 **仅携带可选去向**(`Optional<TransitionIntent>`)——引擎的结束货币只有「下一站」,没有「剧情」 | 一次结束 | 无 | 唯一货币;`svc().self().end(result)` 是实例结束的**唯一**请求口;胜负/原因等结局词汇归内容层 `MatchOutcome`(§3.4) |
| **EndCondition** | 返回 `Optional<GateVerdict>` 的判定器(纯接口,数据);`GateVerdict = MatchOutcome(结局) + 可选 TransitionIntent(去向)` | 随 EndGateComponent | 纯函数 | **归 L3 的 `EndGateComponent` 持有与求值**,引擎不认识它(v2 在引擎里求值,v3 拆出;v3.1 连结局词汇也留在组件层) |
| **Capability(能力标签)** | 外部能力标签:★v3.1 改为**字符串**,词汇由提供方注册(如某宿主扩展注册自己的领域标签)——引擎不定义任何具体标签 | 进程级 | 无 | MatchModeMeta.requiredCapabilities 声明,框架校验(§3.2 阶段 A);缺失 → `REJECTED_BY_TARGET_MODE`(detail 列缺失标签) |
| **ServiceRegistry** | ★v4.1 **进程级服务装配容器**:两阶段装配——`install`(仅声明)→ `seal`(依赖校验 → 拓扑排序 → 按序创建 → start → 注册能力标签);消费面仅 `install/seal/get/require/shutdown` 五方法 | 进程级(`onEnable` 装配 → `onDisable` 关停) | 容器编排 | 缺必需依赖/依赖环 → `ServiceDependencyException` 点名;任一工厂/start 抛 → 逆序回滚已启动服务再抛;不进 `MiniGameApi` 冻结面(§2.9) |
| **ServiceSpec** | ★v4.1 **服务声明式描述符**:`id/type/factory/requires/requiresOptional/capabilities`,Builder 构建,构建期校验 id 非空 | 进程级 | 工厂体 | **无 `freeze()`**(Spec 由 L0 现场构建、只被一个注册表消费);工厂收 `ServiceEnv` 而非 svc(§2.9) |
| **ServiceEnv** | ★v4.1 **服务工厂取物口**:`dep/depOpt/plugin/cfg` | 进程级 | 无 | `dep` 拓扑序保证就绪、取不到响亮抛;`depOpt` 缺席 empty 不抛;`cfg()` 返回惰性只读 `ConfigView` |
| **ServiceLifecycle** | ★v4.1 **服务可选生命周期**:`start/stop`,默认空实现 | 进程级 | 无 | 纯无状态服务不必实现;实现者须保证 **stop 与 start 严格对称** |

### 2.3 `MatchMode`:聚合根的形状(逐字段对照角色系统)

```java
package com.hydrokarbs.engine.mode;

/**
 * 模式聚合根。★ 全类零行为分支——形状逐字段对照角色系统 core/Role:
 *  - Role: id/displayName/description/icon/defaultFaction + 组件表
 *    MatchMode: id/displayName/description/icon/mapTags/MatchModeMeta + 组件表
 *  - Role 的阵营是"模板上唯一的静态声明,实例真值在组件里";
 *    MatchMode 的角色策略/阶段表/结束条件同理:模板上只是组件 Spec 的构造数据。
 * 新增一个模式 = 用 Builder 拼一张组件表;不存在"实现 MatchMode 接口"这回事。
 */
public final class MatchMode {

    private final String id;
    private final net.kyori.adventure.text.Component displayName;
    private final List<net.kyori.adventure.text.Component> description;
    private final Material icon;                 // 入口牌子/GUI 用
    private final Set<String> mapTags;           // 支持哪些地图(按 MapDefinition.tags 匹配)
    private final MatchModeMeta meta;            // requiredCapabilities/recordsHistory/人数窗/缺省去向(★v3.2:joinPolicy 已下放组件)

    /** 唯一有序组件描述符表:LinkedHashMap,声明序 = 装配调用序 = 生命周期/事件派发序。 */
    private final Map<String, ComponentEntry> components;

    private MatchMode(Builder builder) { /* 全 final 拷贝,无派生视图,无行为 */ }

    // ── 仅有的两个方法(都是装配期职责,照抄 Role) ──────────────────────

    /** 装配期依赖检查:缺必需依赖抛异常。切换阶段 A5 调用,失败则切换被拒、旧实例无损。 */
    public void verifyDependencies() { /* 算法逐行照抄 Role#verifyDependencies,见 §2.6 */ }

    /** 造实例的唯一入口:先 verifyDependencies 再造 —— 任何路径不可能绕过检查(照抄 Role#createInstance)。 */
    public MatchModeInstance createInstance(Session session, MapDefinition map, MatchModeConfig cfg,
                                       WorldHandle world, Handoff handoff, EngineServices engine) {
        verifyDependencies();
        return new MatchModeInstance(this, session, map, cfg, world, handoff, engine);
    }

    /** 装配条目:(工厂, 描述符类型, 提供类型, 必需依赖, 可选依赖) 的不可变快照。不持有 Spec 对象。 */
    public record ComponentEntry(
            MatchModeComponent.Factory<? extends MatchModeComponent> factory,
            Class<?> descriptorType,
            Class<? extends MatchModeComponent> providedType,
            List<Class<? extends MatchModeComponent>> requiredTypes,
            List<Class<? extends MatchModeComponent>> optionalTypes) {}

    public static final class Builder {
        public Builder(String id) { /* 空校验,同 Role.Builder */ }
        public Builder displayName(Component c);
        public Builder description(List<Component> lines);
        public Builder icon(Material icon);
        public Builder mapTags(Set<String> tags);
        public Builder meta(MatchModeMeta meta);
        /** 统一装配入口:绑 id → freeze() 取快照 → 入表。id 跨类型去重(同一命名空间)。 */
        public Builder addComponent(String id, MatchModeComponent.Specification<?> spec);
        public MatchMode build();   // 兜底同 Role:displayName 缺省 = id,description 缺省 = 占位文案
    }
}
```

```java
/** 模式元数据:纯数据,无行为。v2 的 requires()/recordsHistory()/transition()/人数窗
 *  四个接口方法收敛到这里(★v3.2:joinPolicy 曾在 v2/v3 收敛为本 record 字段,现已
 *  下放为 JoinControlComponent——入场路由是行为,归组件,§3.2.1、§0.5.4)。★v3.1:能力标签字符串化,不再提供 LOBBY/COMPETITIVE 预设——
 *  预设把 "role"/回退去向等内容词汇写进引擎;各模式工厂自建 meta(§12.4;SHDF 玩法线的工厂示例见 Shdf具体玩法设计案/04-大厅模式.md §4.2)。
 *  注:下方字段注释中的"大厅/lobby"为 SHDF 提供的示例模式 id,非引擎字面量(Lobby 概念行见
 *  CONTEXT.md,本文档内仅为注释级提及;实现见 Shdf具体玩法设计案/04-大厅模式.md)。 */
public record MatchModeMeta(
        Set<String> requiredCapabilities,   // 能力标签(字符串;词汇由提供方注册,如某宿主扩展注册自己的领域标签。空 = 无依赖,大厅即空)
        boolean recordsHistory,             // 是否写 match_history/stats(大厅 false)
        int minParticipants,
        int maxParticipants,
        DefaultTransition defaultTransition // FALLBACK(切到 session.fallback-mode 配置的回退模式)/ STAY / ROTATION(读配置轮换表)
) {
    public enum DefaultTransition { FALLBACK, STAY, ROTATION }
    // ★v3.1 删除:v2/v3 曾有 LOBBY/COMPETITIVE 两个预设常量——它们把 "ROLE" 能力与
    // 回退去向写死在引擎类型上,违反「框架不认识内容」。元数据由各模式工厂逐字段声明。
}
```

> **为什么拆掉 v2 的 `plan(map, cfg)`**:运行差异(哪张图、什么参数、交接了什么)不再经由"重新产出一个计划对象"表达,而是经 `createInstance` 的参数进入 `MatchModeInstanceServices`,由各组件在 `awake()/start()` 里自行取用(`svc().map()` / `svc().cfg()` / `svc().self().handoff()`)。**模式模板因此可以是进程级单例**,不必每次运行重建——这正是 Role 的形状:模板不变,实例万变。

### 2.4 `MatchModeComponent`:行为单元基类(照抄角色系统组件基类的纪律)

```java
package com.hydrokarbs.engine.component;

/**
 * 模式组件基类。纪律逐条来自角色系统组件基类(v3 参照物,参照关系见章首参照框注):
 *  - 只允许出现 svc 字段 + 钩子方法 + getComponent —— "顺手加个 helper"属越界;
 *  - svc 构造期注入四条件:①注入先于一切钩子 ②final 只注一次 ③svc() 未注入即抛
 *    ④组件构造点唯一(容器内单一创建路径,id 与服务集成对产生);
 *  - 基类不认识子类:不为能量/队伍/阶段/角色设任何通用视图(要协作就 getComponent)。
 */
public abstract class MatchModeComponent {

    private final String id;
    private final MatchModeInstanceServices svc;

    protected MatchModeComponent(String id, MatchModeInstanceServices services) {
        if (id == null || id.trim().isEmpty()) throw new IllegalArgumentException("Component id cannot be null or empty.");
        if (services == null) throw new NullPointerException("MatchModeInstanceServices");
        this.id = id;
        this.svc = services;
    }

    public final String id() { return id; }
    protected final MatchModeInstanceServices svc() { /* 未注入即抛,绝不静默 null */ }
    /** 按类型取同实例内的另一组件(未注册 → null;要全部符合者用 svc().components().getAll(type))。 */
    protected final <T extends MatchModeComponent> T getComponent(Class<T> type) { return svc().components().get(type); }

    // ── 生命周期:框架按声明序无条件广播 ─────────────────────────────

    /** 装配阶段:只解析跨组件依赖并缓存引用。幂等;不得改动任何玩家可见状态。 */
    public void awake() {}
    /** 开始生效:初始化数据、传送、发装备、登记显示。玩家可见副作用最早发生在这里。 */
    public void start() {}
    /** 每 tick(由 EngineTicker 按实例周期驱动)。禁止阻塞、禁止登记不回收的资源。 */
    public void update() {}
    /** 实例事件钩子(中央总线;订阅发生在构造/awake 期,随 stop 自动回收)。 */
    public void onEvent(MatchModeInstanceEvent event) {}
    /** 切换出局的交接钩子:向 out 写本组件想带走的载荷(状态尚完整,但不得再改玩家)。 */
    public void onHandoff(Handoff.Builder out) {}
    /** 停止生效:与 start 严格对称。返回后框架自动回收本组件登记的资源(订阅/延时任务/显示)。 */
    public void stop() {}

    // ── 装配期描述符(照抄角色系统组件基类的 Specification) ──────────────

    public abstract static class Specification<T extends MatchModeComponent> {
        /** 诊断标签(只进装配期异常文案,无行为分支读它)。 */
        protected Specification(String descriptorLabel);
        /** 声明必需依赖类型:装配期缺任一则该模式注册失败(响亮失败)。 */
        public final Specification<T> requires(Class<? extends MatchModeComponent> type);
        /** 声明可选依赖类型:缺失不报错,组件运行期自查。同一类型不得既必需又可选。 */
        public final Specification<T> requiresOptional(Class<? extends MatchModeComponent> type);
        /** 本组件提供的类型(供给面):默认由泛型实参推导,家族描述符可覆写为具体类。 */
        public Class<? extends MatchModeComponent> providedType();
        /** ★v3 特有:地图适配声明(默认通过)。切换阶段 A3 对全表调用,任何一条不通过 → REJECTED_BY_TARGET_MODE(detail 带问题清单)。 */
        public List<String> checkMap(MapDefinition map, MatchModeConfig cfg) { return List.of(); }
        /** 冻结:子类自检 → 返回不可变 Snapshot,此后 Spec 拒改(共享实例防串改)。 */
        public final Snapshot freeze();
        /** 抽象创建:由具体描述符决定造哪个组件类。容器把 id 与 svc 成对交给它。 */
        public abstract T create(String id, MatchModeInstanceServices svc);

        public record Snapshot(String descriptorLabel, Factory<?> factory,
                               Class<? extends MatchModeComponent> providedType,
                               List<Class<? extends MatchModeComponent>> requiredTypes,
                               List<Class<? extends MatchModeComponent>> optionalTypes) {}
    }

    @FunctionalInterface
    public interface Factory<T extends MatchModeComponent> { T create(String id, MatchModeInstanceServices svc); }
}
```

> **与角色系统的一个刻意差异**:角色系统的组件基类没有 `onEvent` 钩子(角色系统的事件都挂在具体组件的监听面上)。我们的实例事件是**中央总线**(合成事件/结构事件统一进 `MatchModeInstanceEventBus`),所以基类多一个 `onEvent` 钩子——这是"玩法差异大"带来的必要泛化,但不破坏"基类不认识子类"纪律:钩子收到的是 `MatchModeInstanceEvent` 根(★v3.1:开放接口——可能是引擎的结构事件,也可能是任何组件或宿主扩展发布的类型,见 §12.2),基类不认识任何具体事件类型。

> **为什么 `end()` 是端口而不是引擎去轮询组件**:角色系统的组件从不"被框架询问是否该结束"——组件主动发起(技能释放、伤害结算都由组件触发)。对齐这一心智:结束也是**组件的主动声明**(EndGateComponent 求值命中后调 `svc().self().end(...)`),引擎只负责收口与切换。框架"不提供框架级状态机"的准确含义就在这里——**引擎不解释玩法什么时候结束、怎么推进,只提供"结束/切换"这两个口**。

### 2.5.1 `SessionComponent` 与 `SessionServices`(★v4 新增:会话级组件)

会话的*策略与行为*不再写死在 `SessionPolicy`:v4 把它们下放为**会话级组件**——形态照抄实例级(§2.4/§2.5),挂载级从"随实例"换为"随会话";`SessionServices` 是它的 svc 服务集。

```java
package com.hydrokarbs.engine.component;

/**
 * 会话级组件基类。纪律逐条照抄 MatchModeComponent(§2.4):
 *  - 只允许出现 svc 字段 + 钩子方法 + Specification —— "顺手加个 helper"属越界;
 *  - svc 构造期注入四条件:①注入先于一切钩子 ②final 只注一次 ③svc() 未注入即抛
 *    ④组件构造点唯一(注册表内单一创建路径,id 与服务集成对产生);
 *  - 基类不认识子类:要协作就经 svc().components() 取强类型读口。
 */
public abstract class SessionComponent {

    private final String id;
    private final SessionServices svc;

    protected SessionComponent(String id, SessionServices services) {
        if (id == null || id.trim().isEmpty()) throw new IllegalArgumentException("Component id cannot be null or empty.");
        if (services == null) throw new NullPointerException("SessionServices");
        this.id = id;
        this.svc = services;
    }

    public final String id() { return id; }
    protected final SessionServices svc() { /* 未注入即抛,绝不静默 null */ }

    // ── 生命周期:会话装配期走向,框架按声明序无条件广播(stop 逆序) ──────

    /** 会话装配期(create 之后、首个实例之前):只解析会话级依赖并缓存引用;幂等;无可见副作用。 */
    public void awake() {}
    /** 会话创建完成、首个实例装配之前生效:订阅/登记显示/初始化会话级数据。 */
    public void start() {}
    /** 每 tick 由引擎派发,**与"当前是否有实例"无关**;禁止阻塞、禁止 IO。 */
    public void update() {}
    /** 会话事件钩子(中央总线广播;订阅随 stop 自动回收)。 */
    public void onEvent(SessionEvent event) {}
    /** dissolve(或隔离)时:与 start 严格对称;返回后框架自动回收本组件登记的资源。 */
    public void stop() {}

    // ── 装配期描述符(照抄 MatchModeComponent.Specification;★v4 增 capabilities) ──

    public abstract static class Specification<T extends SessionComponent> {
        /** 诊断标签(只进装配期异常文案,无行为分支读它)。 */
        protected Specification(String descriptorLabel);
        /** 声明必需依赖类型:装配期缺任一 → 会话创建失败(响亮,见下)。 */
        public final Specification<T> requires(Class<? extends SessionComponent> type);
        /** 声明可选依赖类型:缺失不报错,组件运行期自查。同一类型不得既必需又可选。 */
        public final Specification<T> requiresOptional(Class<? extends SessionComponent> type);
        /** ★v4:本组件注册的能力标签(随 dissolve 摘除;词汇由提供方定义,引擎零字面量)。 */
        public final Specification<T> capabilities(String... tags);
        /** 本组件提供的类型(供给面):默认由泛型实参推导。 */
        public Class<? extends SessionComponent> providedType();
        /** 冻结:子类自检 → 返回不可变 Snapshot,此后 Spec 拒改(共享实例防串改)。 */
        public final Snapshot freeze();
        /** 抽象创建:唯一创建点(会话装配期由注册表调用,id 与 svc 成对交给它)。 */
        public abstract T create(String id, SessionServices svc);

        public record Snapshot(String descriptorLabel, Factory<?> factory,
                               Class<? extends SessionComponent> providedType,
                               List<Class<? extends SessionComponent>> requiredTypes,
                               List<Class<? extends SessionComponent>> optionalTypes,
                               Set<String> capabilities) {}
    }

    @FunctionalInterface
    public interface Factory<T extends SessionComponent> { T create(String id, SessionServices svc); }
}
```

```java
package com.hydrokarbs.engine.port;

/**
 * 会话组件的 svc 服务集。★ 成员封闭(2 个)——与实例级同一条纪律:
 * 显示/持久化/角色/世界不在这里转发;要用就拿组件本身(svc().components().get(...)),
 * 或走 self() 上的端口组(含 ★v4 新增的 requestSwitch/requestDissolve 两个行动口)。
 */
public record SessionServices(
        SessionPort self,                    // 会话自面:members/tick/attrs/events/currentInstance + requestSwitch/requestDissolve
        SessionComponentLookupPort components // 会话组件查找(按类型/按 id,含 getAll)
) {}
```

> **注入与装配**:svc 由**会话装配**在构造期注入,四条件与实例级完全一致(§2.4)——①注入先于一切钩子 ②final 只注一次 ③`svc()` 未注入即抛 ④组件构造点唯一。装配点唯一:会话创建内先 `verifyDependencies()`(缺会话级必需依赖 → 抛,**会话创建失败**,L0 SEVERE)再按声明序 `create(id, svc)`;会话组件先于首个实例就绪(首实例的组件才查得到它们)。

> **派发**:按**声明序**广播,`stop` **逆序**;`stop` 由框架**无条件**调用(无单例豁免条款——这正是"组件"与"内核机制"的分界,§2.8 决断一)。`update` 每 tick 派发,与"当前是否有实例"无关(切换间隙照常)。

> **"每会话一份"**:会话级组件在**会话生命周期内**是单例——同一 Session 内 `Specification#create` 至多调用一次,此后一切查询(实例组件、会话组件互查、会话内核)恒返回同一实例;**跨会话不共享**(arena 拓扑下 N 个会话并发跑同一模板,进程级单例会串台)。机械保证:注册表挂在 `Session` 上,**不是进程级静态**;`SessionComponentSingletonTest` 冻结(同 Spec 装配两个会话 → 两个不同实例;同会话查询恒同一实例;跨会话互不可见)。共享的只能是不可变声明(Spec/Snapshot),有状态实例永不跨会话共享。

> **故障隔离**(会话级 quarantine):`update`/`onEvent` 抛异常 → 记日志(会话 id / 组件 id / 原因)→ 对该组件 `safeStop` + 打标 quarantined(此后跳过其派发)→ 发 `SessionComponentQuarantined` 会话事件 → **会话不解散**,其余组件照常。与实例级的差异:**实例级**隔离 → `end()` → 回退模式(模式坏了有兜底);**会话级**没有回退目标,解散代价过大——停用单个策略组件是可接受的降级(空场策略停用 = 行为退回"永不解散"并留日志)。装配期 `awake/start` 抛 → 会话创建失败(L0 SEVERE;arena 则该竞技场不启动)。

### 2.6 装配期依赖校验(算法逐行照抄 `Role#verifyDependencies`)

| 规则 | 内容(与角色系统完全一致) |
|---|---|
| 检查时机 | 两处:`MatchModeRegistry` 注册之前(坏模板不进注册表)+ `createInstance` 之前(实例化前的最后闸) |
| 匹配规则 | A 的必需类型 R 被满足 ⟺ 存在另一组件 B(id ≠ A)使 `R.isAssignableFrom(B.providedType())`;**自己不算自己的提供者** |
| 失败形态 | 抛 `ComponentDependencyException`,消息点名"模式/组件 id/缺的类型";注册期失败 → 该模式跳过并 SEVERE;切换期失败 → `REJECTED_BY_TARGET_MODE`(detail 带异常消息),旧实例无损 |
| 不检查什么 | 可选依赖缺失不报错;**环不检查**(允许环形依赖,awake 顺序 = 声明序,环内"谁先醒"未定义——不得依赖) |
| 自环 | A 声明自己提供的类型 → 仍算缺依赖(硬失败) |

### 2.8 设计决断(v2 保留一条,v3 新增两条;★v4 决断一重写、决断三扩展、新增决断四;★v4.1 决断一三问修订、新增决断五)

#### 决断一(★v4 重写;★v4.1 三问修订):组件两级挂载——机制在内核,策略在组件,跨会话聚合在服务

**Component 有两种挂载级,仅两种**:实例级 `MatchModeComponent`(生命周期随 `MatchModeInstance`,`close()` 全灭,§2.4)与会话级 `SessionComponent`(★v4,生命周期随 `Session`,**每会话一份**,跨模式切换存活、随 `dissolve` 全灭,§2.5.1)。禁止第三级;禁止同一组件类兼任两级——同一行为若要跨级,拆成两个组件、经"只读查询 + 端口"协作(决断四)。★v4.1 新增的**进程级服务**(§2.9)不是第三级组件挂载级,是与组件并列的另一类对象。"如果一段行为需要跨模式存活"不再是唯一判据——★v4.1 两问扩为三问:一问是否跨模式存活,二问机制还是策略,三问状态按会话隔离还是跨会话聚合:

| 判定 | 归属 | 例 |
|---|---|---|
| 不需要跨模式存活 | 实例级组件 | 阶段/计分/队伍/结束判定 |
| 跨模式存活,且是机制/状态权威/可靠性底线 | `SessionService` 内核 | 名册、连接追踪、切换算法、世界引用计数 |
| 跨模式存活,且是策略/裁决/聚合/展示,**状态可按会话隔离** | 会话级组件 | 空场解散(已实现);断线宽限等(候选) |
| **状态必须跨会话聚合,或本就是进程级机制/外部世界翻译** | **进程级服务(★本版新增)** | 全服账本、全局看板、配对队列、经济适配 |

争议仲裁:拿不准时问三问——一问"它需要跨模式存活吗?"(否 → 实例级组件);二问:"它坏了会话会失守底线(名册错/世界漏/切换不原子)吗?"(是 → 内核);"服务器主想要另一种做法吗?"(是 → 组件)。三问"它的状态按会话隔离,还是必须跨会话聚合?"(隔离 → 会话级组件;跨会话聚合,或本就是进程级机制/外部世界翻译 → 进程级服务)。内核向组件只提供端口与事件;组件向内核只经端口请求(决断四);服务与组件互不可见(§2.9)。

#### 决断二(v3 新增):聚合根零行为,行为溢出即设计失败

`MatchMode` 上出现任何"顺手的方法"(v2 的 `plan()`/`transition()`/`validateMap()`/`rolePolicy()` 都犯过)都意味着**有一段行为找不到组件之家**。正确的动作永远是:给某个组件的 `Specification` 加构造数据,或新造一个组件。角色系统 `Role` 类为删掉的 `getFaction()/setFaction()` 写的墓志铭是最准确的表述模板:"①语义不符(模板级口子改的是所有实例);②无消费者(读写都有专门归属)"。本框架同理:`MatchMode` 上每删一个方法,架构纯度就升一格。

> **验收机械**:`AggregatePurityTest` 反射冻结 `MatchMode` 的公开方法集 = `{verifyDependencies, createInstance, id, displayName, description, icon, mapTags, meta, components}`——任何新增方法直接测试红(§16.2-★22)。

#### 决断三(v3 新增):状态唯一——容器不持有玩法状态

`MatchModeInstance` 的形状照抄 `RoleInstance`:不持有 team/score/进度/占用表,甚至**不持有组件实例的长期引用**(构造期用局部变量装配,此后按 id/类型现取)。所有玩法状态住在各自组件里,组件是状态的唯一主人并提供强类型读口。收益与角色系统实测一致:状态不会在"容器与组件"两处漂移;隔离一个坏组件时,它的状态随它一起消失,不污染容器。

> **★v4 扩展(会话级状态)**:`Session`(会话容器)同样**不持有会话组件的状态**——会话组件的状态住在组件自己里,组件是它的唯一主人并提供强类型读口;更进一步,实例组件与会话组件**互不写入**(只读 + 端口,决断四)。隔离一个坏会话组件时,它的状态随 `stop`/隔离一起消失,不污染会话容器(与实例级同一条纪律)。

#### 决断四(★v4 新增):跨级只读——跨级查询只读,跨级干预只走端口

组件协作多了一维:实例组件 ↔ 会话组件。跨级只有"只读查询"与"端口"两种通道,且方向对称:

| 方向 | 通道 | 授权 |
|---|---|---|
| 实例组件 → 会话组件 | `svc().self().session()`(`MatchModeInstancePort` 新增方法)→ `SessionView#component(Class<T extends SessionComponent>)` | **只读**;不得订阅会话事件(第一版,未决) |
| 会话组件 → 实例组件 | `svc().self().currentInstance()` → `Optional<MatchModeInstanceAccess>`;`MatchModeInstanceAccess#component(Class<T extends MatchModeComponent>)` | **只读**;无实例或 `ENDING/SWITCHING` 间隙 → `empty`;**不得缓存实例组件引用越过切换**(现取不缓存) |
| 会话组件 → 实例干预 | 只有 `requestSwitch()` / `requestDissolve()` + 事件 | 等价于实例级 `end()`/`switchTo()` 的口径 |
| 实例组件 → 会话干预 | 只有原有 `end()` / `switchTo()`;会话级干预**不提供**(模式无权解散会话,第一版) | — |

- 跨级干预只走端口:`end()`/`switchTo()` ↔ `requestSwitch()`/`requestDissolve()`;**跨级引用不得跨切换缓存**(切走后 `MatchModeInstanceAccess` 即时失效,违者即悬空引用);
- "只读"是**架构纪律 + review 条款**(无法机械强制调用方不碰写方法);写入 `14-陷阱清单` 与 code review checklist。

#### 决断五(★v4.1 新增):宿主先于接缝

"要加一个常驻能力"时,先决定宿主(组件级/L1/进程级服务/伴随插件,§13 选型四案),再决定接缝(是否需要 Port/组件读口/事件/API)——**Port 不是宿主**;给 `MatchModeInstanceServices`/`SessionServices` 加成员永远是错误答案(★25)。

### 2.9 进程级服务(★v4.1 新增:与组件并列的另一类对象)

> **服务(Service)是进程生命周期的非组件对象**:不挂进会话/实例、不进组件表、不随任何 Session/Instance 生灭(`onEnable` 装配 → `onDisable` 关停);彼此经 **`ServiceRegistry`** 统一装配——两阶段:`install` 声明 → `seal` 依赖校验 + 拓扑序创建 + 启动,任一工厂/start 抛 → **回滚已启动服务(逆序 stop)再抛**,不留半启动态(镜像 switchMode"绝不停在中间态")。**组件体系与服务互不可见**,`MatchModeInstanceServices`(3)/`SessionServices`(2)成员数不变(§2.5、§2.5.1);契约骨架与 L0 接线见 12(§12.2),决策记录见 ADR-0006(`docs/adr/0006-process-service-registry.md`;修正案原文编号 0005,因 docs/adr/0005 已被《架构冻结测试门禁》占用,顺延为 0006)。

**与组件的三条硬边界(D1;A10 原文保留——服务不是第三级*组件*):**

1. **不进组件描述符表**:`svc().components()` 查不到任何服务;
2. **无五钩子派发、不占 `tickAll` 任何一步**:awake/start/update/onEvent/stop 的组件派发链与服务无关——服务自行经 `ServiceLifecycle#start` 订阅事件驱动;
3. **双向 import 冻结**:组件与模式**不得 import** 服务类型(`engine/service/**` 与 `service/**`),服务**不得 import** `mode/**` 与 `component/**`(ArchUnit,★40)。

**服务 ↔ 会话:三条通道,无第四条(D5):**

| 通道 | 方向 | 授权 |
|---|---|---|
| **订阅 `SessionEventBus`**(`SessionCreated / MemberJoined/Left / ModeSwitchStarted / ModeSwitchCompleted / SessionDissolved / SessionComponentQuarantined`) | 会话 → 服务 | 感知生灭的官方通道(§3.1 事件行既有定位"给跨切面逻辑用");订阅句柄在服务 `stop` 中注销 |
| **只读快照**(`MiniGameApi.sessions()` 不可变 record;引擎内代码可经 `SessionService` 遍历 + `MatchModeInstanceAccess`) | 会话 → 服务 | 只读;**不得持有活实例/活组件引用跨切换**(镜像 ★29 的"现取不缓存"纪律) |
| **受控命令**(`SessionService#switchMode / dissolve / createSession`) | 服务 → 会话 | 服务属**外部调用方(切换来源②)**,与 `/sm` 命令同权;`force` 是显式选择,走 review 条款;无其他影响力端口 |

**与组件 `Specification` 的两处刻意差异(D3):**

| 差异 | 内容 |
|---|---|
| **无 `freeze()`** | 组件 Spec 需要冻结是因常量 Spec 跨模式共享(SHDF 玩法线的共享策略 Spec 常量,如其 `BOMB_POLICY`,见 Shdf具体玩法设计案/08-角色桥接.md);服务 Spec 由 **L0 现场构建、只被一个注册表消费**,无共享串改问题——不加仪式(YAGNI) |
| **工厂收 `ServiceEnv` 而非 svc** | 服务不持服务集 record,依赖在创建期经 `env.dep(Class)` 注入(拓扑序保证就绪);`depOpt` 表达可选依赖(缺席 empty 不抛);`plugin()`/`cfg()` 提供平台原语(`cfg()` 返回惰性 `ConfigView`,`/reload` 后自动读新值) |

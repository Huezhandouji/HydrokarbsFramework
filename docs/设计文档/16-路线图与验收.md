> **为什么组件三迁(P0.5)与宿主桥接(P2)这样排**(v3 调整):三个"引擎降级组件"必须在任何真实模式之前成型,否则模式开发期间一定会出现"顺手在引擎加回调"的回流(陷阱 §14.24);而它们不依赖任何宿主扩展线,可与宿主桥接线并行(角色系统接入属 SHDF 扩展线,见 Shdf具体玩法设计案/)。
>
> **为什么 P1.5 会话级组件层排在 P2 之前**(v4 新增):两级挂载机制必须在模式/桥接开发之前落定,避免会话级需求回流。
>
> **为什么 P0.6 进程级服务装配排在 P1 之前**(v4.1 新增):服务层是机制类基建,离线可测;早建防"进程级需求被顺手写进内核/模式"的回流。
>
> **为什么 G1(G2)这样排**(v1.1 新增):过早物理拆分会把 API 面的每个瑕疵固化成二进制契约(Hyrum 定律)——先在单 jar 内把边界守成铁的(白名单纪律 + ApiSurfaceTest),拆分只是换打包方式;G2 不设时间表,只认触发条件(首个真实跨 jar 消费者,A13——Assumption-driven,不做 hypothetical seam)。
>
> **★用户排期决议(2026-10-25,施工排期叠加注)**:施工执行排期上,阶段7 的 **7.1 → 7.2 → 7.5(G1)提前至阶段4(P3)之前**执行、**7.4(全量验收)后置至阶段4 完成后**执行;阶段8(G2)仍按 A13 触发条件——**本表为设计依赖与路线记录,该决议是排期决议、不改变设计依赖**(7 的主体只依赖 P1 会话层;组件库经模式 Builder 消费、不进 API 面,后补为「只增」关系;决议注全文见施工计划 `README.md` §1/§2)。
